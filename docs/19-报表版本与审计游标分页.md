# 报表版本回滚与审计游标分页

> 对应代码：`app/report/revisions.py`、`app/api/reports.py`、`app/api/audit.py`、`app/templates/reports.html`、`app/templates/audit.html`
> 回归：`scripts/smoke_report_version.py`（82 项）

这两件事在 `docs/17` 里被列为"暂不做"，理由是它们和已有约定冲突。本文说明冲突到底在哪、怎么解掉的。

---

## 一、报表回滚：和"一期一份"看起来必然冲突

### 冲突在哪

`docs/17` 把报表改成了"一期一份"：`report` 表里同一 `(period, line)` 只有一行，
重新生成＝覆盖并升版本，靠 `version` + 唯一索引 `ux_report_period_line` 保证。

这个决定解决了"同月堆 15 份、数字互相矛盾"，但代价是**旧内容被物理覆盖**。
于是"回滚到上一版"根本无从谈起——数据已经不在库里了，`audit_log` 里只留了
摘要前 250 字，拿它还原创不出一份完整月报。

表面上看，两个诉求只能二选一：

- 一行一期 → 归档件唯一，导出编号唯一，但旧版没了
- 每版一行 → 旧版都在，但列表里又有 15 份"2026-10"，回到了原来的问题

### 解法：把"当前状态"和"历史版本"分成两张表

| 表 | 存什么 | 谁在读 |
|---|---|---|
| `report` | 只有**当前**这一版，一行一期 | 列表、详情、导出、编号 |
| `report_revision` | 被替掉的**每一版整份快照**，只追加 | 版本历史、回滚 |

`report` 的约束一条没放松，`report_revision` 又让历史一版不少。两个诉求同时成立。

`report_revision` 字段：`report_id / period / line / version / data_json /
generated_at / archived_at / reason / actor`。

- `generated_at` 是**当初生成时刻**，`archived_at` 是**被替掉的时刻**——两个时间
  不能混，否则"这版是哪天报上去的"就答不上来
- `reason` 记 `regenerate`（重新生成）或 `rollback`（回滚前留档）
- `actor` 记**谁**触发的覆盖。审计里的 `actor=system` 只能说明"报表 Agent 干的"，
  指不到人

### 两条硬规则

**规则 1：覆盖前必须先归档。**

```python
archive(rep, "regenerate", actor)      # 先
rep.version += 1                       # 后
rep.data_json = json.dumps(data)       # 后
```

顺序反了旧内容就物理消失，**而且不会报错**——只是删掉了一列的值，事务照常提交。
这是最难查的一类问题，所以测试里专门用"逐字节比对"把它钉死：

```python
check("历史快照与覆盖前那份逐字节相同", hist.get(1) == raw_v1)
```

**规则 2：回滚 = 用旧内容生成新一版，版本号继续往上走。**

回滚**不把 `version` 改回旧号**。原因：版本号是归档件的唯一标识
（"2026-10 第 3 版"会印在导出件的文件头、也会被人写进汇报材料），
一旦允许重号，这个标识就同时指向两份不同内容，等于废掉。

所以回滚的实际语义是：

```
当前 v3  →  回滚到 v1  →  v1 归档（若尚未归档）
                        →  v3 整份存入 report_revision（reason=rollback）
                        →  新内容 = v1 的 data_json
                        →  version = 4，rollback_from = 1
```

界面上写的是"第 4 版（回滚自第 1 版）"，可追溯但不混淆。
`rollback_from` 是新增列（`_migrate_report_table()` 幂等补列），
**默认 NULL 而不是 0**：0 不是合法版本号，写成 0 会让前端把"没回滚过"
画成"回滚自第 0 版"。

### 接口

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/reports/<id>/versions` | `report.view` | 当前版 + 全部历史版，各带摘要前 60 字 |
| POST | `/api/reports/<id>/rollback` | `report.generate` | body `{"version": N}`，不传则回上一版 |

权限刻意分开：**街道能看历史，不能回滚**。回滚是改归档件，写操作挂 `report.view`
的话，监督者就能改被监督的数据。

回滚失败的两种情况都给出可选项，不只说"不存在"：

- 目标 = 当前版 → `第 3 版就是当前版本，无需回滚`
- 目标不可用（越界 / 没有快照）→ `回滚目标第 99 版不可用，当前是第 3 版（可回滚：第 1、2 版）`

### 界面

`/reports` 详情卡右上加了「🕘 版本历史」按钮，展开后是一张表：
版本号、摘要（前 60 字）、生成时间、操作。当前版标 `当前`，
回滚出来的版标 `↩ v1`。回滚按钮只在有 `report.generate` 时出现，
`confirm()` 明确写"当前版本会先整份存档（不会丢），回滚后生成的是新版本号"——
不写这句，用户会以为版本号会倒退，事后找不到"刚才那份"。

## 二、审计日志：为什么必须换成游标

### offset 分页在这个场景是错的

审计日志是**只追加**表：新记录永远插在最前面。用 `LIMIT n OFFSET m` 会同时遇到两个问题：

1. **翻页期间有新写入 → 内容整体后移 → 第 3 页出现第 2 页的记录，同时漏掉几条。**
   这不是理论上可能，只要有人在用系统就必然发生——而审计表恰恰是"一直有人在写"的表。
2. **`OFFSET 50000` 要先数过五万行再丢弃**，越翻越慢。

### 游标怎么定

游标 = `(created_at, id)` 的 base64url，条件写成：

```sql
WHERE (created_at < :ts) OR (created_at = :ts AND id < :cid)
ORDER BY created_at DESC, id DESC
LIMIT :n + 1
```

**必须带 `id`**：同一次批量写入的若干条，时间戳可能完全相同（秒级精度）。
只比时间会在这一秒的边界上漏记录——测试专门造了三条同秒记录来验证。

**多取一条**（`LIMIT n+1`）只为判断"还有没有下一页"，省掉一次 `COUNT`。

索引 `ix_audit_created_id (created_at, id)` 由 `_migrate_audit_table()` 建。
列顺序不能反：`created_at` 在前才能直接满足 `ORDER BY`，`id` 在后用于同秒内的边界定位。

### 参数与返回

| 参数 | 说明 |
|---|---|
| `agent` | 按 Agent 筛（原有） |
| `action` | 按动作筛（新增，`deny` = 越权） |
| `limit` | 默认 100，上限 500；非正值/非数字回默认 |
| `cursor` | 上一页返回的 `next_cursor` |

`counts` 新增 `has_more` / `next_cursor`，保留 `truncated`（= `has_more`）兼容旧字段。
`total` / `security` / `deny` 三个家底数字**不随筛选、不随翻页变化**——
筛"保密审查"时把总数改成 96，会让人以为总共只有 96 条留痕（`docs/14` 的老坑）。

### 坏游标不报错

游标是前端存下来的，可能来自旧版本、可能被手工改过。为它回 400 会让用户
卡在一个翻不动的页面上——它只是个位置，退回第一页比报错有用。
`_decode_cursor()` 吞掉所有解码异常，返回 `None`，等同于首屏。

### 界面

`/audit` 底部加「加载更多」+「已显示最近 N 条 / 已全部加载」。
翻页是**追加不清空**（`ROWS = ROWS.concat(list)`），切 Agent 筛选才重置。
动作列里 `deny` 单独标红——越权拒绝是这一页最该被一眼看到的东西。

## 三、测试覆盖（`scripts/smoke_report_version.py`，82 项）

| 组 | 项数 | 锁住什么 |
|---|---|---|
| 首次生成 | 8 | v1、无历史、一行一期 |
| 重新生成 | 12 | 升版、旧版入历史、**逐字节相同**、行数不变 |
| 回滚 | 14 | 版本号不倒退、`rollback_from`、内容等于旧版、当前版先归档、不新增行 |
| 回滚边界 | 13 | 同版被拒、越界被拒且列可选项、非整数被拒、默认上一版 |
| 权限 | 6 | 街道只看、物业 403、未登录 401、404 |
| 审计游标 | 11 | 不重不漏、全局有序、页数正确、到底即止 |
| 同秒边界 | 2 | 游标带 id 才不漏 |
| 筛选 + 游标 | 5 | matched 正确、家底不变、翻页仍不重不漏 |
| 参数边界 | 5 | 坏游标退首屏、limit 夹取值 |
| 审计留痕 | 4 | `rollback_report` 记人、写明从哪版到哪版 |

关键断言是"不重不漏"：从首页翻到底，把 `id` 收成集合，必须与库里的
`id` 集合**完全相等**。这比"翻页没报错"强得多——offset 分页也能不报错地漏记录。

## 四、明确不做的

- **回滚不能删历史**。`report_revision` 只追加，没有删除接口。归档件的历史
  如果可以删，就等于可以伪造"从来没改过"
- **不做"版本对比"视图**。现在只给摘要前 60 字，够看出"这一版说的是不是同一件事"；
  真要逐字段 diff，得先把两版 JSON 展平成可比结构，收益远小于复杂度
- **审计不提供"跳页"**。游标分页天然不支持跳到第 N 页（那样就要回到 offset）。
  审计的实际用法是"按 Agent/动作筛 + 从头看"，不是"翻到第 47 页"
- **不清理早期审计**。日志按等保要求至少留 6 个月，本项目不做自动归档；
  真上生产要按 `created_at` 分区迁移到独立表

## 五、部署注意

两个迁移都在启动时幂等执行，老库直接起就行：

- `_migrate_report_table()`：补 `report.rollback_from`（NULL）
- `_migrate_audit_table()`：建 `ix_audit_created_id`

老库里已经存在的历史报表**没有 `report_revision` 记录**，`versions` 接口
只会返回当前版一条。这是对的——那些版本的内容当初就没存下来，
编不出来也不该编。页面上会显示"暂无版本记录"。
