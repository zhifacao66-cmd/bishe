# 移动端适配

> 起因是一句话：「有些用户就只有手机。」
>
> 这句话在社区场景里不夸张——网格员在楼道里、物业师傅在天台、居民在楼下，
> 手上只有一部手机。而这个系统从第一版起就是按电脑配的。

## 1. 原来的手机上是什么样

布局的前提是三件事：

```css
body{display:flex}                    /* 侧栏 + 正文，两栏 */
.sidebar{width:230px;flex-shrink:0}   /* 侧栏固定，永不收缩 */
.content{grid-template-columns:repeat(12,1fr)}   /* 正文 12 栏 */
```

在 1440 的电脑上，正文还有 1180px，12 栏每栏 98px，一切成立。
在 375 的手机上，正文只剩 **145px** —— 比一个汉字表还窄。

更糟的是表格。9 个页面共 12 张表，全部没有滚动容器，而
`.card{overflow:hidden}` 会把超出部分直接裁掉。于是手机上看到的是
"表格右边被切平"，不是"可以滑过去"——用户根本不知道还有内容。

这些不是"不好看"，是**功能不可用**：工单状态列、签收按钮、报表操作列
全在右侧，裁掉就等于办不了事。

## 2. 断点为什么选 900

不是照抄的常用值，是按这个布局的实际宽度算的：

| 视口 | 减侧栏后正文 | col-5 实宽 | 结论 |
|---|---|---|---|
| 1440 | 1210 | 500 | 舒适 |
| 1024 | 794 | 327 | 仍可用（12 栏继续） |
| 900 | 670 | 275 | 临界，两栏挤 |
| 768 | 538（若仍留侧栏）| 220 | 不可用 |

所以 **≤900 换布局**：侧栏收起成抽屉，正文吃满宽。
**≤640 再紧一档**：`.card-h` 的说明文字折行、副标题隐藏、多列表单单列。

两个断点各自只做一件事，不叠太多条件——断点越少，越不容易在某个中间宽度
出现"两套规则都没覆盖"的空档。

## 3. 做了哪些改动

### 3.1 侧栏 → 覆盖式抽屉

```css
@media (max-width:900px){
  body{display:block;}
  .sidebar{position:fixed;left:0;top:0;bottom:0;width:min(80vw,304px);
    transform:translateX(-100%);transition:transform .24s ...;}
  .nav-open .sidebar{transform:none;}
  .nav-open{overflow:hidden;}      /* 抽屉开着时压住背景滚动 */
}
```

几个刻意的选择：

- **只切 body 上的一个 class**，位移交给 CSS。如果在 JS 里算 `style.left`，
  转屏或改浏览器字号后算出来的值立刻失配。
- **`overflow:hidden` 加在 `.nav-open` 上**。不加的话，手指在遮罩上滑动会把
  下面那页滚走，关掉抽屉后位置全乱。
- **`pageshow` 也复位一次**。从详情页后退回来时浏览器可能带着 bfcache 里的
  class，出现"抽屉开着、汉堡却没了"。
- **点导航自动收起**，否则从详情返回列表时抽屉还敞着。

宽度用 `min(80vw, 304px)` 而不是固定值：小屏（320）占 80% 不至于遮死，
大屏不至于拉成一行十几个字的阅读跨度。

### 3.2 12 栏 → 2 列，统计卡 2×2

```css
.content{grid-template-columns:repeat(2,1fr);}
.content>*{grid-column:1/-1;}          /* 默认满宽 */
.content>.card.col-3,
.content>.card.col-4{grid-column:span 1;}   /* 统计卡两两并排 */
```

**`grid-column:1/-1` 这句是必须的，不是保险**。单列/两列网格里，一个
`grid-column:span 7` 的卡片会撑出 5 个**隐式列**，页面立刻横向溢出。
改之前我先量过：不加这句，`/tasks` 的 `scrollWidth` 是 743（视口 390）。

四张统计卡排 2×2 而不是一列一个：一列一个要滚四屏才看到正文。

### 3.3 表格：不折行、横着滑

这是本次最需要拿数据说话的地方。第一版只加了滚动容器，结果列被压平——
工单号 `W20261021-153052-02` 折成两截，"内容"列折成四行：

```css
/* 第一版（错的） */
.tw table{min-width:100%;}     /* 表格跟着容器宽，8 列硬塞进 368px */
```

改成让内容决定宽度、再给长文本列一个上限：

```css
.tw table{width:max-content;}
.tw th,.tw td{max-width:170px;}
```

短列（状态、时限）按内容收缩成一行，长文本列最多折两三行。实测
订单表从"每格折 3 行"变成"每行一行字"，代价是需要横滑。

横滑就得让人知道能滑。试过纯 CSS 的 scroll-shadow（`background-attachment`
叠层那一套），失败：表头自带 `background:#fafbfd`，把整层阴影盖掉了。
最后用内阴影——**画在容器内边缘、不随内容滚动**：

```css
.tw{box-shadow:inset -16px 0 14px -14px rgba(16,28,44,.35), ...}
```

它不是精确的滚动位置指示器（滑到头阴影还在），但"这边还有内容"这个信息
给到了，且不需要一行 JS。

### 3.4 触摸目标与 iOS 的两个坑

| 问题 | 现象 | 处理 |
|---|---|---|
| 按钮 32px 高 | 拇指点不中，误触相邻按钮 | `.btn{min-height:40px}` |
| 输入框 13px | **点一下整页放大且不还原** | 手机上 `input,.inp{font-size:16px}` |

第二条是 iOS Safari 的硬规则：`font-size < 16px` 的输入框获得焦点时自动
缩放页面。用户没缩放，是浏览器替他缩的，而且不会缩回去——填完表整页还是
放大的。这个只有真机才看得出来，桌面 DevTools 模拟不出来。

### 3.5 弹窗：底部抽屉化

```css
.modal.show{align-items:flex-end;padding:0;}   /* 贴底 */
.modal-box{max-width:100%!important;width:100%!important;border-radius:12px 12px 0 0;}
```

**这里有一个必须写 `.show` 而不是 `.modal` 的原因**：`.modal` 本身是
`display:none`（规则写在各页面的 `<style>` 里），而页面内 `<style>` 比
`style.css` **晚加载**、同优先级必胜。如果写 `.modal{display:flex}`，
结果是——所有页面的弹窗一进去就全部展开。用 `.modal.show`（特异性 0,2,0）
才压得住页面里那条 0,1,0。

`!important` 也是必需的：`.modal-box` 的 `max-width:640px` 写在页面 `<style>`
里，源顺序在后，外部 CSS 同优先级赢不了。

### 3.6 其余细节

- `viewport-fit=cover` + `env(safe-area-inset-*)`：刘海屏铺满，抽屉底部的
  模型状态灯不被 Home 条压住。
- `theme-color:#206bc4`：安卓 Chrome 的状态栏跟着主色走。
- `@media (hover:none)`：触屏上 `:hover` 会"粘住"，导航项点完一直是高亮底色。
- `@media (prefers-reduced-motion:reduce)`：关掉抽屉位移和状态灯呼吸。
- **没有禁掉缩放**（不写 `maximum-scale=1`）。禁缩放是拿无障碍换整齐，
  老花眼的社区阿姨会骂人。

## 4. 踩过的坑

### 4.1 行内样式压不动

原来 25 处统计卡和 3 处表单单是这么写的：

```html
<div class="card stat" style="grid-column:span 3">
<div style="display:grid;grid-template-columns:2fr 1fr 1fr">
```

行内样式的优先级高于任何外部选择器（`!important` 除外）。窄屏断点写得再好，
也管不到它们。所以做适配的第一件事其实是**清行内布局**——全部换成
`col-3` / `.fgrid-2` 这类类名，之后媒体查询才接管得到。

用 `!important` 硬压也能过，但等于把"为什么这里特殊"埋进 CSS 里，
下一个改的人还得再猜一次。

### 4.2 一条"看起来无害"的规则把审计表撑到 2601px

我一开始写了这么一条，本意是"让宽度由内容决定"：

```css
td[style*="max-width"]{max-width:none!important;white-space:normal!important;}
```

审计页两个摘要列原本限死 220/260px，这条一上，它们变成无限宽。
表格宽度从 939 **涨到 2601**（要滑 6 屏）。而且因为加了 `!important`，
它把我同时写的 `max-width:170px` 也一起干掉了。

教训：**关系型属性（width/max-width）用 `!important` 反着写，先问自己
"原来那个上限是谁加的、为什么"**。这里的上限是防长哈希撑破表格的，
不是历史包袱。

发现方式是量出来的——脚本里打印了每个表格的 `scrollWidth/clientWidth`。
如果不量，这个页面在桌面上完全正常，只有手机上难看，很容易漏。

### 4.3 桌面回归要用 A/B 证明，不能靠"我觉得"

包完 `<div class="tw">` 后看桌面截图，工单表的列显得比印象中窄。
怀疑是自己包的这层改变了布局。

做法：把 `.tw` 临时改成 `display:contents`（让表格回到裸状态），量一遍
列宽；再改回来量一遍。两次结果**逐列相同**（992px，8 列 117/96/156/83/87/75/188/190），
说明不是回归，是桌面本来就窄。

顺带发现一个既存问题：桌面 1280 下"内容（脱敏）"列只有 96px，
而"时限"占了 156px。这属于表格列宽策略，不在本次范围，先记下来。

### 4.4 测试断言自己会骗人

首轮 `smoke_mobile.py` 4 项失败，其中 3 项是**测试写错了**：

1. **断言读到了注释**。CSS 里写着
   `写 .modal{display:flex} 会把这层的弹窗全部默认打开`——这是反面教材，
   正则却把它当成正面事实报了错。修法：断言前先 `re.sub` 剥掉 `/* */`。
2. **压空白把选择器压坏了**。为了少写字，我把 CSS 的空白全删了，
   结果 `.nav-open .sidebar`（后代）变成 `.nav-open.sidebar`（同一元素），
   两种匹配完全不同。修法：只压规则体里的空白，选择器原样保留。
3. **断言太粗**。`grid-column:1/-1` 是"占满一行"，窄屏下本来就对，
   不该和 `span 7` 一起禁掉。

这类错误的共同点：**测试比被测代码更容易写出"看起来对"的假象**。
所以 4 项失败我先逐条核对真实现象（grep 原文、逐行看），再决定改代码还是改断言。

## 5. 验收

### 5.1 真机视口实测（playwright + chromium）

9 个视口 × 11 个页面，两件事：整页有没有横向溢出、断点行为对不对。

| 视口 | 结果 |
|---|---|
| 320×568（iPhone SE 1） | 通过 |
| 360×800（安卓常见） | 通过 |
| 390×844（iPhone 14） | 通过 |
| 430×932（iPhone 15PM） | 通过 |
| 844×390（手机横屏） | 通过 |
| 768×1024（iPad 竖） | 通过 |
| 912×1366（iPad Pro 竖） | 通过 |
| 1024×768（iPad 横屏） | 通过 |
| 1440×900（桌面） | 通过 |

断点断言：窄屏必须出现汉堡、侧栏必须收在屏外；宽屏必须没有汉堡、
侧栏宽度必须还是 230。

表格横滑量（390px 视口）：

| 页面 | scrollWidth / 可视宽 | 滑屏数 |
|---|---|---|
| 工单（8 列） | 1125 / 368 | 3.1 |
| 审计（6 列，摘要列文本长） | 939 / 368 | 2.6 |
| 台账 | 779 / 368 | 2.1 |
| 公告 | 786 / 344 | 2.3 |
| 用户 | 733 / 368 | 2.0 |
| 首页今日任务 | 368 / 368 | 不用滑 |

### 5.2 回归套件

`scripts/smoke_mobile.py`（**51 项**）钉住三类"改了模板就会退回去"的结构：

1. 侧栏没有抽屉形态（漏了正文永远是"屏宽 − 230"）；
2. 表格没被 `.tw` 包住（裸 table 会把 document 撑宽）；
3. 行内 `grid-column:span` / `grid-template-columns` 残留（外部 CSS 压不动）。

这些都是电脑上肉眼看不出来的，必须进回归。

另外 `scripts/_shot_mobile.js` / `_shot_breakpoints.js` 是**本地视觉验收**
用的（需要 playwright-core + chromium），不进回归套件——CI 环境不该依赖浏览器。

## 6. 遗留

- **表格仍要横滑**。8 列表格在 390px 上没有优雅解。彻底的方案是"卡片化"
  （每行变一张卡，标签+值竖排），但要改 12 张表的渲染逻辑，其中多张是
  JS 动态生成 tbody，风险大，收益主要在长尾页。当前横滑 + 阴影提示够用。
- **桌面表格的列宽本就偏挤**（见 4.3）。不是本次引入，但值得单独修：
  给内容列一个 `min-width`，让时限列让出空间。
- **没有做离线/PWA**。手机上弱网常见，"添加到主屏幕 + 缓存首屏"是下一步
  很自然的增强，但会牵扯到接口的 no-store 策略，需要单独设计。
- **触摸目标只到 40px**，苹果建议 44px。表内的小按钮（`padding:4px 12px`
  的"查看"“导出"）仍是 32px 上下——它们在表格里，加大会让列更宽，
  权衡后保留。
