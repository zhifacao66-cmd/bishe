# 部署形态与本地模型的关系

> 这份文档回答一个问题：**项目发布到公网之后，本地大模型部署还有没有用？**
> 结论先放这里：**有用，而且它是论文的主体；公网发布只是"可访问的补充演示"，两者不是替代关系。**

---

## 1. 为什么会产生"本地模型没用"的错觉

因为发布到云端时，云端机器上没有 GPU、没有 Ollama，`/api/health` 返回 `degraded`，
拆解降级成了关键词规则路径。看起来"模型这部分白做了"。

但这个判断混淆了两件事：

- **论文要证明的事**：在无 GPU 云、数据不出社区的约束下，本地 8B 模型能否胜任
  政务记录的拆解与派单。证据是 43 条拆解评测、5 配置消融、24 条端到端、16 并发压测、
  15 分钟长稳——**全部在本地跑出来的，且可复现**。
- **公网链接要干的事**：让导师不装环境、不连 VPN，直接看到系统长什么样、三个角色怎么流转。

前者是研究结论，后者是交付形态。发布不会让已完成的实验失效，
正如论文发表了不会让实验室的仪器作废。

---

## 2. 三种部署形态对照

| | 形态 A：本地全量（默认） | 形态 B：云端 + 远程模型 | 形态 C：纯云端（当前线上） |
|---|---|---|---|
| Web 应用 | 本机 Flask | 云端托管 Flask | 云端托管 Flask |
| 模型 | 本机 Ollama `qwen3:8b` | 本机 Ollama，经隧道暴露 | 无，规则降级 |
| 访问者 | 只有你（或同局域网） | 任何人（只要你的机器开机） | 任何人，7×24 |
| 拆解质量 | **97.7% / F1 99.0%** | 同 A（同一模型同一机器） | 规则路径，约 60%~70%，摘要为原文截取 |
| 延迟 | P50 2.14s | P50 2.14s + 隧道往返（+0.1~0.5s） | < 0.1s（不推理） |
| 依赖 | 本机开机 | **本机必须开机且联网** | 无 |
| 适用场景 | 论文实验、答辩现场演示、录屏 | 导师想亲手试模型效果 | 随时可查看的界面与流程样本 |

**关键点：形态 B 不是妥协，它就是"本地模型 + 公网访问"的正解。**
因为模型仍然跑在你自己的 4060 上，数据没有离开你的机器——这恰好是论文主张的
"数据不出社区"。云端那台机器只负责渲染页面和存业务数据。

## 3. 形态 B 怎么做（约 10 分钟，不需要服务器）

系统里模型地址本来就是配置项：

```python
# config.py
OLLAMA_BASE_URL = os.environ.get("OLLAMA_BASE_URL", "http://127.0.0.1:11434")
```

所以只要云端 Flask 能访问到 `http://<你的隧道地址>:11434`，模型就接上了。

### 3.1 让 Ollama 监听外部（默认只监听 127.0.0.1）

```bat
:: 临时生效，仅当前会话
set OLLAMA_HOST=0.0.0.0:11434
ollama serve
```

确认：`curl http://127.0.0.1:11434/api/tags` 能返回模型列表。

### 3.2 开隧道

推荐 `cloudflared`（免账号、免费、自带 HTTPS）：

```bat
:: 下载（GitHub 直连慢时加 gh-proxy 前缀）
curl -L -o cloudflared.exe https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-windows-amd64.exe

cloudflared.exe tunnel --url http://127.0.0.1:11434
```

它会打印一个 `https://xxx-yyy-zzz.trycloudflare.com` 地址，这就是模型的公网入口。

### 3.3 把地址填给线上应用

在托管环境里设环境变量（或改 `run.py` 里的默认值）：

```
OLLAMA_BASE_URL=https://xxx-yyy-zzz.trycloudflare.com
LLM_TIMEOUT=90
```

`LLM_TIMEOUT` 要放宽：隧道往返 + 冷启动首次加载模型可能到 15~20 秒，默认 60 秒在
长文本上会踩线。

### 3.4 ⚠️ 安全前提（这一步不能省）

Ollama 的 API **没有任何鉴权**。一旦暴露公网，任何人都能调用你的显卡，
也能读到 `/api/tags` 里的模型清单。因此：

1. **只在需要给导师看的那段时间开**，看完立刻 `Ctrl+C` 关隧道；
2. 隧道地址不要公开发在群里，只单独发给导师；
3. 不要把 `OLLAMA_HOST=0.0.0.0` 写成永久环境变量（`setx`），
   否则以后每次开机 Ollama 都对外监听；
4. 若要长期开，在 cloudflared 前面加一层 Cloudflare Access（邮箱验证码）或
   Nginx Basic Auth，不要裸奔。

### 3.5 已知限制

- **隧道地址每次重启都变**，需要重新填环境变量并重发布；
- 国内访问 `trycloudflare.com` 的稳定性一般，偶有超时，此时系统会自动降级到规则路径
  （这是设计好的行为，不会 500）；
- 你的电脑休眠 / 断网，导师那边就退回形态 C。

## 4. 为什么不建议"换个远程大模型 API"来救线上

有人会想：线上接个 DeepSeek / 通义千问的 API 不就有模型了吗？技术上 5 分钟能改完，
但**这会直接动摇论文命题**：

| 论文标题里的词 | 换成云 API 后 |
|---|---|
| 「本地大模型」 | 不成立，变成了云端调用 |
| 「数据不出社区」 | 不成立，原始记录要发给第三方 |
| 8GB 显存 / 量化 / 显存闸门 / 并发上限 1 | 全部失去意义，这几章实验无法解释 |
| 量化对精度的影响（第 5 章消融） | 无从谈起 |

答辩时若被问"你为什么不用 API，便宜又快"，正确回答不是"我没想到"，而是：
**"能用，但我研究的就是不能用的场景。"** 街道和社区的居民记录含身份证、住址、
健康状况，多数地区的政务数据管理办法不允许出内网；这正是本课题的存在理由。

如果确实要加一个云 API 作为对照组，正确做法是**把它做成消融实验里的一个配置**
（对比"云 API / 本地 8B / 本地 4B / 规则"），而不是替换主链路。这样反而加分。

## 5. 答辩口径（背这三句）

1. **"线上链接是交付形态，本地部署是实验环境。"**
   论文里所有数字——97.7% 拆解准确率、2.14 秒 P50、0.62 QPS 饱和点、15 分钟长稳——
   都来自本地 4060 上的实测，脚本在 `scripts/` 里，可一键复现。

2. **"线上没有 GPU，所以拆解走了规则降级路径，这是系统的容错设计，不是缺陷。"**
   `/api/health` 会如实报告 `degraded`，页面照常可用，只是摘要质量下降。
   一个会因为模型掉了就白屏的系统，在社区场景是不可接受的。

3. **"要让模型在线跑，不需要改代码，改一个环境变量就行。"**
   `OLLAMA_BASE_URL` 指向隧道地址即可，模型仍在我本机，数据不出内网。

## 6. 建议的演示组合

| 场合 | 用什么 | 为什么 |
|---|---|---|
| 给导师发链接（现在） | 形态 C | 她随时能点开，不受你电脑开关机影响 |
| 导师说"想看看模型的真实效果" | 临时切形态 B，约好时间 | 10 分钟能开好，看完就关 |
| 答辩现场 | 形态 A，本机跑 + 录屏兜底 | 不赌会场网络；录屏里有完整模型输出 |
| 论文附录 | 形态 A 的复现命令 | 评审可自行验证 |

**录屏是这套组合里性价比最高的一环**：一次录 3~5 分钟，
把"同一段口语记录 → 模型拆出两个业务项 → 自动派单 → 台账建档 → 月报"完整走一遍，
配上终端里的 `llm_used: true` 和耗时，比任何在线链接都更有说服力。

## 7. 发布到托管沙箱的三个坑（形态 C 实操记录）

发布脚本是 `scripts/_sync_publish.py`，把代码与数据同步到 `F:\bise4-publish`
（精简副本，约 0.5 MB，不带 thesis / docs / 评测产物），再对该目录执行发布。
下面三条都是实际踩过的，与"模型能不能用"无关，纯工程问题。

### 7.1 依赖清单里出现数据库驱动名 → 直接被拒

沙箱在**上传前**扫描 `requirements.txt`，见到 `pymysql` 就判定"依赖外部 MySQL"
并拒绝部署——**即使那一行是注释**。本项目运行时其实只用 SQLite，
所以发布副本单独写一份只含 `Flask / Flask-SQLAlchemy / requests` 的干净清单，
本地原文件里的说明性注释保持不变。同步脚本负责生成，不需要手工维护两份。

### 7.2 沙箱按 `main.py` 找入口 → 启动失败

沙箱探测 Python 项目入口时优先找 `main.py`，找不到就直接跑
`python main.py`，于是报 `can't open file '/workspace/main.py'`、60 秒后判启动失败。
本项目真正的入口是 `run.py`。解决办法是在发布副本里生成一层薄壳 `main.py`：

```python
from app.extensions import db
from run import app

if __name__ == "__main__":
    with app.app_context():
        db.create_all()
    app.run(host="0.0.0.0", port=int(os.environ.get("PORT") or "3000"), threaded=True)
```

启动命令同时显式声明为 `python main.py`，端口 3000。**壳不要写业务逻辑**，
只做转发，避免和 `run.py` 出现两套配置。

### 7.3 沙箱里的 data 目录是持久卷 → 重新发布不会覆盖数据库

这一点最反直觉：改代码重新发布，`app/` 会更新，但 `data/community.db`
会保留沙箱上一次运行的内容。所以

- 本地改演示数据（`seed_demo.py --reset`）后再发布，**线上数据不会跟着变**；
- 在线上做过的提交（比如试填一条居民报修）会一直留着，且没有删除接口
  （工单按审计要求不可删）。

要彻底重置线上数据，只能在沙箱侧换一个库文件（或先下线再重新创建应用）。
做演示前应当先想清楚：线上数据是"一次性摆好"的，试操作要挑不会污染观感的动作。

### 7.4 发布后的验收清单

```bash
B="https://community-agent.app.workbuddy.host"; SC="sharecode=<你的码>"
curl -s -c /tmp/ck -o /dev/null "$B/?$SC"      # 先取访问 cookie
for p in /portal /portal/report /portal/notices /portal/contacts /login; do
  echo "$(curl -s -b /tmp/ck -o /dev/null -w '%{http_code}' "$B$p?$SC")  $p"
done
curl -s -b /tmp/ck "$B/api/health?$SC"          # status 应为 degraded（线上无模型）
```

六个页面全 200、`/api/health` 返回 `degraded` 且 `llm.available=false`，即为正常态。
`degraded` 不是故障：它表示数据库正常、模型不可用、系统走规则兜底，
这正是形态 C 的预期表现。
