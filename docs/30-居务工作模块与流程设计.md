# 30 · 居务工作模块与流程设计

> 前面 `docs/01` 把系统定位成「FDE 录入 + 拆解 + 分派」，那只是社区工作里**填表**这一小块。
> 真正占时间的是**居务运转本身**：收文要签、要办、要报；发文件要核稿、要编号、要盖章；
> 上级要周报，平级要函，下级要派工；开一次居务会要通知、签到、记录、纪要、督办、公开。
> 本文把这些活拆成六个模块，给出流程与数据模型，并说明哪些现在能直接做、哪些要新建表。
>
> 依据：民政部公开的村（社区）履职事项规范（江苏"一套表、两本账、三张清单"）、
> 中山市社区工作事项准入目录、北京海淀区公开的居委会职责，以及《党政机关公文处理工作条例》
> （中办发〔2012〕14 号）与 GB/T 9704—2012《党政机关公文格式》。

---

## 1. 居委会到底干哪几摊事

三类法定职责（《城市居民委员会组织法》口径），加两类实际承担但不在法定职责里的事：

| 类别 | 具体内容 | 谁交办的 |
|---|---|---|
| **一、依法组织自治** | 召集居民（代表）会议、办理公共事务与公益事业、便民服务、群防群治、矛盾调解、共驻共建、**居务公开**、收集诉求向上反映 | 居民、居民会议 |
| **二、依法协助政府** | 社会治安、社区矫正、流动人口、医疗保健、社区环境、人口计生、优抚救济、防灾减灾、社区教育、劳动就业、社会保障、社会救助、住房保障、文体、老年人/残疾人/未成年人/妇女权益 | 街道、区直部门 |
| **三、依法监督评议** | 组织居民评议街道和驻区单位、监督供水供电供气电信环卫绿化等市政服务、指导监督业委会与物业 | 居民、街道 |
| **四、党建** | 组织生活、党员管理、党建引领基层治理、双报到 | 街道党工委 |
| **五、准入外的摊派** | 各类检查、创建、评比、报表、挂牌、证明 | 各部门（应经准入审批） |

江苏的做法是把上面这一大堆压缩成 **"一套表 + 两本账 + 三张清单"**：
统计数据一套表、党建与民生两本综合台账、主体责任/协助准入/负面事项三张清单。
这正是系统该有的骨架——**不是给每件事做一个功能，而是按"账"归口**。

中山的公开数据能说明量级：一个社区平均常住 1.5 万人、工作人员约 15 人，
承担近 100 项业务、40 余项考核、40 份定期报表；准入制度落地后报表减到 29 份。
（引自民政部网站，是当地的数，不是本项目的数。）

## 2. 六个模块

| 模块 | 干什么 | 频次 | 现状 |
|---|---|---|---|
| **M1 公文流转** | 收文签办、发文拟制、平行函、密级与格式、编号用印、归档 | 每天 | 只有收文（`Notice`），**无发文、无密级、无文种区分** |
| **M2 会议与议事** | 居务会、两委联席会、居民（代表）会议、议事协商、决议督办 | 每周~每月 | **完全没有** |
| **M3 台账与报表** | 一套表、党建账、民生账、月报、**周报**、迎检材料包 | 周/月/季 | 有月报（数字型 Excel），**无周报、无两本账归口** |
| **M4 任务与督办** | 街道交办、社区派工、网格员/物业承办、超时告警 | 每天 | 有（`Task` + `WorkOrder` + 督办 Agent） |
| **M5 居务公开与告知** | 公开栏、居民端公告、政策宣传、诉求收集 | 每周 | 有公告与居民端（只读） |
| **M6 材料与证明** | 出具证明、上报材料、盖章登记 | 每天 | 无（减证后仍需少量） |

M1 + M4 合起来就是用户说的"上级 / 平级 / 下级沟通"：
**上行**（请示、报告、周报）、**平行**（函：物业、辖区单位、兄弟社区）、**下行**（通知、任务、派工）。

## 3. 三条沟通流向与文种

| 流向 | 对象 | 文种 | 系统落点 |
|---|---|---|---|
| **上行** | 街道、区直部门 | 请示、报告、情况说明、**周报/月报** | `Notice.direction=out` + `doc_type` |
| **平行** | 物业公司、辖区单位、兄弟社区 | 函、告知书、协办单 | 同上，`to_org` 为主送 |
| **下行** | 网格员、物业、居民 | 通知、公告、任务单、派工单 | 现有 `Notice(kind=local/original)` + `Task` |

真实约束：**上行文必须"一文一事"、"不得越级"、"请示不得抄送下级"**；
平行文用"函"，不能用"通知"（通知是下行文种）。这些是公文常识，系统里最好用枚举约束住，
而不是让用户随便选——选错了打印出来就是硬伤。

## 4. 密级：社区没有定密权，只能"标"和"继承"

这一条必须写清楚，否则做出来的功能是错的：

- 法定密级只有三级：**绝密、机密、秘密**（《保守国家秘密法》），且**只有依法定密的机关才能定密**。
  社区居委会不是定密机关，它对上级来文只能**继承密级**，对自己产生的材料只能标**"内部"或"公开"**。
- 所以系统里的字段应叫 `secret_level`（密级标识），取值：
  `公开 / 内部 / 内部·敏感 / 秘密（继承） / 机密（继承）`。
- **"内部·敏感"是本项目要自己定义的一档**：不是国家秘密，但含居民个人信息
  （身份证、手机号、健康状况、低保/残疾身份），依据《个人信息保护法》限制分发范围。
  这一档和已有的 `FieldSecurity`（明/脱/密）是两套东西：
  - `FieldSecurity` 管**字段**（这条业务项的哪个字段要脱敏）
  - `secret_level` 管**整份文件**（这份文件能给谁看）
- 分发规则：`scope` 已有 all/community/property，再加一条硬约束——
  `secret_level != 公开` 的文件不得出现在居民端（`/portal/notices`），且导出要留痕。

另外两个常被忽略的标注：**紧急程度**（平件/急件/特急）和**保密期限**（如"秘密★5 年"）。
社区实际用得最多的是紧急程度，因为它决定 SLA。

## 5. 公文格式要素（生成 docx 时按这个排）

GB/T 9704—2012 的 18 个要素，社区场景实际用 12 个：

| 要素 | 位置 | 现有 `Notice` 字段 |
|---|---|---|
| 份号、密级和保密期限、紧急程度 | 版心左上角，自上而下三行 | **无** |
| 发文机关标志（红头） | 版心上部 | `issuer`（有，但导出时是文字不是红头图） |
| 发文字号 | 红头上方居中 | `doc_no` |
| 签发人 | 上行文必须有，与发文字号同行右侧 | **无** |
| 标题 | 红头下 | `title` |
| 主送机关 | 标题下顶格 | **无**（只有 `scope` 范围，不是具体机关） |
| 正文 | — | `body_md` |
| 附件说明 | 正文下 | **无** |
| 发文机关署名、成文日期、印章 | 正文右下 | `issuer` + `issued_at`，**无印章** |
| 附注（如"此件公开发布"） | 成文日期左下 | **无** |
| 抄送机关、印发机关和印发日期 | 版记 | **无** |

现在的 `render.py` 只做 Markdown → HTML，`export.py` 只导出报表 Excel；
公文 docx 导出走的是 `notice/export.py`（红头是靠文字模拟）。
要真做"生成格式"，最小可行是补齐**密级、紧急程度、签发人、主送、抄送、附件、附注**七项，
模板固定 A4、仿宋 GB2312 三号、行距 28 磅——这几项定了，打印出来就像公文了。

## 6. 四条流程

### 6.1 收文（上级来文）

```
来文（纸质/PDF/docx/微信群截图）
  → ① 登记：扫描/上传 → 解析出标题、文号、发文机关、成文日期、密级
  → ② 拟办：办公室（社区书记/主任）批"谁办、几天办完"
  → ③ 签收：承办人签收（现有 recv_status: dispatched → received）
  → ④ 承办：关联任务/工单/台账，边办边留痕
  → ⑤ 办结：填办理结果 + 佐证材料
  → ⑥ 归档：按年度-文号归档，进"一套表"统计
```

现状：①②③有，④半有（能关联任务但没强绑定），⑤⑥没有。
**缺的关键是"办理结果"和"超期判定"**：`deadline` 字段有了，但没有"到期未办结"的告警口径。

### 6.2 发文（上行文/平行文）

```
  → ① 拟稿：选文种（请示/报告/函）→ 填主送、事由、正文
  → ② 核稿：查四件事——文种对不对、一文一事、密级标没标、格式齐不齐
  → ③ 签发：书记/主任签，记签发人与日期
  → ④ 编号：按 年份+机关代字+序号 自动生成（幸街社〔2026〕12 号）
  → ⑤ 用印：盖章登记（谁盖的、什么时候、盖在哪个件上）
  → ⑥ 分发：主送 + 抄送，记录送达方式（系统内/纸质/微信）
  → ⑦ 归档
```

现状：**全缺**。这块是"上级沟通"最刚性的部分——请示要等批复，报告不用等，
函要回执，这三者的流转状态机不一样，不能做成一个"发送"按钮。

### 6.3 居务会（会议与议事）

```
  → ① 议题征集：两委成员/网格员/居民提，进议题池
  → ② 定会：定时间、地点、参会范围、列席
  → ③ 通知：提前 N 天发（居民代表会议要提前更久），记谁收到
  → ④ 签到：到会人数是否过半（涉及表决的必须有这条）
  → ⑤ 记录：发言要点 + 形成的决议（谁负责、什么时候完成）
  → ⑥ 纪要：生成纪要 → 签发 → 分发 → 归档
  → ⑦ 督办：决议转成 `Task`，到期未完成进督办看板
  → ⑧ 公开：应公开的决议进居务公开栏
```

这块现在完全空白，但它**天然适合自动化**：议题池 → 议程 → 纪要草稿（LLM 从记录里提炼）
→ 决议自动转任务。而且和现有的 `Task`、`supervise` 能直接接上。

### 6.4 周报（自动生成）

```
  → ① 取数：本周 FDE 条数、业务项数、工单（派/接/结/超时）、台账新增、
            收文（收/办/逾期）、发文数、会议场次、任务（下/完/逾期）、居民诉求
  → ② 成稿：模板骨架 + 服务端 count 填数 + LLM 润色"本周重点/存在问题/下周计划"三段
  → ③ 人工改：书记改措辞（LLM 只是初稿，改完才算数）
  → ④ 签发：算一份正式上行文，进 6.2 的编号/用印流程
  → ⑤ 快照：发布后冻结，改要出修订版（复用 `ReportRevision` 的模式）
```

**周报该不该自动出？该，但只自动到"初稿"。** 理由：
- 数字部分必须自动——这正是"减负"最直观的地方，手工抄 12 个统计项最容易错；
- 文字部分不能全自动——"存在问题""下周计划"是书记的判断，模型写出来一眼假；
- 必须留"人工改过"的痕迹，否则上级问一句"这条谁写的"就答不上来。

数字口径有一条硬规矩要沿用：**服务端 count，且与明细同源**（`docs/14` 已踩过坑），
周报里的"本周办结 12 件"点开必须正好是那 12 件，不能一个是 `len(rows)` 一个是 `count()`。

## 7. 数据模型改动

### 7.1 `notice` 扩字段（不新建表，改动最小）

| 字段 | 类型 | 说明 |
|---|---|---|
| `direction` | String(8) | in 收文 / out 发文 / inner 内部 |
| `doc_type` | String(16) | 通知/请示/报告/函/纪要/通报/决定/公告 |
| `secret_level` | String(16) | 公开/内部/内部·敏感/秘密/机密 |
| `secret_until` | Date | 保密期限 |
| `urgency` | String(8) | 平件/急件/特急 |
| `to_org` | String(128) | 主送机关（多个逗号分隔） |
| `cc_org` | String(128) | 抄送机关 |
| `signer` | String(32) | 签发人（上行文必填） |
| `handler` / `handled_at` / `handle_result` | — | 承办人与办理结果 |
| `attachments` | Text | 附件清单（JSON） |
| `seal_by` / `sealed_at` | — | 用印登记 |
| `archived_at` | DateTime | 归档时间 |

### 7.2 新表

```
meeting      会议：id, kind(居务会/两委会/居民代表会/议事协商), title, held_at,
             place, host, attendees_json, quorum_ok, minutes_md, status(筹备/通知/已开/纪要/归档)
meeting_item 议题/决议：id, meeting_id, seq, subject, decision, owner, due_at, task_id
weekly       周报：id, period(2026-W43), data_json(快照), body_md, editor, signed_at, revision
doc_log      公文流转日志：doc_id, action(拟稿/核稿/签发/用印/分发/归档), actor, at, note
```

`doc_log` 按事件追加、不改历史，和 `work_order_log` 一个模式——
这也是本项目已经在做的：**状态变更只能走一个入口，顺带写日志**（`orderflow.push()` 的教训）。

## 8. 分期

| 期 | 内容 | 依赖 | 答辩价值 |
|---|---|---|---|
| **P0** | `notice` 扩字段 + 发文流程 + 密级/紧急度 + 周报自动生成 | 现有表够，只需扩列 | 最高：直接补上"上级沟通"和"周报"两个被问的点 |
| **P1** | 会议模块 + 纪要生成 + 决议转任务 | 新表 meeting/meeting_item | 高：居务会是最"居委会"的功能 |
| **P2** | 一套表归口 + 迎检材料包 + 证明出具登记 | 依赖台账分类重构 | 中：锦上添花 |

不建议一上来做 P2：**台账归类是深水区**，现有 `ledger.line` 只有综治/民政/卫健，
真要按"党建账/民生账"重组，会牵动统计口径、报表导出、权限过滤一大片。

## 9. 与现有系统的接口

- 密级过滤：`app/notice/ingest.py:staff_query()` / `can_view()` 是公告口径的唯一入口
  （`docs/26` 红线 15），加密级必须从这里加，不能在各个列表页各写一遍。
- 会议决议转任务：直接建 `Task`（`assignee_role` 用白名单，不能写"除街道外都收窄"，
  踩过：admin 被筛掉导致待签恒 0，`docs/26` 红线 1）。
- 周报数字：复用 `app/agents/report.py` 的取数函数，但周期改成"本周一~今天"，
  且必须和 `docs/14` 的口径表对齐（一条事项可派多线，合计 ≥ 事项数）。
- 公文导出：`app/notice/export.py` 现在导的是红头文本，补七项要素时注意
  **导出件只读 `data_json` 快照**（`docs/15` 教训：报表数字不能每次打开都变）。

## 10. P0 实现记录（2026-10-26）

P0 已落地：`notice` 扩字段 + 发文状态机 + 周报自动生成。以下是实现口径，改之前先读这一节。

### 10.1 落地清单

| 内容 | 位置 |
|---|---|
| 公文属性（18 列） | `app/models.py:Notice`；老库由 `app/auth.py:_migrate_notice_table` 幂等补列 |
| 流转记录表 `doc_log` | 与 `work_order_log` 同构，只追加 |
| 周报表 `weekly` | `body_md` 给人看，`data_json` 给机器核 |
| 发文状态机 | `app/docflow.py`：`ACTIONS` / `ALLOWED_FROM` / `push()` |
| 文号生成 | `docflow.make_doc_no()`（用印时取号，`doc_seq` 落库） |
| 周报取数与成稿 | `app/weekly.py`：`collect()` / `render()` / `polish()` |
| 接口 | `app/api/docs.py`（7 个）、`app/api/weekly.py`（6 个） |
| 页面 | `/docs`、`/docs/<id>`、`/weekly`、`/weekly/<id>` |
| 权限点 | `doc.view` / `doc.manage` / `weekly.view` / `weekly.manage`（共 22 个功能点） |
| 演示数据 | `scripts/seed_docs.py`（3 份公文 + 1 份已签发周报，幂等可续跑） |
| 回归 | `scripts/smoke_docs.py`，66 项 |

### 10.2 状态机

```
draft ─check→ checked ─sign→ signed ─seal→ sealed ─send→ sent ─archive→ archived
  │              │                                              │
  └──sign（函可不核稿）──┘                                      └─reject→ draft
```

前置校验（`docflow.check_ready`）：签发必须有签发人、上行文必须有主送；用印必须有文号与密级；分发必须有主送。
非法迁移抛 `ValueError`，API 转 409。

### 10.3 三条不能改的口径

1. **公告与公文共用表，但公告口径必须排掉 `direction='out'`**（`app/notice/ingest.py:_exclude_docs`）。
2. **周报数字与明细同源**：`collect()` 一次查询产出 `counts` + `items`，正文数字由同一份 payload 渲染。
3. **社区无定密权**：`doc_type` 中的"秘密/机密"只允许继承，社区建文标这两档直接 400。

### 10.4 验收

- `smoke_docs` 66 项全绿：状态机 22 项、编号 2 项、密级与角色 6 项、周报 15 项、页面与隔离 21 项
- 全量 29 套回归逐套单跑全绿（原 28 套 + 新增 1 套）
- 演示库实测：3 份公文（已用印 / 已归档 / 已分发）+ 1 份已签发周报；公文不出现在公告列表，也不进"待签收"

### 10.5 下一步（P1）

会议与议事：新建 `meeting` / `meeting_item`，议题池 → 通知 → 签到（表决类校验过半）→ 记录 → 纪要 → 决议转 `Task` 督办 → 应公开的决议进居务公开。这块能直接接上现有的 `Task` 与 `supervise`。
