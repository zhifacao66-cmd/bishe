> **当前状态（2026-11-03 起）：演示库是 300 条合成数据。**
> 由 `scripts/gen_demo_persons.py` 生成，社区归属／地址精度／权重分布三项
> 与真实台账同构，但**没有一条真人**。真实台账原件已移出项目目录到
> `F:\bise4-archive\ledger-originals\`。撤换原因见 §10。
>
> 下文正文里的数字（2842 人、41.3% 到门号、1855 人无社区）都是**真实台账
> 导入后实测的**。保留它们是因为：这些数字说明了"真实台账到底脏在哪"——
> 重复登记、地址残缺、社区归属缺失，正是接入方案要解决的问题。换成合成
> 数据就看不见这些了，所以按"历史实测值 + 现状说明"两层来写。

## 0. 一句话说清这套东西

街道下发的三类台账（残疾、防溺水、留守）是**人**，不是**事**。系统原先把
所有东西都当"要办的事"（`WorkItem`），人一进来就会把工单列表冲垮。所以单独
建 `Person` 表接管底册，让它在两处产生价值：**网格员按楼栋查人**、
**报修时自动认出"这户有重点人员"并提级**。

## 1. 四张表的真实情况

| 表 | 物理行 | 其中数据行 | 列 | 性质 |
|---|---|---|---|---|
| 矛盾纠纷排查登记表 | 26 | **0** | 15（表头第 2 行） | 空表头模板 |
| 留守儿童台账 | 151 | **0** | 14（表头第 3 行，上方两行合并大标题） | 空表头模板 |
| 残疾人台账 | 598 | **559** | 17（表头第 2 行） | 真实数据 |
| 防溺水台账 | 2921 | **2466** | 21（表头第 2 行） | 真实数据 |

**两张空模板不是无用数据**：它们是街道每月要收的报表格式。系统按它生成导出，
社区填完报上去。这比"只做导入"更贴近真实工作——社区真正的高频动作是**往上报**，
不是往系统里录。

### 1.1 两个有数据的表，打开看不到数据

这是真踩过的坑：拿到文件后双击打开，`disabled.xlsx` 只有 20 行可见（还全是空行），
`drowning.xlsx` 只有 455 行可见（还是空行），一度以为社区发来的是空表。

实际是**行被隐藏了**，而且文件里留着筛选条件：

| 文件 | 隐藏行数 | 文件里留存的筛选条件 | 结果 |
|---|---|---|---|
| `disabled.xlsx` | **578 / 598** | 「社区区划」= 住武社区 | 连住武社区自己的 381 行也藏了 |
| `drowning.xlsx` | **2466 / 2921** | 「包保看护责任人」= 某位包保责任人 | 2466 条数据行**一条不剩**全藏 |

那一列存的是**包保责任人姓名**（这里不写具体是谁）——大概是这样：某人打开全员台账，把筛选设在
"我负责的这些人"看了一下，然后直接保存、发出去了，筛选状态跟着文件走。

**对导入没有影响**：`openpyxl` 读单元格不看行的 hidden 标记，559 和 2466 照样读全。
但对人是灾难——打开是一张空表，而且"表里有数据"这件事完全看不出来。

> 所以核查数据量时**不能只看"打开能不能看见"**。要点：
> `ws.max_row`（物理行）vs 隐藏行数 vs 有内容的行数，三个数分开数。
> 本例中 `drowning.xlsx` 的隐藏行数 2466 恰好等于数据行数 2466，是巧合也是线索。

两张有数据的表，原始数据行合计 3025，去重后 **2842 人**（详见 §4）。
**这是真实台账导入后的实测值**；现演示库为 300 条合成数据，见 §10。

## 2. 为什么必须新建模型，不能塞进 WorkItem

系统原有的 `WorkItem`（业务项）是"**一件要办的事**"：有 `open→doing→done` 流转、
有 SLA、会进看板、会算超时。而这 2842 人是"**人**"：一人一条，按年更新，
没有"办完"这个动作。

硬塞进去的后果是可量化的：

- 工单列表从 41 条涨到 2885 条，演示时翻不到真实工单
- 这 2842 条永远停在 `open`，超时告警会被打爆
- "本周办结 N 件"这类指标会被永久污染

所以新建 `Person`（人员）+ `PersonTag`（标签，一人多标签）：

```
Person      id_hash / name_masked / id_masked / gender / age
            street / community / grp / address / addr_level / addr_mid / addr_room
            risk_level / guardian_masked / guardian_phone / source / batch
PersonTag   person_id / kind（残疾·防溺水·留守）/ detail（肢体|三级）/ risk_weight
```

`risk_weight` 是提级计算的**唯一依据**（1=需关注 2=重点关注 3=重点看护）。
不在调用处再写一遍阈值——两处各写一遍必然漂，这个教训项目里已经有过三次。

## 3. 脱敏：原始身份证不落库

原表有 3000+ 条真实身份证号、真实姓名、真实手机号。这是**在册居民的真实个人信息**，
一旦明文入库，备份文件、导出件、审计日志、答辩投屏全都是泄露面。

入库时统一处理：

| 字段 | 存什么 | 示例 |
|---|---|---|
| 身份证 | 只存 `sha256` 前 32 位（去重键）+ 前 6 后 4 掩码 | `520201********2599` |
| 姓名 | 保留姓 + 星号 | `张*` |
| 监护人姓名 | 同上 | `王*` |
| 电话 | 保留头尾 + 4 星 | `138****8000` |

原始 xlsx **不放项目里**（已移到 `F:\bise4-archive\ledger-originals\`，项目外，
打包不会带走）；`data/incoming/real_ledgers/` 仍在 `.gitignore` 里兜一道。
需要重跑真实台账时用 `LEDGER_SRC` 指到原件目录。

> `smoke_person.py` 的 [A] 组有硬断言：库内 `id_masked` 必须全部带 `*`、
> 姓名必须全部带 `*`、电话必须全部带 `****`。**任何一条明文残留都会让测试变红。**

## 4. 去重：只能靠身份证，且原表确实有重复

**以下为真实台账导入时的实测值**（演示库是 300 条合成数据，见 §10）：

| 现象 | 数量 |
|---|---|
| 防溺水表**内部**同一身份证重复出现 | 164 个身份证 / 多出 166 行 |
| 残疾人表与防溺水表**跨表**重叠（既残疾又是未成年人） | 15 人 |
| 无有效身份证被跳过 | 2 条 |
| 去重后 | **2842 人** |

**为什么不能按姓名合并**：同一社区同名同姓并不罕见，按姓名去重会把人并错，
而且并错之后没有任何报错——两个人的标签、地址会混成一条，看起来完全正常。

去重键用 `sha256(身份证)` 前 32 位，`Person.id_hash` 上加唯一索引，
重复导入时自动识别为"补充标签"而不是"新增人"（[E] 组验证幂等）。

## 5. 地址：能识别到哪一级就记到哪一级

这是整套功能最重要的一条诚实性约束。

| 地址形态 | 条数 | `addr_level` |
|---|---|---|
| `××社区×栋×单元×××室` | 1174（41.3%） | 3 栋+单元+门号 |
| `安置房4-2-15-2`、`3期廉租房3-3-4` | 80 | 2 栋+单元 |
| `住武社区陈家寨组`、`李家寨组` | 808 | 1 仅到楼栋/组 |
| `贵州省六盘水市水城区` | 780 | 0 无法定位 |

只有 **41.3%** 能精确到户。页面必须如实显示定位精度——
否则看到"住武社区"会以为能直接上门，实际那 808 条只知道在哪个组。

导入时做了两件规范化，把门号级比例从 35.6% 拉到 41.3%：

1. **中文数字**：台帐里"20栋**一**单元403室"和"20栋**1**单元403室"混着写，
   不归一化就有 8 条解析不出门号
2. **横杠格式**：`安置房4-2-15-2` 这类安置房/廉租房写法，原正则完全认不出

**不猜**：地址里出现"以朵安置房"不等于属于"以朵社区"——那是小区名，
归谁管要看街道划定。所以 `community` 只在地址里**明确写了社区名**时才给值。

## 6. 社区归属：1855 人无法归社区（真实台账实测），这是真实状态

按地址归社区的结果：

| 归属 | 人数 |
|---|---|
| （未明确） | **1855** |
| 住武社区 | 809 |
| 滴水岩村 | 126 |
| 以朵社区 | 52 |

**防溺水表 53.7% 只写到"水城区"**——因为它是街道下发的**全街道未成年人全员覆盖台账**，
本来就不按社区切分。这不是数据质量问题，是台账的性质。

系统据此定了口径：

- 底册**存全街道**（真实台账 2842 人；合成数据 300 人）
- 社区角色通过 ABAC 只看到本社区（住武社区账号看到 **809 人**）
- `community` 为空的 1855 人**只有街道能看到**——社区拿着一份"不知道是不是自己辖区"
  的名单去上门，是错误的

### 系统社区名与真实社区的映射

系统里的组织是虚构的「幸福里社区」，台账来自「以朵街道 · 住武社区」。两者名字对不上。

不改系统名的原因：`幸福里` 出现在 20 多个源文件、31 个回归脚本、8 张表里，
改名要把整套测试和演示数据一起搬，改动面远大于收益，且一次漏改就是
"页面显示幸福里、数据来自以朵"的半吊子状态——比现在更糟。

处理方式：在 `app/personbook.py:ORG_ALIAS` 里**显式登记映射**，并让它成为唯一出口：

```python
ORG_ALIAS = {
    "幸福里社区": "住武社区",
    "幸福里街道办事处": "以朵街道",
    "幸福里物业": "住武社区",
}
```

所有"当前账号属于哪个社区"的判断都走 `visible_communities()`。以后真要改名，只改这张表。

## 7. 派单联动：底册唯一真正产生价值的地方

只做"能查"的底册，答辩时说不出为什么要它。所以接进了风险复核 Agent
（`app/agents/riskreview.py` 第 ④ 条规则）：

```
302 室报修漏水
  → addr_parts 认出「3栋2单元+302」
  → 底册匹配到该户人员 → 取最高 risk_weight
  → weight 3（一级残疾/高风险/事实无人抚养）→ 直接「紧急」4h
  → weight 2（二级残疾/中风险）      → 升一档（一般 72h → 较急 24h）
  → weight 1（三四级残疾/低风险）    → 不表态
```

**为什么权重 1 不提级**：底册 2842 人里权重 1 占 2490 人，全都提级等于没提。

**为什么只认门号级**：模糊到"栋"会把整栋楼几十户都算成"这户有重点人员"。

**结论里不写姓名**：复核依据会进协作轨迹、会被导出。写
「2栋2单元202 在底册上有 1 名重点人员（残疾）」足够派单用，写姓名是多余泄露。
（[D] 组有断言：结论文本里不能出现当事人姓氏。）

**底册查不到不影响派单**：整条规则包在 try 里，底册没导入、表不存在、
以后结构改了，都只让这条规则失效，不让工单建不出来。

## 8. 真实数据暴露的三个坑（都已修）

1. **电话掩码格式不统一**：原表有 5 条短号（不足 11 位），早期分支只给 3 个星号，
   于是"库里还有明文电话"的检查一直红着——实际是掩码规则不统一。
   改成任何非空电话都"保留头尾 + 4 星"。
2. **`fail(msg, 400)` 不会返回 400**：`fail` 的第二个参数是**业务码**不是 HTTP 状态码，
   只写 `fail(...)` 会被 Flask 用 200 发出去。必须 `return fail(...), 400`。
   这个错被自己的测试抓出来了（[C] 组）。
3. **`--purge` 的删除顺序**：先删 `person` 再删 `person_tag` 会
   `FOREIGN KEY constraint failed`。子表先删。

## 9. 页面第一版为什么"点了没用"

第一版上线后反馈是"面板没设计好，点了没用"。查下来三个成因，**都不是"样式没调好"**：

**① 顶层块不写 `col-*`，会被 12 栏网格压成 73px**

`.content{display:grid;grid-template-columns:repeat(12,1fr)}` 是全站约定：直接子元素
必须自带 `col-12` / `col-4` 这类跨列类，否则只占**一栏**。第一版把说明条、KPI 行、
表格卡三个块直接丢进去，实测每块宽 **73px** —— 说明条成了竖排单字，表格的横向
滚动容器只剩 **35px**，按钮被挤到看不见的位置，表现就是"点了没反应"。

> 实测证据：修复前 `.content` 的 `grid-template-columns` 是
> `73.26px 150px 73.26px …`，修复后 KPI 卡 373px×6、列表卡 1154px。

**规矩**：`.content` 的直接子元素一律带 `col-*`；卡片内部的子块再自由布局。

**② 表格类名撞了全局的标签页按钮**

全站已有 `.ptab` 表示"页面内的标签按钮"（`risk.html` 的风险榜/反复投诉…）。
第一版把人员表写成 `table.ptab`，两套样式互相污染。其实全站的 `table / th / td /
tr:hover` 已有全局样式，**表格根本不需要起类名**，外面套 `.tw` 就够。

**③ 页面自己判"要不要提级"，与派单规则说的相反**（最严重）

第一版在反查结果后面写死"→ 该户报修应提级处理"。实测某个门号级地址命中两人，
权重都是 1（三级/四级残疾）——派单规则**根本不提级**。页面说会提级、工单停在 72h，
这种"说的和做的相反"比不显示更糟。

改法是把判据收到一处：

| 位置 | 职责 |
|---|---|
| `app/personbook.py:LIFT_MIN_WEIGHT=2 / URGENT_WEIGHT=3` | 阈值**唯一定义处** |
| `personbook.lift_note()` | 把命中结果算成一句结论（miss / flat / lift / urgent） |
| `GET /api/persons/match` | 返回 `verdict`，前端只显示 |
| `app/agents/riskreview.py` 第 ④ 条 | 读同一对常量决定 SLA |

`smoke_person` 加了三档断言（权重 1 → `flat`、权重 3 → `urgent`、未命中 → `miss`），
以及"阈值只有一处"的断言——这个 bug 就是靠测试守住的，不是靠看。

**顺带改的四处**

- **KPI 卡片点得动了**：重点看护 → `weight>=3`、可匹配到户 → `precision=3`、
  未明确社区 → `community=__none__`。空串在这个接口里表示"不筛选"，
  两者必须分开，否则点了卡片等于没点。
- **社区下拉按 `stats.by_community` 生成**，不再写死三个社区名——街道下次多下发
  一个社区，写死的下拉会让那批人"列表里有、下拉里选不到"。
- **页码与筛选进网址**（`replaceState`）：刷新、分享都还在原处，翻页不污染历史。
- **导出改成 `<a href>`**：附件下载交给浏览器，点了一定有反应，不会出现"点了没动静"。

## 10. 从真实数据撤回到合成数据

### 10.1 为什么撤：脱敏只做了一半

库里一条记录原本长这样：

```
id_masked    520201********2599     ← 前 6 位地区码 + 后 4 位顺序码（示意值）
name_masked  张*                     ← 留姓
age          32
risk_level   三级                    ← 残疾等级
address      ××社区×栋×单元×××室     ← 完整门牌（示例已打码）
```

身份证中间 8 位生日遮住了，看起来"脱敏了"。**但地址是完整门牌。**

社区网格员看到"完整门牌 + 三级残疾 + 32 岁女性 + 姓张"，
不需要身份证号就能确定是哪一户的谁。这叫**重识别**：单个字段都处理过，
组合起来等于没处理。

原来那套脱敏的目标是"防止身份证号明文泄露"，这个目标达成了；但它没解决
"这条记录能不能对应到具体的人"——而对居民数据来说，后者才是真正的红线。

### 10.2 撤换动作

| 动作 | 做法 |
|---|---|
| 清库 | 按批次删 `person_tag` → `person`（先子后父，否则外键拦住） |
| 换数据 | `scripts/gen_demo_persons.py --apply` 写入 300 条合成数据 |
| 移原件 | `data/incoming/real_ledgers/` → `F:\bise4-archive\ledger-originals\` |
| 清副本 | `data/backups/` 里 8 份 `before-import-*.db`（各带 2842 人）、`_sync` / `_synctest` 里的库拷贝、孤儿 `-wal` → `F:\bise4-archive\ledger-db-snapshots\` |

移出项目目录而不是留在原地，是因为 `.gitignore` 只能拦 `git`，拦不住压缩包。
压整个 `F:\bise4` 交作业、拷 U 盘、发微信，原件都会跟着走。

**验证方式**：把新库和换数据前的备份做 `id_hash` 集合求交，交集必须为 0：

```
现库人数: 300 | 备份人数: 2842
哈希交集: 0
```

同时把真实台账里的门牌逐个拿到新库里查出现次数（合成数据里一个都不该出现），
全部为 0。另加一层字节级检查：库文件里搜真实身份证的地区码，必须搜不到——
`DELETE` 只是把页挂进空闲链，**旧行还躺在文件里**；要 `secure_delete=1` + `VACUUM`
才真正抹掉（见 §10.3 ③）。

### 10.3 撤的过程中暴露的三个问题

**① 测试本身成了泄露通道。**

换完数据后跑回归，`smoke_person` 的 [E] 组（导入幂等）**把真实 2842 人又导回来了**。
因为它调的是 `import_ledger.py --apply`，读的就是真实台账。数据换掉了，但
测试还指着旧路径——"改用合成数据"等于白做。

改法：[E] 组不再调外部脚本，直接测 `Collector`（导入去重的唯一实现）。
真实台账这条路径由 `import_ledger.py --check` 负责验证，那是要人看着结果的
操作，不该塞进自动回归。

> 教训：**换数据源时，要搜所有还在读旧源的地方**，包括测试。
> 只改主路径不改测试，等于换个地方漏。

**② 断言绑定了数据规模，不是业务特征。**

三项变红：

```
[FAIL] 底册人数 > 2000（真实台账量级）      300
[FAIL] 未明确社区的人确实存在（真实数据特征）  150
[FAIL] 街道能看到未明确社区的记录             150
```

这几条看着像功能坏了，其实功能是好的——是断言把 `> 2000` 这种**当时那批数据
的规模**当成了判断标准。改成比例断言后与规模解耦：

```python
# 改前：n > 2000
# 改后：n >= 200                      → "够撑分页与筛选"
# 改前：n_blank > 500
# 改后：n_blank >= 0.4 * n_total      → "未明确社区占四成以上"
```

后者的语义是"台账大量没写清社区"这个**业务特征**，前者只是数字巧合。

**③ 删掉的行并没有从文件里消失。**

`DELETE FROM person` 之后表里查不到了，但**旧行还在文件里**——SQLite 只是把
那些页挂进空闲链。实测换完合成数据后：

```
page_count 452 | freelist_count 276 | secure_delete 0
```

452 页里 276 页是空闲的（61%），直接按字节搜库文件能捞出**完整记录**：

```
×**  52××××********××××  男  ××街道××社区××组  ××社区×栋×单元×室  一级残疾
```

身份证掩码、姓名、门牌、残疾等级、台账来源、导入时间戳，一条不少。
拷库、压缩包、发微信、交作业，这些记录都会跟着走——**"换成合成数据"等于没做**。

处理三步（缺一步都留残页）：

```sql
PRAGMA secure_delete = ON;      -- ① 之后释放的页会被零填充
VACUUM;                          -- ② 整库重建，只写现存行
PRAGMA wal_checkpoint(TRUNCATE); -- ③ WAL 里的旧页也要截掉
```

结果 `page_count 452 → 175`、`freelist_count 0`、`integrity_check ok`。
注意 **VACUUM 要独占**：先停掉 dev server，否则 `database is locked`。

两个容易漏的点：

- **`-wal` / `-shm` 是独立文件**。把 `smoke_policy.db` 移走了，`smoke_policy.db-wal`
  还留在原地，1.6 MB，里面是**整份真实底册**（按真实数据的证件地区码扫，命中 2237 处）。
  删/移库必须连 `-wal`、`-shm` 一起处理，并检查有没有"孤儿 wal"。
- **验证不能只查表**。表里查不到不等于文件里没有；要么按空闲页数判
  （`freelist_count` 必须为 0），要么直接扫字节找真实身份证地区码。

### 10.4 合成数据的设计：结构同构

合成数据不是为了"省事随便造几个"，而是要把答辩要讲的三个特征**精确复现**：

| 维度 | 真实台账（实测） | 合成数据 | 是否保持 |
|---|---|---|---|
| 人数 | 2842 | **300** | 缩规模，够撑分页与筛选 |
| 社区归属：未明确 | 65.3% | 50.0% | 保持"最大一块"，但不至于 300 人里 200 个查不了 |
| 地址：栋+单元+门号 | 41.3% | **41.3%** | **严格保持**——这是能不能匹配工单的分水岭 |
| 地址：仅到楼栋/组 | 28.4% | 28.3% | 保持 |
| 地址：无法定位 | 27.4% | 27.7% | 保持 |
| 权重 1（需关注） | 87.6% | 87.3% | **必须保持长尾**，否则"权重 1 不提级"讲不通 |
| 权重 3（重点看护） | 3.5% | 3.7% | 保持 |
| 标签：残疾 / 防溺水 | 19.7% / 81.3% | 19.7% / 81.3% | 保持 |

**三个锚点不能随机**，因为 `smoke_person` 依赖它们验证三档判据：

| 门牌 | 权重 | 派单结论 |
|---|---|---|
| `1栋1单元101` | 3（一级残疾） | `urgent` → 紧急 4h |
| `2栋2单元202` | 2（二级残疾） | `lift` → 升一档 |
| `3栋3单元303` | 1（三级残疾） | `flat` → 不提级 |

锚点地址特意用**顺号**（1栋1单元101 / 2栋2单元202 / 3栋3单元303）。早先用的
是真实台账里挑的门牌——那户真的住着一级残疾人，留在演示数据里
等于把"某社区某门牌住着一级残疾人"讲出来了，和"不用真实数据"直接冲突。
顺号一眼看得出是编的，反而安全。

生成器还有几条内部自洽检查，缺一条就会造出"一眼假"的东西：

- 防溺水对象必须是未成年人（4–17 岁），所以先定标签再定年龄，不是反过来
- 年龄与身份证生日一致（`expire_ok` 断言）
- 滴水岩村是村子，**不能有"17栋4单元"** —— 第一版真造出来了，村里一律只到组
- 村组名用"陈家寨组/李家寨组"，与城市社区的"昌盛组/诚信组"分开
- 门牌唯一，两户人不能挤同一门牌（否则反查会串）

## 11. 答辩预演

**Q：这些数据是真的吗？**

A：**底册里的 300 条是合成数据，不是真人。**但台账的格式、清洗规则、去重键、
地址解析，全部来自真实社区下发的四个文件（残疾人 559 条、防溺水 2466 条，
另两张是空模板）。真实数据完整跑通过，去重后 2842 人。

后来主动撤掉了，原因是脱敏只做到"姓名打码 + 身份证留前 6 后 4"，配上完整门牌
就是重识别——网格员一眼认得出是谁。现在用合成数据走同一套代码路径，
`LEDGER_SRC` 指回原件就能跑真实台账。详见 §10。

**Q：只有 41% 能定位到门号，那这套底册有什么用？**

A：两个用处。一是**统计与报表**——街道要的是"残疾人多少、按类别和等级怎么分布"，
这些不需要门号。二是**派单提级**——41% 里能精确到户的，报修时系统能认出
"这户住着一位一级残疾人"，把 72h 提到 4h。剩下 59% 不能匹配就按常规处理，
系统如实标注"仅到组"，不假装知道。

**Q：1855 人不知道属于哪个社区，为什么还留着？**

A：因为这是街道台账的真实状态。街道管全域，社保管辖区。留着的作用是
街道能做全街道的覆盖率统计；社区看不到这些，因为让社工拿着一份不知道是不是
自己辖区的名单去上门，是错的。

**Q：为什么不直接改系统名叫「住武社区」？**

A：改动面 20+ 文件、31 个测试脚本、8 张表，风险大于收益。做法是在
`ORG_ALIAS` 里显式登记映射，让"账号所属社区 → 台账社区"只有一个出口。
真要改名时只改这张表，不会漏。

**Q：如果街道换了新台账怎么办？**

A：`LEDGER_SRC=... python scripts/import_ledger.py --check` 先看清洗结果，
`--purge --apply` 清旧导新。脚本自己用 `sqlite3.backup()` 备份，
去重靠身份证哈希，重复导入不会产生重复人。跑完把演示库换回合成数据：
`python scripts/gen_demo_persons.py --apply`。

**Q：合成数据会不会让功能看起来是假的？**

A：不会，因为**判据是代码里的常量，不是数据里的巧合**。提级阈值
`LIFT_MIN_WEIGHT=2 / URGENT_WEIGHT=3` 只定义一处，页面结论、接口返回、
派单 SLA 三处读同一对常量。数据换成什么，这个逻辑都不变。
真要验证，把真实台账指回来重跑一遍，结论一致。
