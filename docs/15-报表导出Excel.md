# 报表导出 Excel：把"月报"做成能直接交的文件

> 对应代码：`app/xlsx.py`（写入器）、`app/report/export.py`（排版）、
> `app/views.py: report_export`（路由）、`scripts/smoke_report_export.py`（72 项回归）
>
> 结论先说：一份月报从"截图贴 Word"变成"点一下拿到 6 页表格"，
> 数字与系统内报表**完全一致**，且导出件不随库变化——这是它能当证据用的前提。

---

## 1. 为什么非要导出 Excel

报表页做出来之后，真实使用流程并没有闭环。街道要的是一份**能在自己电脑上改的表格**：
汇总到区里的模板里要粘数字、要按科室拆分发、要盖章扫描归档。
网页上的 ECharts 图和一段摘要，落到这个流程里只能"截屏贴进 Word"，
截出来的图既不能选中复制，也没法再做二次统计。

导出件要同时满足三件事，缺一件就不算能交：

| 要求 | 为什么 | 本文怎么保证 |
|---|---|---|
| 数字对得上 | 街道会把文件与系统里的页面并排看 | 只读报表快照，不重新统计（§4） |
| 打出来能看 | 最终形态是 A4 纸，不是屏幕 | 列宽/行高/合并/横向/铺满一页宽（§3） |
| 谁该拿谁不该拿 | 报表含治理数据，物业无权 | 沿 `report.view` 权限，403 并记审计（§6） |

## 2. 为什么自己写 xlsx，不用 openpyxl

和 `notice/export.py` 手拼 docx 是同一个判断：**线上托管环境里装没装包是不可控的**。
`requirements.txt` 每多一个包，就多一分"部署时装不上"的风险；而沙箱只给一个
HTTP 端口，出问题也不会有人来帮你 `pip install`。

openpyxl 的体量在 3 MB 级（还带 `et_xmlfile`），而本报表真正用到的东西很少：
单元格、合并、列宽、行高、冻结、筛选、十几种样式、日期与百分比格式。

自己写的代价与收益就摊在这里：

| | 自己写（`app/xlsx.py`，约 380 行） | openpyxl |
|---|---|---|
| 依赖 | **零**（`zipfile` + `xml` 都是标准库） | 1 个主包 + 1 个依赖 |
| 可控 | 每个 XML 字符都自己拼，格式问题能定位到行 | 黑盒，报错信息抽象 |
| 打不开能查 | `unzip -l` + 逐个 part 做 XML 良构校验即可 | 只能信它 |
| 公式 / 图表 | **不支持**（本系统也不需要） | 支持 |
| 大数据量写入 | 一次性进内存，几万行会慢 | 有 write_only 模式 |

不支持公式是刻意的：报表数字全部由服务端算好，导出件要的是"打开就能交"，
不是"打开还能算"。真有街道要在文件里改公式，那是他自己的二次加工，
不该由我们埋一堆易碎的 `formula` 进去。

### 手拼 xlsx 的五个坑（都已踩过并写进注释）

1. **`[Content_Types].xml` 必须覆盖每个 part**。漏一个 worksheet，
   Excel 直接弹"文件已损坏、是否尝试恢复"，而且不告诉你是哪一段。
2. **`styles.xml` 的 fills 前两项必须是 `none` 和 `gray125`**，位置固定。
   这是格式规定，不是约定；换序后 Excel 会静默丢掉所有填充色。
3. **worksheet 子元素顺序受 schema 约束**：`autoFilter` 在 `mergeCells` 之前，
   `printOptions` / `pageMargins` / `pageSetup` 必须在最后。顺序错了不报错，
   只是筛选和打印设置"看起来没生效"。
4. **文本用 `inlineStr`**，并给 `<t>` 加 `xml:space="preserve"`。
   否则 `" 附注"` 前面的空格会被吃掉——中文表格里首行缩进就是靠这个空格。
5. **日期要转序列号**（原点 1899-12-30），不能写字符串。
   写字符串的话 Excel 里是文本，排不了序、画不了图，筛选"本月"也筛不出来。

另外 XML 1.0 不允许的控制字符（`\x00-\x08` 等）必须先剥掉：
台账里从别处粘进来的奇怪字符，会让整个文件打不开。

## 3. 文件长什么样

一份 6 个工作表，顺序固定（`smoke_report_export.py` 会校验这个顺序）：

| # | 工作表 | 内容 | 给谁看 |
|:--:|---|---|---|
| 1 | 月报概览 | 标题、报送单位/编号、9 项核心指标（本期/上期/环比/口径说明）、统计区间、月度摘要 | 领导先看这一页 |
| 2 | 业务线分布 | 5 条业务线的事项数与占比 + 合计 | 按科室拆分发 |
| 3 | 业务类型分布 | 7 类业务的事项数与占比 + 合计 | 看结构变化 |
| 4 | 工单办理 | 三种状态分布、办结率、超期件数、SLA 分级说明 | 追物业进度 |
| 5 | 业务项明细 | 本月业务项清单（序号/类型/摘要/业务线/录入时间），冻结表头 + 筛选 | 抽查核对 |
| 6 | 填报说明 | 口径、数据来源、脱敏声明、生成方式、责任追溯、盖章与签字栏 | 被质疑时先看这里 |

几个刻意的排版决定：

- **表头用系统主色蓝、白字加粗**。打印成黑白后，表头与正文仍有明确分界，
  不会出现"一页全是横线看不出哪行是表头"。
- **每个表头都是"标题 / 副标题 / 空行 / 列名"四行结构**，与公文习惯一致。
  标题只合并到本表实际用到的列——合并到用不到的列，右侧会拖一条空白边框，
  打印出来像"少画了内容"。
- **工单页末尾是结论区**，不是纯表格：办结率、超期件数、SLA 分级各一行。
  报表是给人做判断的，不是数据集。
- **说明页带盖章与签字栏**。这不是装饰——纸质报送件必须有，
  没有的话社区还得自己在 Word 里画一个。
- **明细页横向、冻结表头、带自动筛选**。明细列多，纵向打印会挤成一团。

### 口径上最容易吵的两处，直接在表里写清楚

1. **一单多派**：一个业务项可以同时去多条业务线（如"隐患排查"同时去街道和综治），
   所以「业务线分布」的合计**可能大于**业务项总数。表下方的口径注释写明了这一点，
   避免街道拿合计去对首录数，对不上就以为系统错了。
2. **占比列之和可能大于 100%**：原因同上，营业线维度的分母是"业务项数"，
   分子是"该线的事项数"，跨线重复计入。

## 4. 数字从哪来：只读快照，绝不重算

这是本文最重要的一条规矩。

导出时**不查库**，只把 `report.data_json` 排版：

```
首录 → 拆解 → 派工单/写台账
        ↓
   报表 Agent（选月份，一次性汇总）
        ↓
   report 行：data_json = 汇总数字 + 明细快照（前 300 条）
        ↓                    ↓
   网页详情（读同一份）   导出 Excel（读同一份）
```

如果导出时重新统计，会出现两种很难解释的情况：

- 页面上写 12 件，导出文件里 15 件（导出前又录了 3 条），街道拿着两个版本对账；
- 去年 10 月的报表，今天导出来数字变了，归档件失去证据效力。

要新数字就**重新生成一份报表**，两份都留着——这本身就是可追溯。
`smoke_report_export.py` 第 4 组专门守这条：生成报表后往库里补首录和业务项，
再导出，数字必须**一点不动**。

### 明细快照为什么只留 300 行

报表主体是汇总，明细是附件。真要看全量，应该导出工单台账（下一步要做的），
而不是把几千行塞进月报的 JSON 里——`report` 表会被撑大，
`/api/reports` 列表也会变慢。

截断不是"悄悄少给"：快照里同时记 `item_rows_truncated` 条数，
Excel 明细页底部会写明"其余 N 个业务项未列入"。

### 缺失字段怎么显示

早期生成的报表没有 `org` / `overdue_count` / `item_rows` 这些字段。
导出时一律 `.get()` 兜底，缺的显示 `—`（而不是 0，也不是报错）：
- 显示 `0` 是**撒谎**——"超期 0 件"和"没统计"是完全不同的意思；
- 显示报错是**推卸**——老报表也是报表，得能打开。

## 5. 内容与网页的关系

| 网页 | Excel | 关系 |
|---|---|---|
| 报表详情页的九项指标 | 概览页同九项 | 同一个 `data_json`，一一对应 |
| 详情页的柱状图（业务线分布） | 业务线分布页 | 图看趋势，表看数字 |
| 摘要段落 | 概览页「月度摘要」 | 同一段文字，不重写 |
| —（网页没有） | 工单办理页、明细页、说明页 | 导出件比网页多三块：报送件需要的结论、附件与声明 |

网页不加这三块，是因为它们只在"交出去"的场景有用；
但导出件缺了它们，社区还得另开一个 Word 补，减负就打了折。

## 6. 权限与审计

- 导出挂 `report.view`，不是 `report.generate`。
  街道（`street`）有 `report.view` 没有 `report.generate`，所以**能导出、不能生成**——
  这正是上级单位的定位：核对与汇总由社区做，街道只取文件。
- 物业没有 `report.view`，导出返 403，并按既有规则写一条
  `audit(agent=auth, action=deny)`。保密场景下"谁试图下载了报表"本身要留痕。
- 未登录访问导出链接 → 302 到登录页（`next` 带回原地址）。

确认每张表的数值、数字格式（`#,##0` / `0.0%` / `+0.0%;-0.0%;0.0%`）都被正确识别。

## 8. 局限与后续

1. **只做了月报导出**。工单台账、审计日志还不能导出 Excel。
   台账是下一步优先项（社区交季度检查时最常要的那份）。
2. **无公式、无图表**。导出件里的柱状图位置是空的——需要图的话，
   打印网页版（ECharts 出图）或后续补一个原生 chart part。
3. **PDF 仍交给浏览器打印**。理由同 `notice/export.py`：容器里没有稳定的
   PDF 库，且打印前必须人工确认版面。
4. **明细上限 300 行**。超过的月份底部会注明，完整明细要走台账导出。
5. **样式规模有限**。没有条件格式、没有数据验证（下拉），
   因为这些都是"打开后还要编辑"才需要的功能。

---

## 9. 给答辩用的一句话

> 报表不是"页面上好看就行"，它的终点是一份能盖章报送的文件。
> 我们让报表在生成时冻结成快照，网页和 Excel 都从这一份快照出数，
> 所以页面数字、导出数字、历史归档三者永远一致——这是它能当口径证据的前提。
