# 统计口径与数据一致性

> 本文记录一次"页面数字全都不对"的排查与整改。
> 起因是做一次双角色走查（社区工作者 + 管理者视角），发现三个页面的
> "总数"类指标没有一个是对的——而且**没有任何报错**，页面看起来一切正常。
>
> 这类问题比功能缺失更危险：功能缺了会有人提，数字错了没人发现，
> 但管理者会拿着这个数字做判断。

---

## 1. 现象：三个页面的"总数"全都不对

| 页面 | 卡片 | 页面显示 | 库内实际 | 差 |
|---|---|---|---|---|
| 工单中心 | 已完成 | 16 | 23 | 少 7 |
| 审计日志 | 审计记录总数 | 200 | 1007 | 少 807 |
| 台账中心 | 台账总数 | 100 | 101 | 少 1 |

三个数字偏小的方向一致，说明是同一个病根，不是三次独立事故。

---

## 2. 根因：在"被截断的列表"里数长度

三个接口都给明细加了上限，而统计是在前端对这份被截断的明细做 `filter().length`：

```js
// 错的做法：数的是"这一屏里有多少"
document.getElementById('cDone').textContent = list.filter(o=>o.status==='done').length;
```

```python
# 接口侧只给最近 N 条
orders = q.order_by(WorkOrder.created_at.desc()).limit(50).all()   # 库内 57 条
logs   = q.order_by(AuditLog.created_at.desc()).limit(200).all()   # 库内 1007 条
items  = q.order_by(Ledger.created_at.desc()).limit(100).all()     # 库内 101 条
```

于是：

- 工单：50 条里恰好 16 条已完成，真实 23 条 → **少报**
- 审计：`list.length` 恒等于 200（上限），与库内无关 → **恒定错**
- 台账：`list.length` 恒等于 100 → **恒定错**

`limit` 本身没有错，列表只给最近若干条是合理的；错在**用明细算统计**。

---

## 3. 定规矩：统计在服务端，且与明细同源

> **凡"总数""合计""覆盖率"这类数字，一律由服务端 `count()` 给出；
> 前端只负责显示，永远不负责计算。**

"同源"是第二半句，同样重要：统计和明细必须基于**同一段过滤条件**。
否则会出现更隐蔽的错误——卡片说 28 条待接单，列表里只有 12 条，
因为卡片数的是全库、列表却按单位隔离了。

落实方式是抽出 `_scoped()` 这个唯一入口，读、统计、告警三处共用：

```python
def _scoped(q=None):
    """按身份收窄可见工单（列表 / 统计 / 超期告警共用）"""
    q = q or WorkOrder.query
    u = current_user()
    if u and u.role == "property" and u.org:
        q = q.filter_by(property_co=u.org)
    return q
```

## 4. 新的接口契约

三个列表接口统一返回 `{items, counts}`：

```json
{
  "code": 0,
  "data": {
    "items":  [ ... ],
    "counts": { ... }
  }
}
```

### 4.1 `/api/orders`

| 字段 | 含义 | 受数据隔离 |
|---|---|---|
| `total` | 可见工单总数 | ✅ |
| `open` / `doing` / `done` | 各状态条数 | ✅ |
| `overdue` | 未办结且已过 SLA 的条数 | ✅ |
| `shown` | 本次返回的明细条数 | — |
| `truncated` | 明细是否被 limit 截断 | — |

`overdue` 直接复用 `SuperviseAgent.is_overdue()`，不另写时间比较——
两套阈值迟早不一致，告警条和卡片就会互相打脸。

### 4.2 `/api/ledgers`

| 字段 | 含义 | 说明 |
|---|---|---|
| `total` | 台账总数 | **不受 `line` 筛选影响** |
| `reused` | 复用历史档案条数 | 同上 |
| `lines` | 覆盖业务线数 | 同上 |
| `matched` | 当前筛选命中条数 | 受 `line` 影响 |
| `shown` / `truncated` | 同上 | — |

### 4.3 `/api/audit`

| 字段 | 含义 | 说明 |
|---|---|---|
| `total` | 审计记录总数 | 不受 `agent` 筛选影响 |
| `security` | 保密审查批次 | 同上 |
| `deny` | 越权拒绝次数 | 同上 |
| `by_agent` | 各 Agent 条数 | 供筛选器一次取全 |
| `matched` / `shown` / `truncated` | 同上 | — |

**筛选只改 `matched`，不改 `total`。** 筛"保密审查"时把总数从 1007 改成 96，
会让人误以为整本审计账只有 96 条——那是最容易误读的一种错。

## 5. 两个实现陷阱

### 5.1 `func.sum(Boolean)` 会把 23 变成 1

台账"复用次数"第一次接上服务端统计时，返回 1，实际 23：

```python
# 错：SQLAlchemy 按列类型推断 sum 的返回类型，
# Boolean 的结果处理器把 23 归一成 True，再 int() 得到 1
total, reused = (Ledger.query
                 .with_entities(func.count(Ledger.id), func.sum(Ledger.reused))
                 .one())
```

```python
# 对：计数就用 count()，语义清楚，也不会被类型处理器改写
total = Ledger.query.count()
reused = Ledger.query.filter(Ledger.reused.is_(True)).count()
```

这个坑的可怕之处在于**不报错**：类型转换是"合法"的，页面上就是一个安静的错误数字。
回归里专门留了一条断言——`复用数没有退化成 1（布尔求和陷阱）`。

### 5.2 布尔事实不该只存在 JSON 里

`reused` 原本只写在 `ledger.content_json` 里，统计得把整表读出来反序列化，
而且报表 Agent 和台账接口各扫一遍——两处口径迟早会漂。

改成真实列 `ledger.reused`：

- 建表时 `FillAgent` 同时写 JSON（供展示）和列（供聚合）
- 老库由 `_migrate_ledger_table()` 补列，并按 `content_json LIKE '%"reused_archive": true%'` 回填
- 报表、台账接口、`eval_e2e.py` 三处统一读这一列

回填必须做：复用次数是"减负"效果的核心指标，老记录一律清零等于把历史效果抹掉。

## 6. 顺手清掉的演示痕迹

走查时发现两处硬编码，老师一眼能看出是"摆拍"：

| 位置 | 原来 | 问题 |
|---|---|---|
| 工单页副标题 | 写死"当前视角：幸福里物业" | 换任何一家物业公司都是错的 |
| 登录页演示卡片 | "张科长 · 和平街道" | 账号单位早已是"幸福里街道办事处"，同一个人两个名字 |

改法不是把字符串换对，而是**去掉硬编码**：

- 工单页：`{{ current_user.org }}`；非物业角色显示"监督视角 · 全部单位工单"
- 登录页：卡片由 `DEMO_USERS` 循环生成，姓名/单位/账号/密码全部来自账号数据；
  图标、配色、标签按角色查表

新增 `_login_page()` 统一渲染登录页，避免三处 `render_template` 各写一遍。

## 6.1 首录台看板：三块写死的数字

首页（FDE 首录台）是全系统的门面，也是"演示痕迹"最重的一页。走查时逐块核对：

| 位置 | 原来 | 问题 |
|---|---|---|
| 业务线柱状图 | `data:[12,9,15,5,5]` | 跟库里一条都对不上 |
| 柱状图 x 轴 | `['综治','民政','物业','卫健','城管']` | **系统里根本没有"城管"这条线**，真正有的是"街道" |
| 处理量趋势 | 拆解/派单/台账三组固定数组 | 同上 |
| 本周节省工时 | 写死 `18.5h` | 无法解释怎么算的 |
| 今日任务 | 5 行写死的"3栋楼道灯维修…" | 库里没有这些事项 |

危害不在于"数字不好看"，而在于**录完十条新事项图表一动不动**——评委只要问一句
"这根 15 是今天的吗"，就没有任何依据可答。

### 改法：新增 `GET /api/fde/dashboard`，所有数字现查

| 指标 | 口径 | 实现要点 |
|---|---|---|
| 首录总次数 | `fde_record` 全表 count | 与统计卡一致 |
| 拆解业务项 | `work_item` 全表 count | |
| 本周节省工时 | `(本周业务项 × 6min + 本周复用台账 × 10min) / 60` | 基准常量在 `app/api/fde.py:MIN_PER_ITEM/MIN_PER_REUSE`；**公式原文随接口下发**（`saved_basis`），页面悬浮提示与答辩口径同一句话 |
| 业务线分布 | 本周 `work_item.target_lines` 按逗号拆分逐项计数 | 多值字段只能逐行拆，无法一条 SQL 分组；只取这一列，不捞正文 |
| 处理量趋势 | 三张表按 `created_at` 日期 `GROUP BY`，**本周一 → 今天** | 用 `func.date()` 让统计与明细同源 |
| 今日任务 | 今日 `work_item` + 其工单流转状态 | 状态分布算**今日全部**事项，不是屏上那 8 行 |

### 五个判断，都不是"顺手写"的

1. **业务线顺序写死** `("物业","综治","民政","卫健","街道")`，不按数量降序。
   否则同一业务线今天在左、明天在右，两张周报截图放在一起颜色对不上。
2. **合计会大于事项数**，这是对的：一条"楼道灯坏了 + 登记租户"会同时派给物业和综治。
   卡片 hint 明写"一条事项可派往多条线"，不让两处数字看起来打架。
3. **趋势只画到今天**，不画满周一到周日。把周四~周日画成 0，曲线末端会像"断崖式下滑"，
   看图的人只会以为系统出事了。
4. **今日为空不粉饰**：回退最近 6 条，并把标题改成"最近录入"、hint 写明"今日暂无录入"。
   显示"今日 0 项"加一张空表，用户不知道是没录还是坏了。
5. **状态分布与"今日 N 项"同源**：都按今日全部事项算。若分布只数屏上 8 条，
   就会出现"今日 12 项"配上"分布合计 8"的自相矛盾。

### 联动：录完必须自己变

`runFDE()` 最后一步调 `loadDash()`。假数据的观感不只来自数字本身，
也来自"操作完页面没反应"——真数据 + 不刷新，看起来和假数据一模一样。

### 回归

`scripts/smoke_dashboard.py`，61 项，只守一件事：**接口吐的每个数字都能对上一条 SQL**。

| 分组 | 覆盖 |
|---|---|
| A 权限形状 | 管理员 200 / 物业 403（真状态码）/ 未登录 401；五个子结构齐全 |
| B 口径 | 统计卡、工时公式、柱状图逐柱、趋势逐日、今日事项，全部与独立 SQL 对账 |
| C 联动 | 插两条业务项 → 总数/本周/工时/柱子/折线/今日表同时变；工单 doing → 事项显示"办理中" |
| D 空态 | 今日无录入 → `fallback=true`、回退有行、count 与行数一致、折线落到 0 |
| E 页面 | 剥离注释后，模板里不许再出现那些写死的数字与"城管" |

> E 组特意**先剥注释再断言**：注释里写着"以前这里是 [12,9,15,5,5]"是有价值的事故记录，
> 为了过测试把它删掉，下次还会有人写回去。

改完的页面见 `docs/img/fig12_dashboard.png`（桌面）与 `fig12_dashboard_mobile.png`（390 宽）：
四张卡 41 / 54 / 2.1h / 46，柱状图 22 项次（> 本周 18 个事项，因为一条可派多线），
折线只到周五（今天），今日任务 1 条配四格分布 0/1/0/0。

## 7. 测试隔离：三套旧测试一直在污染演示库

排查过程中发现：`smoke_auth` / `smoke_tasks` / `smoke_kb` 没有设置 `DATABASE_URL`，
一直直接跑在 `data/community.db` 上。证据是跑一遍全套之后：

```
跑测试前：审计 1014 条，已完成工单 23 件
跑测试后：审计 1079 条，已完成工单 24 件   ← 测试把演示工单真的办结了一单
```

这也是"审计记录总数 1007"里大量记录的真实来源——不是系统跑出来的，是测试写进去的。

处理：

| 脚本 | 办法 | 原因 |
|---|---|---|
| `smoke_auth` | 独立空库 | 自己造 FDE 数据，本来就不依赖演示库 |
| `smoke_kb` | 独立空库 | 知识库文档启动时自动入库，无需演示数据 |
| `smoke_tasks` | **复制** `community.db`（含 `-wal`） | 依赖演示库的 `field_security`，空库跑不了 |

`smoke_tasks` 还有一个细节：SQLite 开着 WAL，只拷主库文件会得到几小时前的旧快照，
必须连 `community.db-wal` 一起拷，否则拷出来的数据是过期的。

改完复跑：12 套 547 项全过，且 `community.db` 的审计条数在跑测试前后**完全一致**。

## 8. 回归测试

`scripts/smoke_stats.py`，50 项，只守一件事：**页面上的数字 = 库里的真实条数**。

| 分组 | 覆盖 |
|---|---|
| 1 契约 | 三个接口都返回 `{items, counts}` |
| 2 工单 | 三状态、超期、总数与库一致；隔离后看不到别家 |
| 3 limit | 改 limit 只动明细，不动统计；超大/非法 limit 有兜底 |
| 4 台账 | 总数/复用/业务线与库一致；**复用没退化成 1** |
| 5 筛选 | 筛业务线只改 `matched`，"家底"三项不变 |
| 6 审计 | 总数/保密审查/越权拒绝与库一致；筛 Agent 不改总数 |
| 7 页面 | 视角文案取会话单位；换一家物业跟着变；登录卡片读账号数据 |
| 8 报表 | 报表不再自己扫 JSON 数复用（防止口径再次分叉） |

复跑：

```bash
python scripts/smoke_stats.py
```

## 9. 还没做的（已知边界）

- **列表仍是"最新 N 条"**：工单 50、台账 100、审计 200，没有分页、搜索、时间筛选。
  现在至少会显示"显示最近 100 条，共 101 条"，不会再假装这就是全部。
- **报表与台账不能导出**：目前月报可导 Excel（`docs/15`），台账与审计还只能看页面，
  社区交季度检查要的那份台账仍得手抄。
- **管理端无移动适配**：侧边栏固定 230px，手机 375px 宽下内容区只剩 145px。
  只有居民端做了响应式。
- **没有消息提醒**：新工单、新来文靠人刷页面。
- **`work_order` 无处理人字段**：只能追到公司，追不到人；"谁办结的"要去审计翻 actor。

以上是"现场够不够用"的问题，不改也不会算错数，但会在真实使用中卡住人。
