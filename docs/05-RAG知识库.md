# 05 · RAG 知识库（F10）

> 目标：让系统“懂政策”，而不是只会拆句子。
> 代码：`app/kb/store.py`（检索）、`app/kb/seed.py`（入库）、`app/agents/knowledge.py`（知识库 Agent）、`app/api/kb.py`、`app/templates/kb.html`
> 测试：`scripts/smoke_kb.py`（27 项，全通过）

---

## 1. 在系统里承担什么

| 场景 | 没有知识库 | 有知识库 |
|------|-----------|----------|
| 居民问“高龄津贴多大能领、要什么材料” | 社工凭记忆或翻文件 | 拆解成「咨询」业务项后自动带出 2 条政策依据，可一键看原文 |
| 新人上手 | 靠老同志口头带 | 直接问系统，答案带文件名与条款位置 |
| 报表口径争议 | 各人理解不同 | 口径说明在库里，检索即得，减少来回确认 |
| 保密 | — | 全部文档留存在本地磁盘与本地库，检索不联网 |

RAG 在 FDE 主链路中只做**检索**（毫秒级），不额外调模型，所以不会拖慢首录；
需要生成答案时走 `/api/kb/ask`，用户主动触发，可以接受 2~5 秒。

## 2. 技术选型：为什么默认是 BM25 而不是向量库

这是本模块最需要讲清楚的一个取舍。

| 方案 | 显存占用 | 中文政策检索效果 | 依赖 | 结论 |
|------|----------|------------------|------|------|
| **BM25 + 字符二元组** | 0 | 专有名词命中准（高龄津贴/居住证/群租） | 无 | ✅ 默认 |
| bge-m3 / nomic-embed + FAISS | 1.2~2.5 GB | 语义泛化更好 | 需再拉模型 | ⚠️ 可选 |
| 直接用 qwen3:8b 做 embedding | 6.7 GB（已被占用） | — | — | ❌ 不现实 |

约束是硬的：本机 8GB 显存已经被 qwen3:8b 占去 6.7GB。再加载一个 embedding 模型，
要么挤爆显存、要么把生成模型挤回 CPU（速度从 42 tok/s 掉到 8 tok/s），得不偿失。

因此默认使用 **BM25 稀疏检索**，中文按**字符二元组**切分（不依赖 jieba，零下载）：

- 政策文本用词规范、术语稳定，“高龄津贴”“居住证”“消防通道”这类词命中即可定位；
- 完全确定性、可解释：能指出命中了哪些词、哪个小节，答辩演示好讲；
- 代价是同义改写能力弱（“认定”与“形成条件”属于能蒙对，“办低保”对“最低生活保障”就吃力）。

**升级路径已留好**：设置环境变量 `KB_EMBED_MODEL=bge-m3`（并 `ollama pull bge-m3`）后重启，
检索自动切换为 `0.65 × BM25 + 0.35 × 余弦相似度` 的混合模式；模型拉不到会自动回落，不会报错。

## 3. 切片策略

| 参数 | 值 | 说明 |
|------|-----|------|
| `KB_CHUNK_SIZE` | 420 字 | 一个切片大约一段到两段，能完整说清一个办理环节 |
| 切分依据 | Markdown 标题 + 段落 | 先按 `##` 分节，同节段落聚合到 0.6 倍长度再切 |
| 超长段落 | 按句号/分号二次切分 | 避免一个切片横跨多个主题 |
| 上下文前缀 | `小节名｜正文` | 让“所需材料”这类片段脱离原文后仍可理解 |
| 跳过内容 | `>` 引用块 | 来源、演示说明没有业务信息，会挤掉真正条款 |

效果：10 篇文档 → 48 个切片，平均 121 字。

## 4. 检索算法

对每个查询：

```
score = Σ_t IDF(t) · tf·(k1+1) / (tf + k1·(1-b+b·dl/avgdl))     k1=1.5, b=0.75
score *= 1 + 0.8 · |查询词 ∩ (文档标题 ∪ 小节名)| / |查询词|      # 主题加成
```

- 主题加成的作用：问“低保要什么材料”时，`所需材料` 小节应当排在前面，而不是被篇幅更长、
  但主题泛化的片段顶掉（实测加成本身把该用例的 Top1 从“注意事项”纠正为“所需材料”）。
- 归一化后输出 0~1 匹配度，前端直接显示百分比。

## 5. 问答约束（防幻觉）

Prompt 里写死五条硬规则：

1. 只依据【资料】回答，不得使用资料之外的知识，不得编造条款、金额、时限；
2. 每条结论后用《文件名》标注出处；
3. 资料不足时直接说“知识库中未收录相关规定”，不要猜；
4. 分点作答，先结论后步骤；
5. 涉及个人信息时提醒最小必要原则。

模型不可用（Ollama 未启动/超时）时降级为**原文摘录**，功能不中断，前端标注“已降级”。

---

## 6. 文档维护

两条路径，都幂等：

1. **页面新增**：`/kb` → 新增文档（标题/分类/来源/正文），保存即重建索引，无需重启；
2. **文件放入**：把 `.md`/`.txt` 放进 `data/kb/` → 重启服务 → 按标题去重增量入库。

页面支持删除（同步重建索引）。物业角色无任何知识库权限；街道只读；社区可维护。

## 8. 局限（如实写）

| 问题 | 现状 | 改进方向 |
|------|------|----------|
| 同义/口语泛化 | BM25 依赖字面重合，“办低保”查“最低生活保障”会漏 | 开 `KB_EMBED_MODEL` 混合检索，或加同义词表 |
| 无重排序 | 单阶段召回，Top1 偶有次优片段 | 加 bge-reranker（需显存）或规则重排 |
| 引用未校验 | 模型标了出处，但未逐句核对是否真出自该段 | 抽句比对，引用句与片段做字面重合校验 |
| 语料规模 | 10 篇示例文件，非真实社区全部文件 | 换成现行文件后重跑评测，统计 Top1/Top3 命中率 |
| 无版本管理 | 文档改了直接覆盖，无历史版本 | 加 `kb_doc_version` 表 + 生效日期 |

## 9. 论文可写的点

1. **资源受限下的 RAG 取舍**：同一张 8GB 显卡上，生成模型与 embedding 模型争显存的真实权衡，
   不是“无脑上向量库”；
2. **可解释检索**：BM25 能给出命中词与小节，符合政务场景“可核对”的要求；
3. **闭环价值**：知识库不是独立问答框，而是嵌进 FDE 拆解结果里，咨询类事项自动带依据，
   这是“减负”而非“加一个功能”；
4. **可量化**：27 项测试 + Top1 命中率可扩展到 50~100 条问法做正式评测。
