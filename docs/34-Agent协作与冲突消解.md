# 34 · Agent 协作与冲突消解

> 一句话：把「顺序调用几个函数」改成「多个 Agent 对同一件事各自表态、
> 按明确规则消解、全过程可回放」。这是标题里 **Multi-Agent 协作** 唯一站得住的做法。

---

## 1. 改造前的问题：那不是协作，是管道

第一版 `Orchestrator.handle_fde()` 长这样：

```
security.run() → parser.run() → for item: dispatch.run() / fill.run() → commit
```

后一个 Agent 只拿前一个的输出当输入，**谁也不能影响谁的结论**。这条链有
三个硬伤，答辩时一问就露：

| 问题 | 事实 | 后果 |
|---|---|---|
| Agent 大多是规则 | 7 个 Agent（parser/dispatch/fill/knowledge/security/supervise/report）里只有 **2 个**调大模型 | 「7 个 Agent」名不副实 |
| 没有交互 | 把 `dispatch.run()` 换成普通函数调用，系统行为一行都不变 | 「协作」二字无意义 |
| 过程不留痕 | `audit_log` 只存 250 字摘要，页面上看不到「谁定的、依据是什么」 | 说不清「多主体强在哪」 |

这一点不自己说，评委也会问。所以这一轮补的不是功能，是**结构**。

## 2. 黑板：让多个 Agent 对同一件事表态

`app/agents/blackboard.py`

```python
bb = Blackboard()                    # 一次诉求处理 = 一块黑板 = 一个 run_id
bb.step("security", "mask", ...)     # 过程记录，不参与消解
bb.post("dispatch", "sla", ("一般", 72), reason="词表命中「垃圾」")   # 表态
bb.post("risk",     "sla", ("紧急", 4),  reason="这户报过 3 次")       # 表态
res = bb.resolve("sla")              # 消解：有分歧才产生记录
```

三个设计点：

**① 表态与留痕是同一个方法。** `step()` 带 `topic` 就是表态。
分成两个方法调用，接口层迟早漏掉一个——而漏掉留痕不影响功能，所以不会有人发现。

**② 没有分歧就返回 `None`。** 把「两个 Agent 意见一致」显示成「裁定过一次」，
等于伪造协作。页面只渲染真分歧，答辩时说的每一句都能对应一次真实冲突。

**③ 消解完把该议题移出待议区。** 否则同一个黑板上处理第 2 个业务项时，
第 1 项的表态还在里面比大小（详见 §7 坑 1）。

## 3. 冲突从哪来：三个信号，都能单独解释

`app/agents/riskreview.py`。派单 Agent 只看一个字符串里的关键词，
风险复核才跨表查历史。

| 信号 | 触发条件 | 效果 | 置信度 |
|---|---|---|---|
| 安全隐患 | 原文含「燃气 / 漏电 / 困人 / 明火 / 消防通道 / 滑倒 / 坠落」 | 直接压到 **紧急 4h** | 0.95 |
| 重复报修 | 同址同类 30 天内已有 N 张单 | N=1 升 1 档，N≥2 升 2 档（封顶） | 0.80 |
| 推诿史 | 同址历史单有过跨单位转派 | 升 1 档 | 0.60 |

**没有信号就不表态**（`level=None`），不硬凑理由。如果每个 Agent 都必须
给结论，「多数一致」会变成常态，冲突消失，消解机制就成了摆设。

### 两份词表故意不完全一样

`dispatch.SLA_RULES` 认的是**已经出事**（水管爆裂、电梯困人）；
`riskreview.SAFETY_WORDS` 认的是**可能出事**（燃气味、冒烟、地面积水致人滑倒）。

同一句「卫生间漏水」，dispatch 读出来是「较急 24h」；
但如果原文里有「老人滑倒」，它就不是普通漏水。**词表重叠但不相等，
这个差本身就是分歧的来源**——不是 bug，是设计。

### 地址识别分三级，精度按问题类别给

真实诉求大多没有门号。翻演示库 41 张单实测：

| 级别 | 能认到什么 | 张数 |
|---|---|---|
| 3 | 栋 + 单元 + 门号（`3栋2单元201`） | 5 |
| 2 | 栋 + 单元（`7栋3单元`） | 9 |
| 1 | 只有栋（`9栋`） | 15 |
| 0 | 认不出 | 12 |

只认三元组，等于功能在真实数据上全线失效——因为电梯、楼道灯、门禁、
垃圾桶都是公共设施，居民只会说「7栋3单元电梯异响」。

所以精度按类别给：

- **住宅类**（漏水 / 噪音 / 油烟）**必须有门号**。否则 3栋2单元的漏水
  会把 501 和 502 合成一件，报修三次的判定就成了捏造。
- **公共设施**（电梯 / 照明 / 门禁 / 消防 / 清运 / 堆物 / 路面）用「栋+单元」即可。
  一栋楼只有一部电梯，「7栋3单元电梯」报三次就是同一部电梯。

判重还必须**同址 + 同类**。不加类别的话，「2栋2单元202漏水」会和
「2栋2单元202电梯异响」算成同一件事，报修三次电梯的居民被判定
「漏水报了三次」，时限升得毫无道理。

## 4. 消解规则：为什么是「更严者胜」而不是投票

```
派单Agent：一般 72h（按规范词表）
风险复核：紧急 4h（这户 30 天内第 3 次报漏水）
→ 采纳「紧急 4h」。规则：合规要求只能加严，不能放宽。
```

系统里 7 个 Agent，5 个是规则实现。把它们做成多数表决没有意义：
规则 Agent 会互相印证同一次词表命中，票数只反映谁的词表更长。

更关键的是**制度上不成立**：如果按票数，两张 72 小时的宽松结论会压过
一张「这户已经报过三次」的紧急结论。而现实里恰恰是后者该说了算。

所以规则是**单向妥协**：

> 合规与安全的要求只能加严、不能放宽。

这条也解释了为什么**顺序无关**——先说的宽松结论翻不了盘（`smoke_collab`
A 段有断言）。也不存在「谁嗓门大」，只有「谁更严」。

## 5. 时序：定级必须发生在建单之前

```
❌ 错：dispatch 按词表建单（写 72h）→ risk 复核后改 sla_hours 为 4h
   后果：工单流转链第一条 log 写着 72h，工单字段是 4h，
        事后没人解释得清「为什么这条记录和这张单对不上」

✅ 对：dispatch 表态（不建单）→ risk 表态 → resolve → 带结论建单
   后果：dispatch log 的 detail 里直接写「紧急 / 4h，风险复核升级：……」
        全程只有一条 dispatch 记录，没有「先建错再改」
```

实现上，`DispatchAgent.run()` 接受 `payload["sla_level"]` / `sla_hours`：

- 调度器**没给** → Agent 按词表自己判（旧路径，也是消融基线）
- 调度器**给了** → 说明黑板上已消解过，Agent 只执行，不改结论

决策权上移是刻意的。让 Agent 自己算完了再被覆盖，等于「先建单再改级」。

## 6. 轨迹：把「系统内部怎么想的」变成可查记录

### 表

`agent_step`（`app/models.py`）：`run_id / seq / agent / action / decision /
reason / topic / took_ms / degraded / fde_id / work_item_id / order_no`

**为什么不塞进 `audit_log`**：审计表是合规账本（谁看、留多久、怎么脱敏都有约束），
刻意只存 250 字摘要。把拆解过程、密级判定塞进去，等于给审计表开一个新泄露面。
两件事的读者、保留期、脱敏要求都不一样。

**行数会涨得比业务快**：一条诉求至少 4 步，一个业务项多两步。
所以 `run_id`/`fde_id` 建索引、`decision` 截 200 字、`reason` 截 400 字、
不做级联删除（FDE 删了轨迹仍留着，它是「当时系统怎么想的」的唯一记录）。

### 接口 `/api/collab`

| 端点 | 作用 |
|---|---|
| `GET /runs?limit=` | 最近的运行列表（按 run_id 归并，带步数/是否提级/工单号） |
| `GET /trace?run_id=` | 单次轨迹：全部 steps + 参与消解的 claims + resolutions |
| `GET /stats?days=` | 定级数 / 复核表态 / 提级数 / 压缩小时 / 各 Agent 耗时 |

### 页面 `/trace`

左边运行列表，右边两步：

```
⚡ 同一件事有两种结论，按「更严者胜」裁定
 ┌────────────────────┐  ┌────────────────────┐
 │ 派单 Agent          │  │ 风险复核  ← 采纳    │
 │ 一般 72h            │  │ 紧急 4h             │
 │ 按规范词表定级       │  │ 这户 30 天内第 3 次 │
 └────────────────────┘  └────────────────────┘
 规则：合规要求只能加严不能放宽 —— 两张宽松结论压不过一张「这户已经报过三次」

① 安全 Agent   脱敏 0 处                        1 ms
② 拆解 Agent   拆出 1 个业务项                1840 ms
③ 派单 Agent   一般 72h                          2 ms
④ 风险复核     紧急 4h                           0 ms
⑤ 消解         采纳 risk 的「紧急 4h」           0 ms
⑥ 派单 Agent   W2026… → 幸福里物业（紧急 4h）     2 ms
```

这一屏就是答辩的答案：**多 Agent 比单次调用模型强在哪**。

## 7. 三个静默失效的坑（都不会报错）

### 坑 1 · 消解污染：第 2 个业务项被第 1 项压住

`resolve()` 原本不清空待议区。一条诉求拆出 3 个业务项时，第 2 项的
`resolve("sla")` 会把第 1 项留下的表态一起拿来比大小——第 2 项明明该升到
紧急，却被第 1 项里「较急」那条旧表态挡住，winner 停在第 1 轮。

**修**：`resolve()` 无论有没有分歧，都把该议题移出 `self.claims`（表态仍留在
`steps` 里，页面时间线读那份）。

### 坑 2 · 判重键不稳定：「501」和「501室」是两户

复用 `fill.extract_room_key()` 时，正则 `\d{3,4}室` 会把「室」吃进去，
于是「2栋2单元202卫生间漏水」和「2栋2单元202室漏水维修」——同一户——
给出两个不同的键，**重复报修永远数成 0**。

更隐蔽的是 subject 由模型重写，同一户两次报的措辞必然不同。于是功能
看起来「上线了」，实际一次都没触发。

### 坑 3 · 升档倒退：报修第 4 次反而不升级

初版写 `REPEAT_UP_LADDER = {1: 1, 2: 2}` + `.get(n, 0)`。n=3 时取到默认值 0，
**第 4 次报修不升级了**，而且一路静默。

「次数越多越宽松」这种错误没有任何机制能发现，只有手工造到第 4 次才看得见。
**修**：`min(n, 2)`，单调不减。回归里专门有一条「报修第 5 次仍然升级」。

### 附带一条：`limit=abc` 会 500

`int(request.args.get("limit", 20))` 对非数字直接抛 ValueError。
分页参数是最常被手工改的东西（把 URL 里的 20 改成 abc），
500 会让人以为整个接口挂了。统一走 `_int_arg()` 兜到默认值再夹区间。

## 8. 权限：轨迹比审计还窄

| 角色 | `/trace` 页面 | `/api/collab/*` | 理由 |
|---|:---:|:---:|---|
| 社区 | ✅ | ✅ | 轨迹是社区自己的内部复盘 |
| 管理员 | ✅ | ✅ | 同上 |
| 街道 | ❌ | ❌ | 街道走 `audit.view`（合规留痕）；问「发生了什么」，不问「为什么这么定」 |
| 物业 | ❌ | ❌ | 被监督方。轨迹里必然有「系统认定这户是反复投诉户」 |
| 居民 | ❌ | ❌ | 只看结果 |

页面权限用 `fde.view`，接口的角色白名单 `TRACE_ROLES = ("community", "admin")`
**与 `fde.view` 覆盖的角色完全一致**。页面上进得去、接口却 403（或者反过来）
这种「半边开」最麻烦：用户看到空白页，日志里记的是「放行」。

## 9. 实测（2026-10-26，隔离库，8 条真实句式）

```
第一轮（建立历史）
  较急 24h | 7栋3单元电梯异响
  一般 72h | 5栋1单元302楼道灯不亮
  较急 24h | 3栋2单元201卫生间漏水

第二轮（复核有机会提异议）
  紧急  4h | 升级 ✓ | 7栋3单元电梯又响了，昨天已经报过
  较急 24h | 升级 ✓ | 5栋1单元楼道灯还是不亮
  紧急  4h | 升级 ✓ | 3栋2单元201又漏水，老人差点滑倒
  较急 24h | 升级 ✗ | 9栋门禁坏了，刷卡没反应
  较急 24h | 升级 ✗ | 6栋3单元402家里水压特别小
```

| 指标 | 值 |
|---|---|
| 定级数 `decisions` | 8 |
| 复核表态 `reviewed` | 3 |
| 提级 `upgraded` | 3（37.5%） |
| 累计压缩 `saved_hours` | 88 |
| 迁移 `pairs` | 一般→较急 ×1、较急→紧急 ×2 |
| 轨迹行数 | 39（有冲突的 run 7 步，无冲突 4 步） |

各 Agent 耗时：`parser` 平均 ~1.6 s（P90 1.5 s、max 2.85 s，本地 qwen3:8b）；
`dispatch` 1.6 ms；`security` 1.0 ms。**耗时几乎全在模型上**，
协作本身是毫秒级开销——这是「多 Agent 不拖慢系统」的直接证据。

演示库（41 单）的判重覆盖率：能识别问题类别 32/41，地址三级识别
5/9/15/12，真实可判重 2 组。

## 10. 能力边界（写论文别越界）

1. **只有 2 个 Agent 调模型**（parser / knowledge），另外 5 个是规则。
   说「7 个 Agent 全部由大模型驱动」不成立。
2. **只有一个消解议题（SLA 时限）**。曾经想加「密级」和「是否督办」，
   但前者两个 Agent 并不矛盾（做了就是伪造分歧），后者没有任何 Agent 会表态
   （做了就是自说自话）。议题表里只留真实存在的分歧。
3. **37.5% 是这批测试场景的提级率，不是线上发生率**。它取决于历史单的
   分布，换一批数据就变。
4. **`saved_hours` 不是省下的工时**。一张单从 72h 压到 4h，压力上升、工时不变。
   它是「响应窗口被压缩的量」，越大说明历史问题越集中。
5. **地址识别有 12/41 认不出**。这些单不会触发重复报修判定。
   这是保守设计：宁可漏，不要错——认不出具体是谁家，就不说「这户重复报修」。
6. **消解规则是制度编码，不是客观真理**。「更严者胜」可以改成别的，
   改完必须重新跑回归。

## 12. 答辩预演问答

**Q：7 个 Agent 都用大模型吗？**
A：2 个用（拆解、政策问答），5 个是规则。这是刻意的：派单定级、脱敏、
填报这些事有明确规范，用模型反而不稳定也不可解释。文档里的消融实验
（docs/03）就是在量化「哪些环节换成模型是加分的」。

**Q：这算多 Agent 吗？还是一条流水线？**
A：流水线那部分还在（脱敏→拆解→入库），但**定级这一段已经不是了**：
两个 Agent 对同一张单各自给结论，不一致时按规则消解，依据和裁定都落库。
评测上能看出来差别——按词表定级，那 3 张单会各多拖 20 小时、48 小时。

**Q：为什么不是投票？**
A：投票要求投票者独立且能力相当。这里 5 个是规则实现，会互相印证同一次
词表命中，票数只反映谁词表更长。而且制度上，两张 72 小时压过一张
「已经报过三次」是错的。

**Q：风险复核的权重/阈值怎么来的？**
A：没有权重，是阶梯规则：历史 1 张升 1 档、2 张及以上升 2 档，封顶。
门槛 30 天来自「一个月内重复报修」这个社区常用口径。这些是可以被质询的
制度参数，不是训练出来的。

**Q：会不会误判？误判了怎么办？**
A：会。所以判重必须**同址 + 同类**，住宅类还必须有门号（分不清 501 和 502
就不判）。宁可漏——漏了只是少提一次级，错了是凭空加严，居民和物业都会投诉。
另外每次提级都留了完整依据，物业可以申诉，社区可以在轨迹页看到是哪条历史单
触发的。

**Q：轨迹表会不会越来越大？**
A：会，而且比业务快。所以：`run_id`/`fde_id` 建索引、字段截断、页面按
run 取不全表扫、不做级联删除。归档策略还没做（记在局限里），
按现在的量级（一条诉求 ~5 行）三年也就几十万行，SQLite 撑得住。
