# 33 · 流程监控与长尾风险预警

> 对应代码：`app/process.py`（流程挖掘）、`app/risk.py`（风险评分）、
> `app/textmine.py`（投诉文本）、`app/api/insight.py`（三个接口）、
> `app/templates/process.html`（流程监控台）、`app/templates/risk.html`（风险预警台）
> 回归：`scripts/smoke_insight.py`（107 项）
> 演示数据：`scripts/seed_risk.py`（24 条诉求 / 造出 41 张单 113 条流转）

---

## 1. 这一轮只做"能立刻成立的那半"

原计划里有两个东西：**流程挖掘**和**投诉文本聚类**。它们的可信度完全不在一个量级，所以拆开做：

| | 流程挖掘 / 长尾预警 | 投诉文本聚类 |
|---|---|---|
| 输出是什么 | 每步停留几小时、哪条边最慢、哪张单卡了 56 天 | 25 条诉求分成 11 个簇 |
| 由什么决定 | 流转日志的时间戳，是**事实** | 2-gram 字面相似度 + 人工阈值 |
| 数字稳定吗 | 稳定，重跑不变 | 阈值一动结论就变 |
| 敢照着行动吗 | 敢（"这单超 30 天，该督办"） | 不敢（"这 5 条相近"——相近所以呢？） |

所以本轮的做法是：**流程的每一项都做成可核验的确定结论，文本这块先留接口、把纯度如实标出来、结论一律以人工词表为准。**

这不是保守。反过来做（先吹聚类有多准）在会上会被问一句"这个簇为什么算一个簇"，答不出来。

## 2. 停留时长：用相邻日志差，不用工单字段

最容易写错的一步，也是本项目真写错过的一步。

**错误做法**：拿 `order.assigned_at` 当"接单时刻"，和 `done_at` 相减。

`assigned_at` 只记**最后一次**接单。一张单被转派 3 次，`assigned_at` 是第 3 次的时间，于是"处理时长"从第 3 次算起——前面 40 天凭空消失。而这张单恰恰是最该被看见的那张。

**正确做法**：`app/process.py:transitions()` 把日志按 `(order_id, created_at, id)` 排序，取**相邻两条的时间差**作为"从前一个动作到后一个动作的停留时长"。

```
工单 W20260831-050907-68 的日志
  08-31 派单
  09-01 转派   ← 派单→转派 停留 24h
  09-05 转派   ← 转派→转派 停留 96h
  09-16 转派   ← 转派→转派 停留 280h   ← 这就是"打转"的形状
```

边（edge）才是流程挖掘的基本单位。只看"平均处理时长 5 小时"会掩盖"一单压了 30 天、其余都是 1 小时"。

实测结果里 `转派 → 转派 n=3, 平均 178.0 小时` 排在 `接单 → 办结 n=25, 平均 38.9 小时` 前面——**"在两个单位之间推来推去"比"正常办完一单"慢 4.6 倍**。这句结论不需要任何模型，日志自己能说。

## 3. 已办结的单必须算到 `done_at`，不是算到 `now`

实现 `age_hours()` 时的分叉：

```python
def age_hours(o, now=None):
    now = now or datetime.now()
    end = o.done_at if o.status == "done" else now
    if end is None:          # done 但没有 done_at：数据缺失，不猜
        return None
    return round((end - o.created_at).total_seconds() / 3600, 2)
```

不这么写的后果实测过：18 张单里 **17 张被判"异常"**，等于没筛。

原因：9 月 20 日办完的单，拿 10 月 26 日的 `now` 去减，得出"已 36 天未结"。它早就办完了，只是被当成了"还没办"。**这个错不抛异常、不报错，只让告警排满早已完结的单**，使用者点开一看全是办完的，从此不再看这个页面。

改完之后异常从 17 降到 8（在当时的样本上），后来垫数据到 41 张单是 24 张。

推论：凡是"从创建到现在的时长"这类指标，**必须先问一句终点是什么时候**。

## 4. 分位数门槛：样本不够就写"样本不足"，不能给个数

`MIN_N_FOR_P90 = 5`、`MIN_N_FOR_MEDIAN = 3`。

```python
def _stat(values):
    n = len(values)
    if n == 0:
        return {"n": 0, "median": None, "p90": None}
    return {
        "n": n,
        "median": _median(values) if n >= MIN_N_FOR_MEDIAN else None,
        "p90": _p90(values) if n >= MIN_N_FOR_P90 else None,
    }
```

P90 用最近秩法（`math.ceil(n * 0.9) - 1`），不做线性插值。3 个样本插值从数学上说得出数，从业务上说是在编——**n=1 的 P90 就是把那一条换个名字**。

页面上 `None` 渲染成「样本不足」并带 `title` 说明"需要 n≥5"：

```javascript
function statCell(v, n, need){
  if (v === null || v === undefined)
    return `<span class="text-secondary" title="该分组 n=${n}，需 ≥${need} 才出这个数">样本不足</span>`;
  return fmtH(v);
}
```

**关键细节：不能渲染成横线 `—`。** 横线会被读成"这一格没数据"（就是没有这类工单），而真实含义是"有这类工单，但不够算"。这两种情况对使用者的决策完全相反。

实测：41 张单分组后，`转派 → 转派` 只有 3 个样本、`转派 → 办结` 3 个，这两条边的 P90 都显示「样本不足」。而 `派单 → 接单` 35 个样本，P90=12h 正常出。

## 5. 异常检测用规则，不用模型

题目里提到"异常检测"，最自然的联想是 Isolation Forest。本项目**没有用它**，理由是可解释性，不是技术难度。

当时有 18 张单，喂给 Isolation Forest 的结果只有两种：contamination 设低了全部正常，设高了全部异常。即使调出中间值，输出是一个 `0.87` 的分数和一个不可解释的标签。

而社区工作人员要的不是分数，是**动作**：

> 「这单跨了 2 个单位、转了 3 次、56 天没结，归你督办。」

这句话本身就是一条制度。规则写下来就是管理办法，模型给不出。

所以 `ANOMALY_RULES` 是 5 条明写的规则：

| code | 判据 | 建议 |
|---|---|---|
| `over_sla` | 超 SLA 1 倍 / 3 倍 | 按倍数分档督办 |
| `idle` | 从最后一次动作起 > 7 天无动作 | 联系处理人确认 |
| `long_pending` | 未办结且 > 30 天 | 提级到街道 |
| `transfer` | 转派 ≥ 3 次 | 查是否推诿 |
| `disputed` | 有争议且未裁决 | 送居委会裁决 |

### 5.1 判定函数返回字符串，不返回 bool

第一版每条规则返回 `bool`，结果一张单同时显示「超期 3 倍以上」和「超期 1 倍以上」——两条规则都命中。

改成"由函数内部决定档位，命中就返回说明文字"：

```python
def _hit_over_sla(o, s, t):
    r = s.get("over_ratio")
    if r is None:
        return None
    if r >= 3:  return "超期 3 倍以上"
    if r >= 1:  return "超期 1 倍以上"
    return None
```

**分类问题必须在函数内部互斥，不能靠两条独立规则自己长眼。**

### 5.2 实测命中分布（41 张单）

| 规则 | 命中 |
|---|---|
| `over_sla` | 23 |
| `idle` | 6 |
| `long_pending` | 4 |
| `transfer` | 2 |
| `disputed` | 2 |

去重后异常单 **24 张**。异常榜第一：

> `W20260831-050907-68` · 超期 3 倍以上、转派 3 次、超过 30 天未结、40 天无任何动作 · 超期 56.3 倍

这张单是"6 栋电梯经常卡在 3 楼、有位老人被关在里面二十多分钟"，从 8 月 31 日拖到现在，在幸福里物业 → 广厦物业 → 幸福里社区 → 广厦物业之间转了 3 次。**五项规则同时命中一张单，这张单就是这一轮最该被看到的那一张。**

## 6. 长尾风险：分数是排序工具，不是概率

`app/risk.py` 的权重是**参考经验设定的值，不是训练出来的**：

```
W_REPEAT              18   反复报事
W_CROSS_ORG_TRANSFER  22   跨单位转派（踢皮球的核心）
W_SAME_ORG_TRANSFER    8   同单位转派（交接班，从轻）
W_OVER_SLA            15   超 SLA
W_OVER_SLA_3X         20   超 SLA 3 倍（额外加）
W_LONG_PENDING        25   超 30 天未结
W_REJECTED            20   被居民退回
W_DISPUTED_UNJUDGED   18   有争议未裁决
SCORE_CAP            100
```

因为不是概率，所以**必须能拆开显示**：

```json
{"score": 100, "raw": 112, "capped": true,
 "items": [
   {"name": "跨单位转派", "score": 44, "reason": "在 3 个单位之间转了 3 次"},
   {"name": "长期未结",   "score": 25, "reason": "已 56 天未办结"},
   {"name": "超过 SLA",   "score": 35, "reason": "超出承诺时限 56.3 倍"},
   {"name": "反复报事",   "score": 18, "reason": "同一诉求第 3 次提出"}
 ]}
```

页面上就照这个渲染：`+44 跨单位转派 · 在 3 个单位之间转了 3 次`。封顶时额外显示「原始分 112，已封顶到 100」——**不然使用者会以为 100 就是最高严重度，而实际上它可能远超**。

如果只给一个 100 分和"高危"两个字，社区不敢照着行动：拆不出原因，就不知道从哪一步动手。

### 6.1 跨单位转派才是踢皮球

只数 `transfer` 次数会把维修工请假、交接班也误伤成推诿。

真正的踢皮球特征是**在单位之间换手**。所以 `ping_pong()` 用相邻两次转派的 `actor_org` 变化来判断 `cross_org`：

```
幸福里物业 → 广厦物业 → 幸福里社区 → 广厦物业     cross_org=2（3 次转派里 2 次换了单位）
幸福里物业 维修班 → 王师傅 → 李师傅              cross_org=0（同单位交接班，不是踢皮球）
```

实测：`ping_pong 2 张`，其中 `cross_org 2 张`。41 张单里只有 2 张是真正在单位之间打转的，正是那两张拖了 47 天和 56 天的。

### 6.2 反复投诉从 2 次就报

`repeat_complainants(min_times=2)`。不等 3 次。

理由：一次是偶发，两次就是"上次没解决"。真正的问题在于社区在第二次时还没意识到这是同一个问题——等到第三次才报，中间那次等于白受。

实测：**3 位居民 / 7 条诉求**。榜首那位 3 条诉求都是 3 栋 2 单元 201 卫生间漏水，第一条说"还在漏"，第二条说"涂了防水胶不到一周又开始滴"，第三条说"第三次反映了，昨天家里老人踩到积水滑倒"。

这三条如果分开看是三个工单，合起来看才是"一个修不好的漏水"。

输出里手机号强制脱敏（`138****0001`），回归里专门断言了输出不含明文号。

## 7. 投诉文本：词表给结论，聚类只给候选

### 7.1 词表的三条硬规则

`textmine.TOPICS` 是 18 个主题词表，每一条都是踩过坑之后定的。归纳成三条：

**① 地点词、身份词不能当主题词。**

- 「楼道」「单元门」「小区」说的是**在哪儿**；
- 「老人」「业主」「孩子」说的是**谁**；
- 主题词必须是**问题本身**或**状态词**。

实测代价：词表里有「老人」时，"老人踩到积水滑倒"（漏水）、"老人拎着垃圾走十分钟"（垃圾清运）、"有位老人被关在电梯里"（电梯运行）三条全被吸进「特殊群体」，**热点榜首变成"特殊群体 4 条"，而真正要修的是水管、垃圾桶和电梯**。

改成只用状态词（独居 / 孤寡 / 空巢 / 高龄 / 低保 / 残疾 / 失能）之后，「特殊群体」只剩 1 条——正是那条"10 栋有位独居老人两天没下楼"，这才是真的该关注的人。

**② 宽泛字与常用词不能进词表。**

| 词 | 混进什么 | 命中在哪 |
|---|---|---|
| 卫生 | 房屋漏水 | 「卫**生间**漏水」里的"卫生" |
| 臭 | 垃圾清运 | 「下水道反水，很**臭**」 |
| 邻居 | 邻里纠纷 | 「**邻居**帮忙撬的门」 |
| 单元门 | 门禁对讲 | 「1**单元门**口消防通道停车」 |

**③ 宁可漏，不要错。**

漏掉的还有救——`ngrams()` 会把没命中词表的高频字串列出来，人工一眼能补进词表。错了没有任何机制能发现，而且使用者看到"漏水被归到垃圾清运"就再也不信这个页面了。

### 7.2 实测（25 条诉求）

```
25 条全部命中词表，未命中 0 条
命中 28 次（一条可命中多主题，如"噪音"同时命中「噪音扰民」和「邻里纠纷」）
16 个主题，榜首：房屋漏水 4 条
```

"未命中 0 条"在这份语料上不完全算好消息——词表是照着这批数据调的，属于样本内。真实场景里一定会有未命中的，`unmatched` 字段就是为了让这种情况显性化，而不是静默丢掉。

### 7.3 聚类：纯度 30%，如实标注

`cluster()` 做了：2-gram TF-IDF（`min_docs=2`、`max_df=0.5`）→ 余弦相似度 → 平均链接层次聚类（阈值 0.16）。

实测：

```
n=25  簇数=11  多成员簇=9  特征数=72  纯度=30.4%  质量=低
相似度分布：median=0.000  mean=0.059  p95=0.290  max=0.505（300 对）
```

**`median=0.000` 这个数字比任何措辞都可信：一半以上的诉求两两之间连一个共同字串都没有。**

最大的簇（5 条）簇内高频词是「楼道 / 单元 / 坏了 / 自己」——它没有共同主题，是**被地点词串起来的假簇**。页面上这个簇的标签就是「新主题候选（需人工命名）」，不硬安一个名字。

#### 纯度为什么从 39% 变成 30%

先说清口径：纯度**按成员加权**，分母是"多成员簇的成员总数"，分子是"簇内全体成员主题交集非空"的那部分成员。

严格版定义：

```python
for g in groups:
    if len(g) < 2: continue
    sets = [set(_hit_topics(texts[i])) for i in g]
    tot += len(g)
    if all(sets) and set.intersection(*sets):
        hit += len(g)      # 全体成员共有一个主题，才算纯
```

**宽松版（取簇内最常见主题算占比）在 25 条上给 69.6%，但那是假的**：2 条成员的簇里 1 条命中就给 50%，**随机分组也能刷到接近 50%**。一个随机基线都刷得到的指标没有诊断价值。

严格版第一次实测 **39.1%**（9/23），和人工逐簇核对的结果一致。

然后改了词表（去掉「老人」），**聚类算法一行没改，分数掉到 30.4%（7/23）**。

这是本轮最值得写进论文的一个现象：

> 纯度拿人工词表当标准答案，衡量的是"聚类与词表的一致程度"，不是"聚类绝对正确"。**标准答案一变，分数就变。**

所以：**任何纯度数字都必须连同词表版本一起报。单独说"聚类纯度 30%"是没有意义的。** 代码注释里也改成了这个口径，并写明 39% → 30% 的因果。

#### 也试过、也失败过的调参

`max_df` 自动停用词试了 0.5 / 0.35 / 0.25 三档，**纯度三档都是 39.1%，特征词表完全不变**。

结论：噪声不是"超高频词"（那种 `max_df` 能滤掉），而是**中频地点词**（"楼道""单元""物业说"各出现在四五条里）。这个发现的过程比结果更值得记——它说明"调参能解决"这个直觉在这里是错的。

阈值也扫过：0.30→17 簇、0.22→14、0.16→11、0.12→10、0.08→6。取 0.16。

#### 所以这块怎么定位

接口留着，页面留着，纯度必须显示，措辞是：

> 「以词表结论为准。聚类只用于发现词表没覆盖到的新主题候选。」

**这是这一轮唯一的正确用法**：不是让它给结论，是让它指出"这批诉求里有 5 条聚在一起、但词表认不出它们是什么"——那是词表的下一个补充方向。

## 8. 小区分权：新页面不能绕过 ABAC

`process` / `risk` / `textmine` 三个模块最初都是直接 `WorkOrder.query.all()`。这会让**物业看到全社区的工单**——而工单页明明是收窄的，新页面把收窄绕过去了。

统一走 `policy.scope_query`：

```python
def _visible():
    u = current_user()
    q = policy.scope_query("order", WorkOrder.query, u)
    return process.visible_ids(q)
```

实测（同一份数据、两个账号）：

| | 物业（幸福里） | 社区 |
|---|---|---|
| 流程监控页 | 200，41 张里见 **40** 张 | 200，见 **41** 张 |
| 踢皮球 | **1** 张 | 2 张 |
| 投诉热点 | **403** | 200 |
| 居民画像（反复投诉） | 不返回 | 返回 |

物业少的那张单正是已经推给广厦物业的那张——**"推出去就不管了"，在数据上就是这个样子**。这张单恰好是踢皮球最严重的那张（56 天、3 次转派）。这不是 bug，是这套权限模型在如实反映现实。

投诉热点对物业 403 是**代码硬判**而非配置：`_can_see_topics()` 白名单 `("community", "street", "admin")`。理由是热点背后是居民原话，物业作为被投诉方不该拿全量文本去比对是谁投诉的。即使管理员误把权限勾给物业，这里也会拦住。

## 9. 演示数据：先有样本，才谈统计

流程监控要谈"平均停留 178 小时"，得有 41 张单；风险预警要谈"3 人反复投诉"，得有 25 条诉求。原始演示库只有 18 张单、1 条诉求，**什么统计都做不出来**。

`scripts/seed_risk.py` 造了 24 条诉求，覆盖：

- 三组反复投诉（3 栋漏水 ×3、5 栋消防通道 ×2、7 栋噪音 ×2）
- 两张跨单位踢皮球（6 栋电梯 56 天 3 次转派、2 栋外墙渗水 47 天 2 次转派）
- 四张超 30 天未结
- 15+ 个主题

几个必须守住的约束：

**① 全程走 `orderflow.push(at=...)`，不裸改 `status`。** 裸改状态会让流转日志和历史对不上，`check_integrity` 立刻报"工单状态与流转链末步不一致"。

**② 每条 `hours` 是"距诉求提交多少小时"，不是绝对时刻。** 写绝对时刻，过两天再跑就全落在未来。

**③ 正文里不加任何标记。** 第一版用 `[演示]` 前缀拼进 `raw_text` 做判重，结果 `ngrams()` 榜首变成「演示」——**造数据的痕迹污染了文本分析**，而且演示时一眼看出是编的。改成按 `SEED_HEAD = 20`（正文前 20 字）判重与清理。

**④ 必须真建 `FdeRecord` → `WorkItem`。** `work_order.work_item_id` 有外键约束，传虚构 id 直接 `FOREIGN KEY constraint failed`。

**⑤ 造完要按 `itemstate.stage()` 回写 `ticket.status`。** 否则居民端显示"办理中"而工单已办结。

`--clean` 一键清（按前 20 字匹配，删 WorkOrderLog / WorkOrder / WorkItem / ResidentTicket / FdeRecord）。

## 11. 90 秒演示动线

1. **流程监控台**（`/process`）→ 四张卡：41 张单、13 张卡住、12 张超 SLA、4 张超 30 天
2. 顶部样本提示条：「41 张工单 / 113 条流转日志，分组后多数边 n<5」
3. **瓶颈排行** → 指着「转派 → 转派 178.0 小时 / n=3」：比正常办结慢 4.6 倍，这是"踢皮球"的量化形态；同时指着 P90 那一格说「样本不足」——**主动说这块数据不够，比被问出来强**
4. 切到**流程路径** → 58.5% 的单走标准三步，其余是转派、零接单
5. 切到**卡在哪一环** → 榜首 40 天无动作，转派 3 次
6. 切到**异常清单** → 榜首那张单五项全中、超期 56.3 倍
7. **风险预警台**（`/risk`）→ 高危 7 张，点开榜首看分项拆解：`+44 跨单位转派 · 在 3 个单位之间转了 3 次`
8. 切到**反复投诉** → 3 人，榜首 3 次都是同一个漏水，手机号已脱敏
9. 切到**投诉热点** → 房屋漏水 4 条居首
10. 切到**聚类分析** → 主动说：「纯度 30.4%，偏低，页面已提示以词表为准。聚类只用来发现词表没覆盖的新主题，不拿来下结论」

**第 10 步是这套演示的加分项，不是减分项。** 一个肯说"我这里只有 30%"的人，前面 9 步的数字才可信。

## 12. 这套东西的边界

诚实地写清楚，比答辩被问出来好：

- **样本 41 张单，统计意义有限。** 页面顶部常驻样本量提示条，不藏着。
- **纯度随词表变，不能说"聚类准确率 30%"。** 措辞是"聚类纯度"，且必须附词表版本。
- **2-gram 是字面相似，不是语义。** "楼道堆物"和"楼道灯坏"字面很近但主题完全不同；"消防通道停车"和"下水道反水"仅因都含"物业说"相似度 0.343。
- **风险分是经验权重，不是概率。** 排序可用，概率不可用。
- **异常规则是当前制度的编码，不是客观真理。** 换一套管理办法就得改规则。
- **词表是人工维护的，会漏。** 漏了靠 `ngrams()` 补，`unmatched` 显性化。
