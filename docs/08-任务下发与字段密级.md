## 1. 为什么单独写这一节

毕设最容易翻车的地方，不是功能做得少，而是**设计文档承诺了、代码里没有**。答辩时老师按《总体设计》逐条对照演示，任何一条对不上都是硬伤，而且很难用"时间不够"解释——因为它不属于"没做完"，属于"说法和实现对不上"。

这次盘查发现两处：

| 设计文档里的承诺 | 代码实际情况 | 性质 |
|------|------|------|
| `docs/01` 第 36 行：街道职责含"下发任务"；第 67 行架构图画了"任务看板" | `task` 表 0 行；`/api/tasks` 只有 GET 无 POST；无 `/tasks` 页面；街道登录直接落报表页 | **功能完全未实现** |
| `docs/01` 第六节：字段三级管控（明文/脱敏/加密） | `FieldSecurity` 模型存在，但全项目零写入，表内 0 行；实际只有正则脱敏文本 | **承诺无实现支撑** |

两者都在本轮补齐。

## 2. 任务下发（街道 → 社区 / 物业）

### 2.1 为什么它是必要的，不是"锦上添花"

系统原有的数据流是**自下而上**的：社区录入 → 派单/建档 → 报表上报街道。但真实基层还有一条**自上而下**的流：街道下发专项任务（人口核查、消防排查、年检配合），社区/物业承接并反馈。缺了这条，系统只是个"录入+统计"工具，体现不出"上下级业务关系"。

更关键的是，**督办 Agent 本来就依赖 `task` 表**——它会在 `deadline` 到期时告警。表里没有数据，督办就永远只有工单超时一种告警，功能是"半条腿"。

### 2.2 数据模型

`task` 表在原 5 列基础上补 4 列（启动时幂等 `ALTER TABLE`，旧库可直接升级）：

| 字段 | 说明 |
|------|------|
| `title` | 任务标题（≤100 字） |
| `assignee_role` | 受派角色 `community` / `property` |
| `assignee_org` | 受派组织（幸福里社区 / 幸福里物业） |
| `detail` | 任务说明，交代口径与要求 |
| `deadline` | 截止时间，**督办 Agent 的判据** |
| `status` | `open` / `done` |
| `creator` | 下发人（取会话身份） |
| `closed_at` | 办结时间 |

### 2.3 权限设计：新增两个权限点

| 权限点 | 社区 | 物业 | 街道 | 说明 |
|------|:--:|:--:|:--:|------|
| `task.view` | ✅ | ✅ | ✅ | 三方都有，但**只看得到派给自己的** |
| `task.manage` | ❌ | ❌ | ✅ | 下发 / 关闭 |

设计上有个刻意的取舍：**`task.manage` 是街道唯一的写权限**。

街道在系统里的定位是"监督方，不下场办事"，它不产生业务数据、不改工单状态、不写台账。但"给谁派活、什么时候要"属于管理动作，必须给它。这条边界让"街道能写什么"这个问题有唯一答案，答辩时好解释。

### 2.4 行级隔离

和工单"物业只看本公司"同一套逻辑，不靠前端过滤：

```python
if u.role != "street":
    q = q.filter(Task.assignee_role == u.role)
    if u.org:
        q = q.filter(db.or_(Task.assignee_org == u.org,
                            Task.assignee_org.is_(None),
                            Task.assignee_org == ""))
```

注意 `assignee_role` 过滤是**必须**的：只按组织过滤不够，因为社区工作者与物业可能挂同一社区名。

### 2.5 接口

| 方法 | 路径 | 权限 | 说明 |
|------|------|------|------|
| GET | `/api/tasks` | `task.view` | 按角色过滤的列表 + `summary`（待办/超时/完成）+ `can_manage` |
| POST | `/api/tasks` | `task.manage` | 下发，校验标题非空、角色合法、截止时间晚于当前 |
| POST | `/api/tasks/<id>/done` | `task.view` | 受派方确认完成；街道可代关闭 |

越权访问由 `perm_required` 统一拦截，并写 `audit_log(action=deny)`——街道以外的角色尝试下发，会留下"谁试图下发任务"的记录。

### 2.6 页面

`/tasks` 单页双形态，用 `can('task.manage')` 切换：

- **街道**：左侧下发表单（标题 / 受派角色 / 组织 / 截止时间 / 说明）+ 右侧任务列表，操作为"关闭"
- **社区 / 物业**：无表单，全宽列表，操作为"确认完成"

逾期任务整行浅红底、状态徽章显示"超时 Xh"；24 小时内到期显示橙色"剩 Xh"；顶部有督办告警条，与工单页视觉一致。

### 2.7 演示数据

启动时若 `task` 表为空，写入 4 条（幂等，不覆盖演示中改过的数据）：

1. 10 月人口变动台账补录 → 社区，**已超时 6 小时**（让督办告警一登录就有东西可看）
2. 高层住宅消防通道专项排查 → 社区，5 天后
3. 3 栋电梯年检材料准备 → 物业，2 天后
4. 9 月独居老人走访全覆盖 → 社区，已完成

## 3. 字段三级管控

### 3.1 原先缺的是什么

`security.py` 做的是**文本级脱敏**：拿整段话跑正则，把身份证、手机号替换成掩码。这解决了"原文别泄露"，但没解决三个问题：

1. **不知道哪个字段敏感**：只知道"这段话里有 1 个手机号"，不知道它属于哪条业务项的哪个字段
2. **没有级别**：脱敏和明文在库里没有区分，无法按级别做跨角色裁剪
3. **无法举证**：事后要回答"这条数据里哪些是敏感个人信息"，只能重新跑一遍正则

`field_security` 表就是为这三件事存在的，但一直是空的。

### 3.2 判定规则：字段名 + 字段值双规则

拆解 Agent 输出的是结构化 `fields`（如 `{"楼栋":"3栋","房号":"501室","电话":"13800001234"}`），逐字段判级：

**第一优先：公开键白名单**（命中即 1 级）

```
楼栋 / 楼号 / 小区 / 类型 / 问题 / 事项 / 事由 / 时间
```

> 这一条是被测试逼出来的。最初只按"值里有没有门牌模式"判断，结果 `楼栋="3栋"` 命中 `\d+栋` 被判成 2 级。但《总体设计》里明确把"楼栋号"举为 1 级明文的例子——**楼栋号不等于住址**，不构成对自然人的定位。加了白名单后，值规则也去掉了 `栋`，只保留 `单元 / 室 / 号楼`。

**第二优先：字段名规则**

| 级别 | 匹配键名 |
|:--:|------|
| 3 加密 | 身份证、证件、社保号、银行卡、手机、电话、联系方式、微信 |
| 3 加密 | 健康、病史、病情、血压、血糖、用药、残疾、精神、孕 |
| 2 脱敏 | 姓名、户主、联系人、监护人、住址、地址、门牌、房号、单元 |

**第三优先：字段值兜底**（键名不规范时）

- 18 位身份证正则 → 3 级
- 11 位手机号正则 → 3 级
- `\d+单元 / \d+室 / \d+号楼` → 2 级

字段值规则与 `PATTERNS` 用**同一套正则**，避免出现"脱敏了但判级没判到"的不一致。

### 3.3 落库与展示

`Orchestrator` 在业务项 `flush()` 拿到 id 后立即写入：

```python
sec_fields = self.security.classify_fields(it.get("fields"))
for sf in sec_fields:
    db.session.add(FieldSecurity(work_item_id=wi.id,
                                 field=sf["field"], level=sf["level"]))
```

同时把 `security` 与 `sec_max` 放进接口返回值，首录台的拆解步骤直接显示：

```
2. 报修：3栋2单元楼道灯损坏（→ 物业）  [房号·脱敏 / 电话·加密]
```

`/api/fde/stats` 增加 `secure_count`（level ≥ 2 的字段数），首录台统计卡从原来错用的"审计条数"改成"敏感字段管控(个)"。

### 3.4 一个必须说清的口径：为什么不做 AES 加密

原设计写的是"加密（身份证号 AES 存储）"。实现时改成：**3 级字段在入库前就被替换为不可逆掩码，原文根本不落库**。

理由：

- AES 是**可逆**的，密钥泄露即可还原。不可逆掩码没有这个风险，安全性严格更强
- 系统业务上不需要还原原文（工单、台账、报表都不需要拨打居民电话），可逆性带来的是风险而非收益
- 密钥管理本身是新攻击面：密钥存哪、怎么轮换、备份怎么加密，在单机部署的社区场景里很难做对

因此 `docs/01` 第六节已改为如实描述。若将来确有可逆需求（如社区回访需拨号），再叠加字段级 AES，并在论文里作为"生产增强项"讨论——这是**主动的设计选择**，不是没做完。

## 4. 测试结果

`scripts/smoke_tasks.py`，32 项断言全部通过：

**A. 任务看板（16 项）**

## 5. 对论文的意义

1. **任务下发补上了"自上而下"的业务闭环**，使 FDE（自下而上）与任务派发（自上而下）形成双向流，架构图的完整性不再有缺口。
2. **字段密级把"保密"从一句承诺变成一张可查的表**。论文里可以写："系统对 N 条业务项的 M 个字段完成了密级标注，其中 3 级字段 X 个，全部以不可逆掩码存储"——这是可验证的陈述，而不是"我们做了脱敏"。
3. **"不可逆优于可逆"是一个可讨论的设计判断**。答辩时如果被问"为什么不用加密"，答案不是"没做"，而是"业务不需要还原原文，可逆性只增加风险"。这类有取舍的设计说明比堆功能更加分。

## 6. 附：另外两处"口径漂移"（同批修正）

补齐 A 组缺口时，顺手盘查了"文档写的"与"代码跑的"还有哪些不一致，又找出两处。它们的共同特征是：**功能都在跑，只是跑的口径与承诺不同**，比"完全没做"更难被发现。

### 6.1 报表按周期过滤（原先是"假月报"）

`ReportAgent` 原来统计的是**全表累计值**：`FdeRecord.query.count()`、`WorkItem.query.all()`，只把 `period` 当作标题写进去。后果是 9 月报表与 10 月报表的数字完全一样，街道拿去环比会失真，而界面上看起来一切正常。

修正为按 `period` 的**闭开区间**统计：`created_at >= 月初 and created_at < 次月初`，同时补上上月对照，摘要里直接给"环比 ±X%"。非法周期（如 `bad-input`）回落到当月，不会抛异常。

演示数据实测：9 月首录 17 条 / 业务项 21 个 / 工单 7 件；10 月首录 23 条（环比 +35%）/ 业务项 32 个 / 工单 10 件。两张报表的数字不再相同，环比也有意义了。

> 这条留个教训：**"接口有返回、页面有数字"不等于"统计口径正确"**。报表类功能必须用两个不同周期的数据交叉验证，否则永远发现不了。

### 6.2 工单 SLA 分级（原先一律 24h）

知识库 `data/kb/04-物业报修响应时限与处置规范.md` 明确分三级：紧急（电梯困人、燃气泄漏、水管爆裂、停电）4 小时办结，较急（电梯故障、门禁失效、屋顶漏水）24 小时，一般（楼道灯、下水道、健身器材等）72 小时。

而 `DispatchAgent` 把 `DEFAULT_SLA_HOURS` 硬编码成 24，**系统自己检索出来的规范和系统自己派的单互相矛盾**。更实际的后果是督办误报：楼道灯不亮本该 72 小时，第 25 小时就被报成超时，物业会被无理由追责。

修正为 `classify_sla(content)`：按关键词匹配三级，未命中的按"一般 72h"处理（宁可宽限，不误报）。`work_order` 增加 `sla_level` 列（启动时幂等 ALTER），工单列表直接显示"紧急/较急/一般"徽章。

实测分类：`电梯困人` → 紧急 4h；`电梯异响`、`门禁坏了`、`屋顶漏水` → 较急 24h；`楼道灯不亮`、`垃圾桶满` → 一般 72h。

> 这条的意义在于：**知识库不只是给模型答问用的**。如果 KB 里写了规则而代码不执行，那 KB 就只是装饰。把 SLA 分级做成 `dispatch` 里的规则函数，等于让"规范"真正约束"执行"——这一点在论文里可以作为"知识如何进入流程"的例证。
