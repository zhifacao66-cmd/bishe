## 0. 演示前 5 分钟检查清单

```bat
:: ① 模型在不在（返回 version 才有 GPU 加速）
curl -s http://127.0.0.1:11434/api/version
ollama ps

:: ② 系统健康状况（status 必须是 ok；degraded 表示模型没连上）
curl -s http://127.0.0.1:5000/api/health

:: ③ 居民端与公告（两条都要返回 200）
curl -s -o nul -w "%{http_code}" http://127.0.0.1:5000/portal
curl -s -o nul -w "%{http_code}" http://127.0.0.1:5000/portal/notices

:: ④ 数据是否完整（应为 40+ / 52+ / 17+）
python -c "import sqlite3;c=sqlite3.connect(r'data/community.db');print([c.execute(f'select count(*) from {t}').fetchone()[0] for t in ['fde_record','work_item','work_order','task'])"
```

| 检查项 | 合格标准 | 不合格怎么办 |
|--------|----------|--------------|
| Ollama | `/api/version` 返回 0.40.x | 双击 `scripts\start_ollama.bat`，等 10 秒 |
| 显存 | `ollama ps` 中 qwen3:8b 在列 | 关掉浏览器多余标签/其他占用 GPU 的程序 |
| `/api/health` | `status: ok`，`db.ok: true` | 若 `degraded`，说明模型不可用，演示会退化成规则拆解 |
| 演示数据 | 首录 ≥ 40、工单 ≥ 17 | `python scripts/seed_demo.py --reset`（约 90 秒） |
| 浏览器 | 用无痕窗口，先登录一次 | 避免缓存旧 JS |
| 居民端 | `/portal` 返回 200，能提交 | 若 500，看日志；多半是数据库被占用 |
| 公告 | `data/notices/` 有 3 个文件，`/notices` 列表 ≥3 条已发布 | 没有就 `python scripts/make_notice_demo.py` 后点「扫描目录」 |
| **模型预热** | 「系统状态 → 模型自检」返回 `ok: true` 且耗时 < 3 秒 | 第一次点会慢（4.7 GB 权重进显存，实测冷启动超过托管网关 60 秒上限，前端只看到超时）；再点一次就 1 秒内返回。**开场前必须点这一次** |
| 侧栏状态灯 | 左下角绿点 + "本地大模型运行中" | 若是灰点＝还在探活；若是**红点**说明通道真断了，别硬演，先查隧道 |

> 侧栏那颗灯是**真探活**（`/api/health/llm` 每 20 秒读一次后台探活缓存），
> 不是装饰：模型挂掉它会变红并写"走规则路径"。演示时如果它自己变红，
> 那正好是讲"降级路径"的现成素材——不要假装没看见。

> ⚠️ **不要**在演示库上跑评测脚本（`eval_*.py`），它们会写库把数据搅乱。
> 要跑评测请指定独立库：`set DATABASE_URL=sqlite:///data/tmp.db`。

## 2. 逐段脚本

### 2.1 开场 + 居民入口（1 分钟）

> "社区工作者每天要做的事，本质上是**一次信息采集、多次分发**。居民来反映一件事，
> 里面往往同时有：人口登记要报综治、老人情况要报民政、楼道灯要派物业。
> 过去这段话说一遍，要在 3 个系统里各填一次。
>
> 我这套系统做的事情就是：**你只说一遍，剩下三次由智能体完成**。而且全程本地模型，
> 居民身份证号一个字节都不出内网。"

**切到手机窗口打开 `/portal`（或直接用手机投屏）**：

> "但只做管理者之间的流转，闭环其实是开环的——因为**提诉求的人不在系统里**。
> 所以第四类使用者是居民：不用注册、不用下 App，填手机号就能把问题递进来，
> 系统给一个 6 位查询码，凭码随时查进度。"

点「我要反映问题」，填：

```
2栋2单元202楼道灯坏了半个月，另外老人身份证要办高龄补贴，电话138****1111
```

提交后停在**成功页**，指着查询码：

> "这个码就是他的凭证。为什么不做账号体系？因为辖区里五六十岁的居民占多数，
> 多一步注册就有一批人放弃。而系统这边也不存密码，就没有密码泄露风险。"

### 2.2 首录：说一遍（2 分钟）

固定输入（**建议提前存在记事本里，现场粘贴，不要手打**）：

```
2栋2单元202室新租户赵某，身份证320102199003074512，电话13712345678，
这周搬进来的；他反映楼道声控灯不亮，另外7栋地下室还有群租情况
```

提交后，实测返回（`llm_used: true`，耗时约 1.6 s）：

| # | 类型 | 摘要 | 去向 | 字段密级 |
|:--:|------|------|------|----------|
| 1 | 人口变动 | 2栋2单元202室新租户赵某登记 | 综治 | 单元·L2、房号·L2、姓名·L2、**身份证·L3、电话·L3** |
| 2 | 报修 | 3栋楼道声控灯不亮 | 物业 | 均为 L1 |
| 3 | 隐患排查 | 7栋地下室存在群租情况 | 综治 | 均为 L1 |

产出：**1 张物业工单 + 2 条台账**。

讲解要点（按顺序说，别跳）：

1. **脱敏发生在模型之前**。页面上"身份证320102\*\*\*\*\*\*\*\*4512"——注意是"入库前就已经是掩码"，
   数据库里查不到明文，我用 `docs/06` 的库内明文扫描验证过，**残留 0 处**。
2. **密级是逐字段打的，不是整段打**。同一条业务项里，楼栋是 L1（可以公开），
   姓名 L2（脱敏），身份证 L3（不可逆掩码）。这张表是 `field_security`，可查可审计。
3. **去向决定谁来干**。含"物业"→ 派单；含"综治/民政/卫健"→ 台账；含"街道"→ 上报。
4. **7 类是有限的**，不是让模型自由发挥：报修 / 人口变动 / 走访 / 调解 / 咨询 / 隐患排查 / 其他。
   有限类别才能做统计、才能评测。

> 如果评委问"这是不是写死的规则"：现场打开 `/audit`，筛 `parser`，能看到 `source=llm`；
> 或者看返回里的 `llm_used: true`。再补一句"规则兜底只在模型不可用时生效，两者返回字段不同"。

### 2.3 物业闭环（1.5 分钟）

用 `wuye / 123456` 登录，落地页就是 `/orders`。

- 找刚生成的那张工单：内容只有"3栋楼道声控灯不亮"，**没有姓名、没有电话**——这是最小必要原则。
- 点"接单"→ 状态 `open → doing`，列表里的**处理人**立刻变成"李经理"（不是"幸福里物业"）。
- 点"转派"→ 选 `赵师傅` → 填一句"李经理外出，交接" → 处理人变成赵师傅，
  再点工单号打开**流转记录**：派单 → 李经理接单 → 转派给赵师傅 → 待办结，每一步都有**人和时间**。
- 用 `wuye2 / 123456`（赵师傅）登录，给这张单**提交反馈**"已更换灯具并检查线路" → `done`。
- 强调三点：
  1. **状态机是强校验的**，`open` 直接点完成会被拒绝（可现场演示一次报错）；
  2. **处理人记到人，不记到单位**：一个物业公司好几个维修工，只记"物业办的"
     等于出了事找不到人。换手也不丢——原处理人留在流转记录里，删不掉、改不了；
  3. 完成瞬间，系统自动往台账里补一条"物业工单闭环"记录，**不需要人再填一次**。
- 顺带指一下 SLA 徽章：紧急 4h / 较急 24h / 一般 72h，**分级的依据来自知识库里的
  《物业报修响应时限与处置规范》**，不是拍脑袋定的。
- 如果被问"处理时长怎么算"：`办结时刻 − 接单时刻`，转派不重置接单时间
  （否则换个手 SLA 就自动复活）；老工单没有接单时间时显示"未记录"，不拿 0 冒充。

### 2.5 街道：任务下发 + 月报 + 审计（2 分钟）

## 4. 高频提问与答法

**Q1：为什么不用 GPT-4 / 通义千问 API？效果不是更好吗？**
> 不是效果问题，是**合规红线**。社区数据含身份证、病历、低保信息，走公网 API 就违反了
> 《个人信息保护法》和街道的数据管理规定。这套系统的前提是"数据不出内网"，
> 所以只能在本地 8 GB 显存里做，这也是我论文里"隐私强约束下的可用性边界"那一节的由来。

**Q2：本地 8B 模型能力够吗？**
> 拆解任务不需要通用智能，需要的是**稳定的结构化输出**。我用 JSON Schema 约束解码把
> 数量准确率从 86% 提到 97.7%（+11.7pp），这个提升**比换更大的模型更划算**——
> 消融实验里换模型只带来 3pp 左右。`docs/03` 有完整对比。

**Q3：59.3% 怎么算的？**
> 24 条语料，传统方式要录 24 次记录 + 11 张工单 + 24 条台账 = 59 次动作；
> 系统只要 24 次（每段话说一遍）。35/59 = 59.3%。**这是录入动作的减少，不是工时的减少**，
> 我在 `docs/06` 里明确写了这个边界，不敢说"省了一半时间"。

**Q4：台账 F1 只有 92.3%，为什么不做到 100%？**
> 差的 7.7% 全是**多建**，没有漏建。归因有三类：拆分传导 1.3、跨线重复 2.7、真重复 0。
> 也就是说系统"多做了一点"，而不是"漏了事"——对政务场景来说，多做可人工删，
> 漏做要担责，所以我选择了偏保守的阈值。

**Q5：并发只有 0.62 QPS，这系统能用吗？**
> 一个社区一天几十条首录，0.62 QPS 相当于每小时 2200 条，够用。
> 但如果是全街道 30 个社区同时用，就不够了——所以我把"异步受理 + 任务队列"写进了后续工作，
> 并且用压测数据（`docs/07`）证明了瓶颈在模型而不在框架：框架层 275 QPS，差 440 倍，
> 优化 Flask 没有意义。

**Q6：这和钉钉/企微的表单有什么区别？**
> 表单要求人**先想清楚填哪张表**，也就是"人适配系统"；这套系统是**系统适配人的表达**。
> 而且表单填完是孤立的，这里是拆解 + 分发 + 留痕一条链。

**Q7：知识库为什么不用向量检索？**
> 显存不够。8 GB 已经被 8B 模型占掉 6.7 GB，再加载 bge-m3 就爆了。
> 中文二元组 BM25 在 10 篇文档的规模上 Top-3 命中率够用，且零显存。
> 代码留了 `KB_EMBED_MODEL` 开关，显存宽裕时可以直接切混合检索。

**Q8：怎么保证模型不瞎编政策？**
> 两级约束：① 咨询类事项必须检索知识库，答案要带出处，检索不到就明说"资料里没有"；
> ② 拆解结果是枚举的 7 类 + 固定的字段集，Schema 约束解码不允许自由发挥。

**Q9：这套东西真能落地吗？**
> 能落地的是"半自动"形态：系统负责拆解、分发、台账，人负责确认与处置。
> 我没做全自动闭环，因为政务场景里"谁批的"必须有人负责——这也是我把审计日志做成
> 只追加、且每个 Agent 强制留痕的原因。

**Q10：工作量看起来不大？**
> 代码 4000 行左右，但配套做了 43 条拆解评测集、5 组消融、24 条端到端评测 ×3 次、
> 16 并发压测、15 分钟长稳测试。过程中修掉了 4 个只有压测/评测才能暴露的缺陷
> （事务边界、审计存原文、工单内容未最小化、SLA 与知识库矛盾）。
> 这些在 `docs/07`、`docs/08` 里都有复盘。
