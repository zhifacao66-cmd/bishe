# 16 · 模型通道与线上部署

> 线上演示环境没有 GPU。本文记录"怎么让线上真的在跑大模型"，以及这条链路上
> 踩过的坑、最后的取舍，和一次真实的线上数据库损坏事故复盘。

## 1. 问题：部署成功了，模型却没在跑

系统设计里模型推理全部在本地 Ollama（`qwen3:8b`，RTX 4060 Laptop 8GB）。
但发布沙箱是**没有显卡的无状态 Python 容器**：装不了 Ollama，也放不下 5GB 权重。

于是第一次上线后，`/api/health` 的 `status` 一直是 `degraded`——
数据库正常、页面正常、什么都能点，但每个 Agent 都在走**规则桩**。
这在论文里是"设计好的降级路径"（消融实验的基线配置），
可对一个要演示的系统来说，等于把最核心的部分摘掉了：
老师看到的是"多 Agent 协作"，看不到"大模型"。

## 2. 三条候选路线

| 方案 | 可行性 | 代价 |
|---|---|---|
| WorkBuddy 云服务的免密钥 LLM | ❌ 不可用 | 该通道只给**浏览器直连**（`/.cloud/llm/chat/completions` + publishableKey + Origin 校验），官方文档明确把"从服务端代理调用"列为禁止写法。本项目 6 个 Agent 全在 Python 后端，搬不到前端 |
| 云端 API（DeepSeek / 通义等） | ✅ 可行 | 延迟低、稳定，但要用户备 Key；且**居民数据会离开社区网络**，\"数据不出内网\"这条论证直接失效 |
| 请求回本机 GPU（隧道） | ✅ 采用 | 要装 cloudflared、演示期间本机要开着；隧道地址会变，变了要重发一次 |

选第三条的核心理由不是技术，是**论证自洽**：
系统主张"居民信息不出社区"，如果演示环境为了好看把数据送去云端 API，
那这句话在答辩现场就不成立了。回隧道后，链路是

```
浏览器 → 云上 Flask（无状态）→ 公网隧道 → 本机网关 → Ollama(GPU)
```

推理仍然发生在开发者自己的显卡上，没有任何第三方模型服务参与。
代价是"模型算在云上跑还是本机跑"要讲清楚——这一点写进了系统状态页，
没有藏起来。

## 3. 通道抽象：换通道不改代码

`app/llm/channel.py` 把"推理在哪里"收敛成唯一裁决点，调用方只认
`base_url + token + model`，不关心对面是 localhost 还是公网隧道。

配置优先级（高 → 低）：

1. 环境变量 `LLM_BASE_URL` / `OLLAMA_BASE_URL`、`LLM_MODEL`、`LLM_TOKEN`
   —— 本地开发、评测脚本、压测用，临时指向别的端口不影响别人
2. 项目根 `llm.json` —— **发布副本携带**，线上只能靠它（沙箱没有环境变量注入能力）
3. `config.py` 默认值 —— `http://127.0.0.1:11434`

`llm.json` 按 mtime 缓存：每次请求读盘没必要，改了文件又能立刻生效。

## 4. 网关：不能让 11434 裸奔

Ollama 自身没有任何鉴权。如果直接用 cloudflared 把 11434 映射出去，
任何扫到那个随机域名的人都能：① 白嫖显卡；② 用任意提示词调用模型；
③ 把显存打满，让答辩现场降级。

所以线上连的不是 Ollama，而是 `scripts/llm_gateway.py`：

- 校验 `X-LLM-Token`（`hmac.compare_digest` 定长比较，防时序侧信道），不对就 401；
- 只放行 `/api/chat`、`/api/tags`、`/api/ps`，其余 404；
- 转发时**丢掉**令牌头，凭据只在本机一跳内有效；
- 监听 `127.0.0.1`，只有隧道进程能到它。

令牌首次运行自动生成，写进 `.llm_gateway_token`（本机）与 `llm.json`（线上），
两边一致才能通。

## 5. 两个代理坑（方向相反）

| 目标 | 必须 | 不这么做的后果 |
|---|---|---|
| 本机 `127.0.0.1:11434` | `trust_env = False`（绕开系统代理） | 代理不认识内网地址，回 404 `/api/chat`，模型调用全部失败、**静默降级**，日志只有一句"本地模型不可用: 404" |
| 公网隧道 | `trust_env = True`（走系统代理） | 沙箱多半只能经代理出网，关掉代理就完全连不上 |

所以 `client.py` 维护**两套 Session**，按 host 选。判据是
`channel.is_local_url()`：`127.0.0.1 / localhost / ::1 / 0.0.0.0` 算本机。

## 6. 冷启动与超时

qwen3:8b 从磁盘加载权重到显存约 **5.3 秒**，加上隧道往返，第一次调用实测 7.6～8.8 秒。
`channel.resolve()` 对远程通道强制 `timeout ≥ 90s`（默认 180s）：

```python
if remote:
    timeout = max(int(timeout), 90)
```

不这么兜的话，超时值会被 `LLM_TIMEOUT=60` 限制住，第一次调用必超时 →
降级 → 看起来就像"模型没生效"。这个坑在本地开发时不会暴露，因为权重早就热了。

## 7. 降级不是故障

隧道断开时，`chat()` 抛 `LLMUnavailable`，Agent 捕获后走规则桩，
HTTP 仍然返回 200，只是 `llm_used=false`。

这条语义必须保住，有两个理由：
- 演示现场网络抖动不该让整个系统 500；
- 规则路径本身就是**消融实验的基线**，它不是"残次品"，是对照组。

系统状态页把这件事说得很直白：通道离线时显示"已降级 / 业务请求仍会正常返回"，
不谎报在线。

### 7.1 一次失败 ≠ 不可用（重试）

上线后遇到过真实的一次：网页版问「高龄老人津贴怎么申请」，返回的是降级文案。
查审计表发现——

| 时间 | 结果 |
|---|---|
| 16:11:30 | 降级（原文摘录） |
| 16:12:17 | 同一个问题，正常回答 |

**中间隔 47 秒，同一个问题就好了。** 这不是模型坏了，是瞬态故障：
公网隧道的长连接空闲后被边缘节点回收、容器被托管侧回收后首个请求打空、
模型正在加载权重——这三种在业务上都表现为"这一次没成"。

而当时的实现是**一次失败就直接降级**，用户看到"模型暂不可用"，
会以为整个系统坏了，实际上再点一次就行。所以改成：

```python
attempts = 2 if ch["remote"] else 1
```

只对"对面这次没接住"的错误重试：`connect`、`timeout`、`bad_response`、
`http_502/503/504`。两类不重试：

- **排队超时（queue）**：GPU 已经满载，再塞一次只会让排队的其他人更慢；
- **4xx**：请求本身有问题（令牌错、模型名不存在），重发一百次也一样。

本机通道也不重试：连不上基本是 Ollama 没启动，重试只是白等。

### 7.2 失败必须留下原因

第一版统计只记 `ok / ms`，所以那次降级事后**无法归因**——而且还赶上容器重启，
进程内计数直接清零，`calls` 只剩 1。排障时"知道失败了"和"知道为什么失败"是两件事。

现在每次失败都记 `kind` 与 `detail`：

| kind | 含义 | 处置 |
|---|---|---|
| `connect` | 隧道/模型服务连不上 | 重试即可；持续出现查隧道进程 |
| `timeout` | 推理超时 | 调大 `timeout`，或查显存是否被占满 |
| `http_502/503/504` | 网关层错误 | 隧道抖动，重试 |
| `http_401` | 令牌不对 | 检查 `llm.json` 与网关是否同一令牌 |
| `bad_response` | 返回体不是 chat 结构 | 多为隧道回了自己的错误页 |
| `queue` | 显存排队超限 | GPU 过载，需要降并发或加卡 |

`detail` 截断 200 字，**不含 prompt 与输出正文**——只留异常本身。
`/system` 页把它提到表格上方单独显示，不用在 20 条记录里翻哪次红了。

### 7.3 别让模型被反复卸载

Ollama 默认 `keep_alive=5m`：5 分钟没人问，就把 8B 权重从显存卸掉。
社区场景是"人来了才点一下"的低频使用，间隔往往超过 5 分钟，
于是**几乎每次提问都是冷加载**——要重新读 4.7GB 进卡，既慢又最容易在加载期间超时。

现在请求体固定带 `keep_alive`，默认 `30m`，可用 `LLM_KEEP_ALIVE` 或
`llm.json` 的 `keep_alive` 覆盖。代价是模型常驻约 5.6GB 显存；
8GB 卡上仍有余量，但若同时要跑别的模型，就把它调回 `10m`。

### 7.4 探活超时给太小，会持续误报"降级"

线上容器到公网的链路质量波动很大。同一条隧道实测过两种形态：

| 指标 | 快的时候 | 慢的时候 |
|---|---|---|
| DNS | 2 ms | 247 ms |
| TCP 443 | 423 ms | 8189 ms |
| TLS 握手 | 1084 ms（整次探活） | **9120 ms，且偶发 `Network is unreachable`** |

原来远程探活超时给 6 秒，慢的时候**每次都超时**，健康页于是长期显示"降级"，
而模型推理其实是好的。**探活误报比不报更伤人**——它会让人去修一个不存在的故障。
现在远程探活给 25 秒，本机仍给 3 秒。

### 7.5 僵死槽位：一次网络卡顿能让整个模型通道停摆

这条是本次排查最凶的一个。

现象：网页版知识库问答返回"模型服务暂不可用"，但稍等一会重问又正常；
健康页 `inflight` 一直是 1，`served` 不增长，`calls` 停在 1。

根因：**有一次模型调用卡在网络层，`requests` 的 `timeout` 没兜住它**。
`timeout` 不覆盖 DNS 解析，也不覆盖"中间设备只回 SYN-ACK、不回数据"的半开连接。
于是 `inflight` 永久停在 1，而并发上限也是 1 —— **之后所有请求都在这里排 40 秒队然后降级**。
表现出来就是"模型忽然全挂了"，重启一下又好了，问题被掩盖。

这类故障不能只靠人重启。现在 `LLMGate` 给每个槽位记开始时刻，提供 `reclaim_stale()`：

- `max_hold = 请求超时 + 30s`，超过就认定不是"在推理"而是"卡在网络"；
- 排队超时**之前**先试着回收僵死槽位，能回收就再抢一次；
- 健康检查顺手调用一次（它是唯一一定会被周期调用的入口，不必额外起后台线程）；
- 回收数与当前持有年龄进 `/api/health` 的 `llm.gate`，`/system` 页面上直接能看到"已回收僵死 N"。

僵死请求后来才 `finally` 交还时，用 token 标记避免重复扣减计数——
否则 `inflight` 会被减成负数，下一次并发判断就全乱了。

### 7.6 平台自有变量不能猜语义

排查上面那个问题时，`/api/health/net` 列出容器里带 `proxy` 的变量名，看到两个：

```
SPACE_PROXY_ENDPOINT = 172.30.1.89
X_IDE_AUTH_PROXY     = auth.proxy
```

名字都像代理，于是把它们当 HTTP 代理塞进 `proxies=` 参数——**结果把一个本来能通的直连弄坏了**：
`SPACE_PROXY_ENDPOINT` 的值是个裸内网 IP、没有端口，`requests` 直接报 `ProxyError`。

教训：**平台自有变量只该观察，不该猜语义**。代理只认显式配置
（`LLM_PROXY` 环境变量或 `llm.json` 的 `proxy` 字段），宁可让人手动填，
也不要靠名字相似去自动推断——猜错一次的代价是"把能用的搞坏"，比不猜更糟。

## 8. 观测：怎么证明"真的在跑模型"

探活只证明端口通，不能证明推理发生。所以做了三层：

1. `/api/health` 暴露 `llm.channel`（channel / label / base 掩码 / model / token_set / source / timeout / keep_alive）
   与 `llm.stats`（累计调用、成功、失败、平均耗时、**最近一次失败原因**、最近 20 次记录）；
2. `/api/health/llm-test`（仅管理员）：**真的让模型干一件业务活**——
   把一句报修描述压成工单标题，返回输出原文与耗时；
3. `/system` 页面：把上面两项做成一屏，附"为什么线上是远程通道"的说明。

最近调用只记**耗时与成败**，不记 prompt 与输出正文——那些含居民信息，
进内存日志就是新的泄露面。

**一个必须说清的边界**：`is_available()` 探的是 `/api/tags`，它不触发推理、
也不加载权重。所以"探活通"只证明能连上，**不证明能推理**——模型加载失败、
显存不足、排队超限时它照样返回 `true`。真正的推理状态要看 `stats.fail` 与
`last_error`。这条曾经误导过一次线上排查：健康页显示在线，实际每次调用都降级。

## 9. 事故复盘：线上库损坏（database disk image is malformed）

现象：部署后所有写接口 500，读接口正常；`/api/fde` 0.67 秒就失败（比模型快得多，
说明根本没走到推理）。线上只回了张 500 白页，拿不到任何堆栈。

> **第二次同类事故（更狠的一种）**：持久卷上的库坏了以后，
> `create_app()` 里 `tune_sqlite()` 的 `engine.connect()` 是第一个撞上去的地方，
> 于是进程根本没起来，平台只报"服务没有在指定端口上响应"，
> 分享链接直接打不开——连"打开页面看健康检查"这条路都没有了。
> 处置（坏库自愈 + 降级启动 + `boot_error.log` + 健康页 `boot` 字段）见
> `docs/21-状态可见性与启动韧性.md` 第 2 节。这次事故还有一个副作用：
> 失败的发布会拆掉旧沙箱，而失败当下没有新的访问链接可登记，
> **旧分享域名会短暂失效**；紧接着再发一次即可恢复（发布记录同步失败时，
> 返回结果里会带 `applicationSyncWarning`，按提示重发一次即可）。

### 9.1 先让错误可见

`app/__init__.py` 注册全局异常处理器：把异常类型 + 堆栈尾部 4 行写进 `audit_log`
（`agent=error`，**先脱敏再截断**，与 `BaseAgent._audit` 同一规则），
并且返回 JSON 而不是 HTML 白页。管理员在审计页按 `agent=error` 一筛就能看到。

第一次上线这个能力后立刻拿到真凶：

```
sqlalchemy.exc.DatabaseError: (sqlite3.DatabaseError) database disk image is malformed
| [SQL: INSERT INTO fde_record (raw_text, source, creator, created_at) VALUES (?, ?, ?, ?)]
```

### 9.2 为什么修不了，以及怎么修

托管环境的 `data/` 是**持久卷**：部署只换代码、不换库。也就是说
代码就算是完美的，那个坏掉的 `.db` 文件也还躺在那里。

于是加了两个口子：

- `GET /api/health/db-check`（管理员）：`PRAGMA quick_check` + 每张表行数 + 文件大小。
  只读连接（`mode=ro`），不会因为检查再改坏一次。
- **标记驱动的库重置**（`create_app._maybe_reset_sqlite`）：
  发布副本的 `data/` 里放 `.reset_db`（内容是一个 id），启动时若发现标记且
  尚未执行过，就把 `community.db.seed` 覆盖主库，旧库先备份成 `.bak`。

幂等设计是关键：执行后把 id 写进 `.reset_db.done`，**重复部署不会再重置一遍**。
否则每次发布都会把演示数据冲掉，越修越糟。

重置后 `quick_check: ok`，13 张表行数正常，首录链路恢复（11.8 秒，llm_used=true，
手机号 138****1234 已脱敏，拆出报修 + 人口变动两项）。

### 9.3 根因

持久卷上的 SQLite 在写入途中被强杀（部署重启），WAL 与主库状态不一致。
应用层已有 `busy_timeout=20000` 与 WAL，但这防的是并发写冲突，
防不了**进程被强杀**。这类损坏只能事后检测 + 用快照重建。

## 10. 操作手册

### 10.1 目标端是 ECS（当前主线：本机 + 服务器）

**日常只需要双击根目录那一个 bat：**

```bat
启动模型服务-47.108.235.113.bat              :: 通道 + 推送到服务器，一条命令
启动模型服务-47.108.235.113.bat --no-push    :: 只起通道，不碰服务器
```

它按顺序做四件事，任何一步不满足就停下来把原因说清楚：

1. **确保 Ollama 加载的是 `F:\ollama-models`**。这是最容易翻车的一环：
   开机自启的 Ollama 往往没带 `OLLAMA_MODELS`，去 C 盘默认目录找模型，
   `/api/tags` 返回空列表。现象极具误导性——**Ollama 明明在线、`/api/version` 正常，
   通道却报"验证没通过：接口通了但模型列表为空"**。脚本检测到"在线但模型列表里
   没有 `qwen3:8b`"时，会自动重启 Ollama 并显式指定模型目录，不需要人干预。
2. 起网关 11435（校验 `X-LLM-Token`，不让 11434 裸奔上公网）。
3. 申请 Cloudflare 隧道，先从本机自探 `/api/tags` 拿到模型列表才继续。
4. 调 `ecs_push_llm.py` 把新地址写进 `C:\app\llm.json`，并等服务器把通道点亮。

推送失败**不影响通道本身**：脚本会打印失败原因并继续常驻，网络恢复后单独重跑
`python scripts\ecs_push_llm.py` 即可，不用重启通道。

需要拆开手动执行（排查问题）时，等价的三步是：

```bat
:: 1. 起本机模型（必须带 OLLAMA_MODELS=F:\ollama-models，否则 /api/tags 空）
scripts\start_ollama.bat

:: 2. 起模型通道（网关 11435 + 隧道，建成后自动写 llm.publish.json）
python scripts\start_llm_channel.py

:: 3. 把新隧道地址推到服务器（关键一步，见下）
python scripts\ecs_push_llm.py

:: 4. 验证（可选，真实调一次模型）
::    POST /api/health/llm-test，需 user.manage 权限
```

**为什么第 3 步不能省**：`ecs_deploy_code.py` 的 `KEEP_REMOTE` 明确保护
`C:\app\llm.json`——那是服务器侧运行环境，不该被代码更新顺带覆盖。代价是
**隧道地址每次重建都变**，而没有任何机制会自动通知服务器。旧地址失效后的表现
极具误导性：接口全 200、业务不报错，只是拆解质量退回规则桩，状态灯变红。
所以补了 `scripts/ecs_push_llm.py`：

```bat
python scripts\ecs_push_llm.py                      :: 推送 + 核验
python scripts\ecs_push_llm.py --show               :: 只读比对两端 base_url
python scripts\ecs_push_llm.py --rollback --stamp 20261023150333
```

它的三条硬性约束，都来自踩过的坑：

1. **不通就不推**。写之前先从本机打一次隧道的 `/api/tags`，拿到模型列表才动手；
   拿不到就拒绝并保留旧地址。宁可线上继续指向一个刚死的地址（至少可回滚），
   也不写进一个自己都没验证过的地址。
2. **一次调用只建两个连接**。链路 22 端口约 50% 成功率、连续快速重连会被拒，
   所以文件先 scp 到 `_llm_new.json`，再由一个 ASCII+CRLF 的 `.bat` 做
   备份 → 原子替换 → 清理。中途断掉最坏结果只是留下一个临时文件，
   `llm.json` 不会变成半个 JSON。
3. **不重启应用**。`app/llm/channel.py` 按 mtime 缓存 `llm.json`，
   换文件即生效，省掉一次停服窗口。

实测（2026-10-23 15:03）：推完 `/api/health` 由 `degraded` 变 `ok`，
`POST /api/health/llm-test` 返回「3栋2单元声控灯故障」，
模型侧 5995ms、含隧道往返 6.1s。

> 注意：通道与业务数据是**两条独立的线**。业务数据就在服务器的
> `data\community.db` 里，服务器自己就是数据源，**不需要任何同步**；
> 只有推理要回到本机 GPU。把"实时数据互通"理解成"两边要互相同步数据"
> 是方向性误解，会引出一堆多余的转发服务。

## 11. 局限

- **quick tunnel 无可用性承诺**：Cloudflare 明确说 account-less tunnel 不保证 uptime，
  域名每次重建都变。真要长稳，应该用具名隧道（需 Cloudflare 账号）或内网穿透服务。
- **单点**：本机断电/休眠 = 线上降级。演示前必须确认 Ollama 与隧道窗口都活着。
- **进程内信号量**：`gate` 的限流只在单进程成立，多 worker 部署要换 Redis 令牌桶
  （与 `docs/07` 同一处局限）。
- 隧道地址出现在配置里，虽然做了一截掩码，但它不是密钥——真正的门是网关令牌。

## 12. 可写进论文的点

1. **部署形态 A/B**：本地全栈（答辩机）vs 云上应用 + 本机推理。后者说明
   "应用可以上云，数据仍不必上云"，是对"社区内网部署"要求的一种折中实现。
2. **降级是有意设计**：模型不可用 → 规则引擎，服务可用性优先。规则路径同时是
   消融基线，两种身份合一。
3. **可观测性作为论据**：`channel` + `stats` + 自检接口让"是否真的用了大模型"
   成为可验证的事实，而不是一句声称。
4. **故障复盘**：持久卷 + SQLite + 强杀导致的库损坏，以及"标记驱动 + 幂等"的修复，
   是工程性很强的一节。
5. **失败可归因**：把"模型不可用"这一句话拆成 `connect / timeout / http_5xx / queue /
   bad_response` 五类，并各自给出处置方式。**同样是降级，原因不同、修法完全不同**，
   这一层细分让"可用性"从布尔值变成一个可运维的对象。
6. **资源占位必须能自愈**：一次卡在网络层的调用占住唯一并发槽位，表现为"模型全挂"。
   给槽位加持有年龄与回收，是把"重启一下就好了"变成"它自己会好"。
