# 12 · 用户与权限管理（账号治理）

前 11 篇讲的是"业务怎么办"，这一篇讲"谁有资格办"。

系统最初只有 3 个写死的演示账号，权限由角色全权决定。这对答辩够用，但对真实社区不够：
社区工作者是流动岗位，新人到岗时管理员往往不在场。如果只能由管理员建号，
实际结果就是**共用老账号**——审计里全是同一个名字，出了问题反而说不清是谁办的。

所以补了一条完整的账号生命周期：**自助注册 → 管理员审核 → 按岗位授权 → 变更 / 停用**。

---

## 1. 三级权限来源

权限不再由角色单独决定，而是三级，优先级从高到低：

| 优先级 | 条件 | 结果 | 用途 |
|---|---|---|---|
| 1 | `role == "admin"` | 全部 18 项 | 管理员不可被降权，防自锁 |
| 2 | `status != "active"` | 无任何权限 | 待审核 / 已停用 |
| 3 | `perms_json` 非 NULL | 以勾选为准 | **按人授权**，这是本期的核心 |
| 4 | 其余 | `ROLE_PERMS[role]` | 角色给默认值 |

全部收敛在 `app/auth.py: user_perms()` 一个函数里。集中算的好处是
不会出现"页面按 A 口径显示、接口按 B 口径校验"的错位——这类错位在权限系统里最难查，
因为单看每一处都"逻辑正确"。

### 为什么保留角色这一层

完全可以只做"按人授权"，但那就退化成每加一个人都要点 16 个勾。
角色提供的价值是**默认值**：新到岗的社区工作者，99% 的场景就是社区那一套权限，
管理员点一次「通过审核并授权」即可；只有这个人需要特殊范围时才去精调。

### `perms_json` 的 NULL 与 `[]` 必须分开

这是整套设计里最容易写错的一处，单独强调：

| 值 | 含义 | 场景 |
|---|---|---|
| `NULL` | 从没单独配过，**跟随角色** | 老账号升级后、管理员点「恢复跟随角色」 |
| `"[]"` | 管理员明确**一个都不给** | 新注册待授权、被收权但账号保留 |

如果代码写成 `if user.perms_json:`，`"[]"` 是**真值**（非空字符串）所以没问题；
但如果写成 `if not user.perms_json or json.loads(...) == []` 之类，就会把
"明确不给"误判成"跟随角色"——**管理员点了「清空」，结果用户拿到了全套权限**。
这是反向授权，比漏授权严重得多。所以判断只用 `is not None`。

代码位置：`app/auth.py: user_perms()`，注释里写明了这条。

## 2. 账号生命周期

```
新同事自助注册（/register）
        ↓  落库即：社区工作者 · 待审核 · 权限 "[]"（一个字的事都办不了）
   待审核页 /pending（每 10 秒自查一次，通过后自动进入系统）
        ↓  管理员在「用户与权限」核对身份
   审核通过 + 勾选权限（可以沿用角色默认，也可以只给两三项）
        ↓  状态转 active，权限从这一刻实时生效
   正常使用
        ↓
   变更角色 / 增减权限 / 重置密码 / 停用
```

### 注册页面的校验

| 项 | 规则 | 原因 |
|---|---|---|
| 账号名 | 字母开头，3~20 位，字母数字下划线 | 便于口述给同事，也能直接进 URL 与日志 |
| 密码 | 至少 8 位 | 账号背后挂着居民信息，6 位密码在离线爆破面前约等于没有 |
| 姓名 / 单位 | 必填 | 管理员要靠这两项核对身份，否则审核变成点一下走形式 |
| 重名 | 拒绝 | 会在登录处产生歧义 |

注册成功即建立登录态，直接落到待审核页——否则新人会反复试登录，
看到的却始终是"用户名或密码错误"，以为没注册成功。

### 两条建号通道

自助注册把角色写死成 `community`，因为那张表是给社区新同事填的。但**街道（上级单位）
和物业不会坐在社区办公室里点注册链接**，他们的账号只能由管理员建。所以系统有两条通道：

| 通道 | 谁用 | 角色 | 初始状态 | 谁授权 |
|---|---|---|---|---|
| 自助注册 `/register` | 社区新同事 | 固定 `community` | `pending` | 管理员审核时勾 |
| 管理员直建 `POST /api/admin/users` | 上级单位、物业、管理员 | 管理员选 | 直接 `active` | 建号时一并勾 |

管理员直建跳过审核队列，因为**建号这个动作本身就是审核**——管理员是照着人事通知
或来函建的，没有第二个人需要再看一遍。两条通道合起来覆盖同一个原则：
**权限由管理员授予，不由注册者自己声明。**

> 早先只有自助注册一条通道，结果是管理员想加一个街道账号只能改数据库，
> 等于把权限体系交给 DBA。这是本轮补上的缺口。

### 待审核与停用的拦截

`has_perm()` 已经把这类账号的权限清空，但仅靠它会让人到处撞 403，
看起来像系统坏了。`app/auth.py: enforce_account_status()` 用 `before_request`
统一处理：页面请求重定向到 `/pending`，API 请求返 403 JSON。
放行白名单只有四项：待审核页、注册页、`/api/admin/me`、登出。

> **踩过的坑**：`/api/admin/me` 最初不在白名单里，结果待审核页的轮询永远收到 403，
> 管理员点了「通过审核」本人也永远不会知道——功能看起来"实现了"，实际断在最后一环。
> 放行它是必须的：这页要查的就是"我通过了没有"。

## 3. 管理员端：用户与权限

入口在侧边栏「管理 → 用户与权限」，只有 `user.manage` 能进。

### 列表页

四个统计（总数 / 待审核 / 正常 / 已停用）+ 按状态筛选 + 每行显示
「权限 N 项（跟随角色 / 已自定义 / 全权）」。

`status=active` 但 0 权限的账号会标一个橙色「未授权」徽标——
这种状态最容易出事：人能登录、页面全空，本人以为是系统坏了，管理员以为已经配好了。

### 新建账号

列表页下方是一张可折叠的「新建账号」卡片：账号 / 姓名 / 单位 / 角色 / 初始密码 / 电话，
加一组按业务分堆的权限复选框。

前端的一处细小设计：**切换角色会自动预选该角色的默认权限**，
管理员在此基础上增减即可，不用对着 18 个框从零点到第 11 个。

提交时前端做一次比较：勾选集合与角色默认完全一致就发 `perms: null`，
库里记成「跟随角色」；一旦有增减就发数组，记成「已自定义」。
这样列表页那一列副标题（跟随角色 / 已自定义）始终说的实话，
不会出现"明明是按角色走的，却显示已自定义"这种让人不敢动的状态。

### 详情页

左侧基本信息（姓名、单位、角色、审核备注），右侧状态与安全（审核 / 停用 / 恢复 / 重置密码），
下方权限点按业务线分五组：事项录入与档案、工单与任务、报表与监督、知识库与公告、账号治理。

平铺 16 个复选框没人看得懂，按"他到底要办哪类事"分堆才选得动。

打开页面时权限框的初始状态分三种，必须由后端算：

| 账号状态 | 初始勾选 | 可编辑 |
|---|---|---|
| 管理员 | 全量 18 项 | ❌ 不可改 |
| 待审核 | 按角色默认预勾 | ✅ 可改 |
| 正常 / 停用 | 如实反映（跟随角色或已自定义） | ✅ 可改 |

待审核账号库里存的是 `"[]"`，那是"还没授权"的占位，不是"管理员决定不给"。
照实渲染的话，管理员要通过一个社区工作者得手点 11 下——这种设计一定会被绕过，
最后变成"反正都是全选，不如不看"。

## 4. 三条防自锁规则

账号系统最典型的翻车不是被攻破，而是管理员误操作把自己降级或停用，
之后**没人能再进后台**。以下三种操作一律 400 拒绝：

1. 停用自己
2. 取消自己的管理员角色
3. 让系统失去最后一个可用的管理员（例如只持有 `user.manage` 的人去停用唯一 admin）

第 3 条的正确性依赖"操作者可能是别人"：管理员 A 停用管理员 B 是允许的（A 还在），
但被单独授予 `user.manage` 的普通账号去停用唯一 admin 必须拦住。

另外 `user_perms()` 里管理员恒定返回 `set(PERMS)`，即使 `perms_json` 被误写成 `[]`
也不会真的失去权限——这是最后一道保险，因为它连"改错了"这种情况都兜住。

## 5. 权限为什么实时生效

权限**不写进 session**。session 里只有 `uid` 和 `role`，每个请求由 `user_perms()`
从数据库现算。代价是每请求多一次主键查询（已命中内存），收益是：

- 管理员点保存 → 对方下一次点击就按新权限判断，不用重启、不用重新登录
- 停用某人 → 对方的会话立刻失效，不用等 session 过期
- 改角色 → 不用把所有人踢下线

答辩时这一点可以直接演示：左边管理员取消勾选，右边账号刷新页面就变了。

> 反过来说，`session["role"]` 这个字段其实是冗余的（只用于登录瞬间的落地页判断）。
> 权限判断一律走 `u.role`（数据库值），不读 session——否则改完角色要等重新登录才生效。

## 6. 接口清单

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET/POST | `/register` | 公开 | 自助注册 |
| GET | `/pending` | 登录 | 待审核落地页 |
| GET | `/admin/users` | `user.manage` | 账号列表（支持 `?status=`） |
| GET | `/admin/users/<id>` | `user.manage` | 详情与授权 |
| GET | `/api/admin/me` | 登录 | 自查状态与权限（轮询用） |
| GET | `/api/admin/users` | `user.manage` | 列表 JSON |
| POST | `/api/admin/users` | `user.manage` | **新建账号**（选角色，建完即可登录） |
| GET | `/api/admin/users/<id>` | `user.manage` | 详情 JSON |
| POST | `/api/admin/users/<id>` | `user.manage` | 更新字段 |
| POST | `/api/admin/users/<id>/approve` | `user.manage` | 审核通过并授权 |
| POST | `/api/admin/users/<id>/password` | `user.manage` | 重置密码 |
| GET | `/api/admin/perms` | `user.manage` | 权限点字典 |

更新接口的 `perms` 字段有三种语义，用「键是否存在」区分：

```json
{"perms": ["order.view"]}   // 设置为这一组
{"perms": null}             // 恢复「跟随角色默认」
{}                          // 不传 = 不动权限
```

未知权限点会被静默过滤（防止前端传错值导致越权或报错），
过滤后为空即 `"[]"`。

## 7. 数据模型

`user` 表新增 6 列，全部用 `ALTER TABLE ADD COLUMN` 幂等补齐（不引入 Alembic）：

| 列 | 用途 |
|---|---|
| `status` | `pending` / `active` / `disabled` |
| `perms_json` | 用户级权限点，`NULL` 表示跟随角色 |
| `phone` | 仅管理员核实用，不对外展示 |
| `created_by` | 「自助注册」/「系统初始化」/ 管理员操作 |
| `review_note` | 审核备注 |

> **踩过的坑**：新增 `status` 列时，老账号该列是 `NULL`。如果代码写
> `if user.status != "active": 无权限`，所有老账号会瞬间变成"零权限"——
> 系统看起来还在，但谁都进不去业务页面。
> 所以建列的同一条升级语句里必须顺手 `UPDATE user SET status='active' WHERE status IS NULL`，
> 把补列和补值一次做完，不留中间态。

## 8. 测试

```bash
python scripts/smoke_admin.py      # 71 项
```

| 分组 | 关键用例 | 项数 |
|---|---|---|
| 管理员账号 | admin 初始化；独立密码登录；公用 123456 登录必须失败 | 8 |
| 越权保护 | 社区访问用户管理 403 且写 deny 审计；未登录 401 | 4 |
| 自助注册 | 落库即待审核 + 零权限；业务页被引到 /pending；弱密码/非法账号名/重名被拒 | 12 |
| 审核授权 | 按勾选授予 2 项；本人自查即时变 active；无权限接口 403 | 11 |
| 权限增减 | 收回即时失效；恢复跟随角色得 11 项；可单独授予 `user.manage`；未知权限点被过滤 | 9 |
| 角色与停用 | 改角色生效；停用后无法登录；恢复不自动放权 | 8 |
| 防自锁 | 不能停用/降级自己；不能停掉唯一 admin；两个管理员时可停一个 | 8 |
| 重置密码 | 过短被拒；成功并写审计 | 3 |
| 老账号兼容 | `perms_json` 为 NULL 时仍跟随角色 11 项 | 3 |

全套回归（含既有 6 套）：**286 项全过**。

> **测试陷阱**：`GET /api/fde` 只接受 POST，写"断言它不等于 403"会**永远通过**——
> 405 也不等于 403。这类断言的失败方式是"假绿"，比红更危险。
> 换用 `/api/ledgers`（有 GET）才测到真东西。同理，`"已停用" in html` 也踩过一次：
> 实际文案是"账号已被**停**用"，四个字中间多一个"被"，断言直接为假。

## 9. 仍然存在的边界

| 项 | 现状 | 生产应做 |
|---|---|---|
| 身份核验 | 管理员人工核对姓名与单位 | 接街道通讯录 / 政务钉钉组织架构同步 |
| 注册防刷 | 无限流 | 短信验证码 + 单位邮箱后缀白名单 |
| 密码找回 | 无（只能管理员重置） | 短信找回，或首次登录强制改密 |
| 权限变更通知 | 无 | 变更后给本人发站内信 / 短信 |
| 操作二次确认 | 仅前端 confirm | 高危操作（停用、授 `user.manage`）需重新输入密码 |
| 审计查看 | 街道与管理员的「审计日志」 | 按账号维度筛「这个人做过什么」，便于离职审计 |

这些不影响答辩演示，但被问到"这套东西真上线还缺什么"时，照这张表答比说"都做完了"更可信。
