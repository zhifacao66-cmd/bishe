# 17 · 严谨性加固：以使用者身份审一遍系统

> 这一轮不是加功能，而是**把"用了会得到错结果"的地方一个个挑出来修掉**。  
> 评审方法、发现清单、修法、以及**明确没修的部分**都记在下面——没修的那几条  
> 比修了的更能说明系统的边界在哪。



---

## 1. 为什么要这样审

功能测试证明"按钮点得动"，但使用者真正会踩的是另一类问题：

- 同一个按钮点两次，数据变成了两条（或时间戳被改写）；
- 输入一个不该接受的参数，页面回 500 白页；
- 数据一多就找不到：106 条台账只能靠上下翻；
- 提示说"已发布"，其实什么都没发生。

所以这轮不看功能清单，只看**边界与非法路径**：空值、超长、类型错、重复提交、  
状态回退、不存在的 id、越权、跨站、分页边界。

工具是 `scripts/audit_probe.py`（体检，会打真实请求并汇总问题），  
回归是 `scripts/smoke_rigor.py`（61 项，把修好的行为锁死）。

```bash
python scripts/audit_probe.py    # 体检：找问题，结果写 data/audit_probe_result.json
python scripts/smoke_rigor.py    # 回归：61 项断言
```

体检脚本故意不追求"全绿"，它的价值是**列出问题**。第一次跑出来 6 条，  
逐条核实后发现 2 条是我自己误判（把 HTTP 200 当成功，本项目业务失败也是 200+code=1；  
另一条是居民按 id 直取，其实那条正好是本次会话自己提交的），其余都真实存在。

## 2. 发现与修复

### 2.1 严重：同一个月的报表堆了 15 份

**现象**：报表列表里 2026-10 出现 15 次，每份都有一个独立的 `report_id`，  
导出件也各带一个编号。

**根因**：`ReportAgent` 生成时直接 `db.session.add(Report(...))`，不查重。  
这本来没什么——报表是快照，多生成一份似乎无害。但报表在本系统里是**归档件**  
（报街道、导出 Excel、论文里"闭环率"的证据来源），归档件一旦一期多份，  
数字互相矛盾时就没有权威版本，"证据"这个属性直接失效。

**修法**：

1. 加 `Report.version`，`(period, line)` 只保留一条，重新生成 = 覆盖 + 版本 +1；
2. 数据库层加 `UNIQUE INDEX ux_report_period_line`（应用层判断挡不住并发两连击）；
3. 老库重复行用 `scripts/_dedupe_reports.py` 收拾（保留 id 最小那条，内容取最新，  
   `version` 记为原组条数，全程写审计）——**不放在启动路径上**，启动时删数据太危险；
4. 前端点"生成"若命中已有报表，明确提示"已重新生成为第 N 版（覆盖原快照）"，  
   否则用户以为"又多了一份"。

**为什么不是"保留历史版本"**：留一堆快照就得回答"哪份算数"。要追溯就靠  
`version` + `audit_log`（每次生成都有记录），而不是留一堆互相矛盾的 JSON。

### 2.2 严重：重复点"发布"会改写发稿时间

**现象**：`publish()` 无条件 `n.published_at = datetime.now()`。

对已经发布的文件再点一次发布（手滑、网络慢重复提交都算），发稿时间就被刷成"刚刚"，  
于是上个月的文件顶到居民端列表最前面——**居民以为刚发的**。发稿时间在这里是证据，  
不能被误触改写。

**修法**：已发布就直接返回 `已于 YYYY-MM-DD HH:MM 发布，无需重复操作`，不动时间戳。  
下架同理，重复下架明确说"已处于下架状态"，不再重复写审计。

### 2.3 高：首录传错类型 → 500

**现象**：`{"raw_text": 12345}` 直接 `AttributeError: 'int' object has no attribute 'strip'`，  
被全局处理器兜成 500「服务内部错误」。

**修法**：先判类型再判内容，顺带补齐三条本来就该有的校验：

| 校验                              | 为什么                    |
| ------------------------------- | ---------------------- |
| 非字符串 → 明确提示                     | 参数错不是服务错，回 500 会让人去查日志 |
| ≥5 字                            | "灯坏了"这种拆不出业务项          |
| ≤2000 字                         | 与居民端一致；再长超出单次拆解的有效上下文  |
| `source ∈ {text, voice, image}` | 枚举外的值会让报表多出一类"幽灵来源"    |

### 2.4 高：任务可以发给不存在的单位

**现象**：`assignee_org` 是自由文本，填"幸福里社区服务中心"（实际叫"幸福里社区"）  
照样能下发。而任务列表按 `org` 做行级隔离，于是这条任务**谁都看不到**，  
成了没人认领的孤儿——街道以为发了，社区以为没收到。

**修法**：下发时用同角色账号的 `org` 集合校验；填错直接拒绝并列出可选值。  
留空仍表示"广播给该角色全部单位"（这条语义保留）。

### 2.5 中：接口层回 HTML 404，前端直接崩

**现象**：`GET /api/orders/abc/accept` 回 Flask 默认 HTML 404 页。  
前端 `const j = await res.json()` 抛 SyntaxError，控制台一片红，页面停在"加载中…"。

**修法**：`/api/*` 的 404 / 405 统一回 `{code, msg, data}`；页面路由的 404 保持原样（不受影响）。  
提示语也写成人话：`接口不存在：/api/xxx`、`该接口不支持 POST 方法`。

### 2.6 中：写接口没有跨站防护

`SESSION_COOKIE_SAMESITE=Lax` 只保护**带 cookie** 的请求；`/api/portal/report`  
连登录都不需要，跨站表单可以直接代居民提交。

**修法**：`before_request` 检查 `Sec-Fetch-Site`，`cross-site` 的写请求一律 403。

**为什么不用 Origin/Host 比对**：线上前面还有一层托管网关，Host 可能被改写，  
一比就会把正常请求全判成跨站——线上直接瘫痪。`Sec-Fetch-Site` 由浏览器声明来源关系，  
不依赖任何代理配置。没有这个头的是 curl / 压测 / 服务端调用，不属于 CSRF 场景，放行；  
老浏览器不发这个头，靠 SameSite 兜底。

### 2.7 中：`size=0` 被夹成 1 条

**现象**：`?size=0` 返回 1 条，看着像"筛出来只有一条"。

`max(1, min(v, cap))` 把"没填"和"填错"都夹成了 1。**数字静默出错比报错难查**，  
这是本项目的老毛病（见 docs/14 布尔求和）。

**修法**：非正值一律回默认值，只有超过上限才夹。`size=0` 与不传等价。

### 2.8 中：数据一多就找不到（使用体验上的"不严谨"）

台账 106 条、工单 62 条时，"找 3 号楼电梯那单"只能上下翻。原来：

- 台账：只有业务线筛选，`limit` 截断后剩下的看不到；
- 工单：只有状态卡片，列表固定最近 50 条，`truncated` 只提示"还有更多"却没入口。

**修法**（前后端都改）：

| 能力      | 工单                 | 台账            |
| ------- | ------------------ | ------------- |
| 关键词搜索   | 工单号 / 内容 / 单位      | 事项 / 门牌 / 工单号 |
| 状态筛选    | 待接单 / 处理中 / 已完成    | 业务线（原有）       |
| 分页      | 上/下一页，`page/pages` | 上/下一页         |
| 状态放 URL | ✅ `replaceState`   | ✅             |

**口径必须守住**：筛选只改 `matched`，不改 `total/open/doing/done/overdue`——  
卡片上一律是"整本账有多少"。这条在 docs/14 里已经踩过一次，这次搜索/分页  
复用同一个 `base` 查询，测试里也专门断言了"筛选不改家底"。

### 2.9 搜索为什么是 `LIKE` 而不是 FTS5（有实测，不是"懒得做"）

台账搜索一直是 `LIKE '%kw%'`。这个选择最开始只是"能用"，后来按"会不会被问住"
的标准补了证据（`scripts/bench_ledger_search.py`，可复跑）：

| 方案 | 1 万条 `count` | 命中「电梯」 | 索引体积 | 2 字词查询 |
| --- | --- | --- | --- | --- |
| `LIKE '%kw%'` | **3.3 ms** | **824 条** | 0 | ✅ 正常 |
| FTS5 `unicode61`（默认） | 0.01 ms | **0 条（漏检 824）** | 8.8 MB | ⚠️ 不报错但恒为 0（整句一个 token） |
| FTS5 `trigram` | 0.06 ms | **0 条（漏检 824）** | **10.6 MB（正文的 5.7 倍）** | ❌ 静默 0 条（需 ≥3 字符） |

四条结论：

1. **FTS5 默认分词器对中文是坏的**。unicode61 按空白/标点切分，一整句
   "3号楼2单元电梯运行异响"变成**一个 token**，搜"电梯"命中 0——不是慢，是漏，
   而且漏得没有任何提示。换任何字段都一样：实测四个查询词，命中 0/4。
2. **trigram 能匹配中文子串，但 2 字词静默失效**。trigram 要求 ≥3 字符，
   搜"电梯""渗水"返回 0 条、不报错；用户只会以为"库里没这件事"。
   而 2 字词恰恰是中文里最常用的检索词。
3. **要让 FTS5 真支持中文，只能引第三方分词器**（jieba 之类）或自建词典切分。
   那才是真的破坏"零依赖、可整包搬移"——本项目连 docx/xlsx 都是自己拼 OOXML，
   不是为了炫技，是为了发布沙箱装没装包不可控。
4. **LIKE 的成本在这个量级完全够**：1 万条 count 3.3 ms、5 万条 17.8 ms、
   取页 0.1 ms 量级。线性外推，撞到人眼可感知的 100 ms 要约 28 万条台账——
   一个街道社区永远到不了。

**但"用 LIKE"这件事本身也踩了两个坑，一并修了**：

- **通配符没转义**。`%` 和 `_` 是 LIKE 元字符。用户搜 `%` 时拼出 `LIKE '%%%'`，
  拿到的是**全表**；有结果、有分页、看不出异常。现在统一转义 `\ % _` 并
  `escape='\'`（`app/search.py:pattern`）。
- **搜的是 JSON 键名**。台账的 `content_json` 序列化后带 `room_key`、`type`、
  `source` 这些键，于是**搜一个下划线就能命中整本台账**（那个下划线来自键名
  `room_key`），跟居民写的内容毫无关系。修法是新增 `Ledger.search_text`：只拼**叶子值**的
  纯文本，由 ORM 的 `before_insert/before_update` 事件自动维护
  （`app/models.py:_sync_ledger_search_text`）——放调用方迟早漏一处，
  而漏掉的表现是"这条搜不到"，最难发现的那种。老库由
  `_backfill_ledger_search_text()` 一次性回填，查询侧再用
  `coalesce(search_text, content_json)` 兜住没回填到的行（宁可假命中，不可搜不到）。
- 顺带补了**多词 AND**：`"电梯 3号楼"` 原来拼成一个长串必然 0 条，像"搜索坏了"；
  现在按空白（含全角空格）切词、逐词都要命中，最多 4 个词。

还有一处**必须做**的收尾：`search_text` 是 content 的第二份拷贝，所以按审计日志
同等的规则脱敏后再落库（`mask_sensitive`），否则等于绕开脱敏在库里多存一份
手机号/身份证明文。代价是按号码搜台账搜不到——台账本来也不该按号码检索。

为什么这不算"加固"而算"把取舍做完整"：**选 LIKE 不是省事，是选了另一条必须
自己承担细节的路**（转义、键名、多词、脱敏、回填），这些都做完了，"够用"才成立。

回归：`scripts/smoke_search.py`（48 项）锁语义——通配符当字面量、键名不参与、
2 字中文词能搜到、多词是 AND、不改家底、老库兜底、脱敏不落明文。

## 5. 给后续开发的检查表

新加一个写接口时，按这个顺序自查：

1. **入参类型**：`request.get_json()` 回来的是任意 JSON，数字/对象/`None` 都可能；  
   `(data.get("x") or "").strip()` 对数字会 500。
2. **长度上限**：文本字段必须有上限，否则超长输入会一路进模型/进库。
3. **枚举值**：角色、状态、来源这类字段必须校验，否则统计口径里会多出幽灵分类。
4. **状态机**：非法流转要拒绝（open 不能直接 done），重复操作要么幂等要么明确拒绝。
5. **归属校验**：按 id 取资源的写接口必须校验归属（IDOR），读接口要判 `status`/`scope`。
6. **统计同源**：筛选只改 `matched`，家底不动；统计与明细共用同一段过滤。
7. **列表可用性**：超过一屏就要有搜索/筛选/分页，且条件放 URL。
8. **失败可读**：业务失败回 `code=1` + 中文原因；只有真正的 bug 才回 500，且落审计。
