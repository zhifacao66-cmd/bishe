## 1. 本轮修了什么

### 1.1 发文搜索：不再手拼 LIKE

`app/api/docs.py` 的公文列表搜索原先自己拼 `f"%{kw}%"`：

```python
q = q.filter(or_(Notice.title.like(like), Notice.doc_no.like(like),
                 Notice.to_org.like(like)))
```

搜一个 `%` 就是 `LIKE '%%%'`，命中全表；搜 `_` 会把下划线当单字符通配。工单/台账/知识库早已统一走
`app/search.py:like_all()`，只有发文这一处绕过了它，属于“同一件事两套口径”。

改为：

```python
from app.search import like_all
cond = like_all([Notice.title, Notice.doc_no, Notice.to_org], kw)
if cond is not None:
    q = q.filter(cond)
```

`smoke_docs.py` 新增 4 项断言：`%` 不返回全表、只命中真含百分号的件、`_` 只按字面量匹配、含百分号的公文可创建。

### 1.2 工单超期统计：从 Python 全量 hydrate 下推为 SQL

`app/api/orders.py` 列表页原先：

```python
overdue = sum(1 for o in base.filter(WorkOrder.status != "done").all()
              if SuperviseAgent.is_overdue(o))
```

演示库 41 条看不出来，量级到几千时，每刷一次列表就要把所有未结单实例化成 ORM 对象再逐条比时间。
现在由 `app/agents/supervise.py:SuperviseAgent.overdue_condition()` 生成等价 SQL：

- `sla_hours` 的正数档位 `h` → `created_at < now - h 小时`；
- `sla_hours` 为 `0`、负数、`NULL` → 按 24 小时兜底，与 `is_overdue()` 的 `sla_hours or 24` 完全同义；
- 未办结（含 `status IS NULL` 老数据）→ 用 `coalesce(status,'open') != 'done'`。

列表接口只做一次 `count()`，不再 hydrate 未结单。`smoke_stats.py` 已有“接口超期数 == 逐条 is_overdue 计数”的断言（50 项），本轮回归通过，证明 SQL 版与 Python 版口径一致。

### 1.3 审计锁定查询：补复合索引

公网查询码锁定每次都要：

```sql
SELECT count(*) FROM audit_log
WHERE actor = ? AND action = ? AND created_at >= ?
```

原来只有 `(created_at, id)` 索引（服务游标分页），这个查询只能靠时间窗口缩到 30 分钟再过滤。
`app/auth.py:_migrate_audit_table()` 新增幂等索引：

```sql
CREATE INDEX IF NOT EXISTS ix_audit_actor_action_time
ON audit_log(actor, action, created_at)
```

列顺序与查询条件一致；重复启动不会重复建索引。

### 1.4 端到端评测的“报表一致：False”是假失败

`scripts/eval_e2e.py` 把报表周期写死成 `"2026-10"`：

```python
rep = c.post("/api/reports/generate", json={"period": "2026-10"}).get_json()
```

跨月再跑时，报表按自然月过滤必然返回 0/0/0，而实际库里有 24/33/11，于是打印
“报表一致：False”。这不是报表口径错，是评测脚本把查询周期留在了过去。

改为当前月：

```python
period = time.strftime("%Y-%m")
rep = c.post("/api/reports/generate", json={"period": period}).get_json()
```

复跑后：**报表一致：True（报表 24/33/11 vs 实际 24/33/11）**。

### 模型通道现状（需要单独处理）

本机模型本身是好的：

- `qwen3:8b` 5.6 GB，**100% GPU**，`/api/chat` 实测返回“正常”；
- 已把 `OLLAMA_MODELS=F:\ollama-models` 写成**用户级环境变量**，避免托盘进程重启后又回 C 盘空目录；
- 网关 `127.0.0.1:11435` 可启动。

但本机到 `api.trycloudflare.com` 的连接在本次复查期间持续抖动，quick tunnel 多次申请失败；
之前那条隧道已在 11/9 被终止。因此 ECS 现在 `llm.available=false`，业务自动降级为规则桩。

这是**网络环境问题**，不是代码问题。网络恢复后执行：

```bat
python scripts\start_llm_channel.py --skip-probe --push-ecs
```

`--skip-probe` 是本次补的逃生口：本机 DNS 解析不了 `*.trycloudflare.com` 时跳过本机自探，
由 ECS 侧 `/api/health` 做最终验证。脚本成功写入新地址后，ECS 的 `channel.py` 按 mtime 热加载，
不需要重启应用。

## 4. 仍保留的已知边界

| 项 | 为什么这一轮不改 |
|---|---|
| `admin` / `kb` 列表无分页（docs/36 P1#7） | 当前账号几十个、知识库 10 篇；改接口形状会同时改页面和 6 套回归，收益低于风险。量级上来再按 ledgers 的 `page/size/matched` 对齐。 |
| `_gen_code()` 最多 30 次查询、全局唯一（P1#9） | 6 位码空间 10^6，社区级票据量下碰撞概率极低；改成按手机号唯一要改 `code` 的唯一约束和迁移，风险大于收益。 |
| 会话 8 小时硬过期 | 演示安排；真要长会话需做滑动续期，不是逻辑错误。 |
| 无 CSRF token | 已有 `SameSite=Lax` + `Sec-Fetch-Site`；引入 token 要改全部表单与前端请求封装。 |
| 限流/准入是进程内内存 | 当前单进程；多 worker 需 Redis 令牌桶（docs/07 已论证）。 |
| MySQL 未实测 | 与 docs/36 结论一致，切库前需跑三套冒烟。 |
