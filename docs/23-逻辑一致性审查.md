# 逻辑一致性审查

> 这一轮不看页面好不好看，也不看有没有报错，只看一件事：
> **系统说的和系统做的是不是一回事。**
>
> 这类问题有个共同特征——不抛异常、不白屏、日志里干干净净，
> 只有数字、状态、可见范围悄悄说错话。等到有人据此做决定（谁该被督办、
> 哪条该归档、这个月办结率多少）时，代价才显现。

## 1. 审查方法

不复用"读一遍代码找 bug"的做法——读的时候人会自动补全意图，
看到的往往是"我本来想写什么"。这里走三步：

1. **先立疑点**：从项目已有的约定反推"哪里最容易破"。
   例如"统计必须服务端 count、必须与明细同源"，那么凡是
   `limit()` 之后才数数的接口都是嫌疑；"读写两侧都要做数据隔离"，
   那么凡是有列表过滤的函数，都要去看对应的写接口有没有同样的校验。
2. **再造数据实测**：复制一份演示库，构造能暴露问题的真实数据
   （130 条任务、跨单位任务、混合 scope 的公告），请求真实接口。
   不看代码猜，看接口返回什么。
3. **最后修 + 固化**：每条修复都配一条断言，写进 `scripts/smoke_logic.py`，
   防止下次重构时又退回去。

## 2. 查出的六个问题

### 2.1 任务卡片数的是"这一屏"，不是"全部"

`/api/tasks` 先 `limit(100)` 取明细，然后用 `len(rows)` 算 summary。
演示库任务少，看起来一切正常；构造 133 条任务后：

| | 修复前 | 修复后 |
|---|---|---|
| 真实任务数 | 133 | 133 |
| `summary.total` | 100 | 133 |
| `summary.overdue` | 只数了前 100 里超期的 | 全量 |

这正是项目里反复写过的一条：**统计一律服务端 count**。
明细有 limit，数出来的是"这一屏有多少"。街道据此判断"这个社区还剩几件没办"，
数字少了会以为进度不错。

修法：统计与明细共用 `_scoped()`，另起聚合查询。顺手补 `truncated`，
让前端知道"列表没给全"。

### 2.2 任务的读侧做了单位隔离，写侧没做

`list_tasks` 按 `assignee_org` 过滤，社区 A 看不到社区 B 的任务。
但 `POST /api/tasks/<id>/done` 只校验了 `u.role == t.assignee_role`：

```
wang（幸福里社区）→ 办结「别的社区」的任务
  列表里能看到吗：False
  直接按 id 调接口：code=0，状态变成 done
```

任务 id 是自增的，可枚举。后果不是"看到不该看的"，而是**改了不该改的**：
状态被推成已完成、留痕写着"受派方反馈"，而真正的受派方什么都没做。

修法：写侧补同一口径的单位校验，跨单位操作写 `audit(agent=auth, action=deny)`。
工单侧早就这么做了（`orders._load_order`），任务侧漏了——说明"隔离"这件事
不能靠记性，必须每个写接口都对着读接口抄一遍。

### 2.3 `recv=dispatched` 把整条查询换掉了，不是加条件

```python
q = staff_query(role)            # ① 按角色收可见范围
if status: q = q.filter(...)     # ② 状态筛选
if recv: q = todo_query()        # ③ ← 这里从 Notice.query 重新起了一条
```

第 ③ 步把 ① ② 全丢了。实测（物业账号）：

```
不加筛选       → ['状态件-published', '公开件-已投递']          ✅ 正确
?recv=dispatched → 5 条，含 scope=community 的内部件、pending、offline  ❌
```

两个后果叠在一起：**越权**（物业看到社区内部件）+ **筛选失效**
（同时选"待确认 + 待签收"，返回全部待签收）。

修法：拆成 `todo_filter(base)`（叠加条件）和 `todo_query()`（新查询），
列表页只能用前者。同时 `counts.todo` 也改成 `todo_filter(staff_query(role))`——
否则卡片写"待签收 4"、点进去 1 条，又是数字打架。

### 2.4 督办告警全表扫描，物业能看到别家工单

`/api/supervision/alerts` 挂的是 `order.view`，物业也持有。
而 `SuperviseAgent.run()` 直接 `WorkOrder.query` 全表扫：

```
物业看到的告警：['W-PROBE-幸福里物业', 'W-PROBE-别家物业', 任务 1]
```

不但看到别家物业的工单号与内容，还看到社区的任务标题。
这个接口页面上没用到（只有测试调），但它是**暴露着的**——
"没人调"不等于"不存在"。

修法：`run(payload)` 接受 `{property_co, role, org}`，接口按会话身份传范围。
扫描逻辑（超时判据、告警文案）仍然只有一份，范围在入口收窄。

### 2.5 只走台账的事项，居民端永远显示"已受理"

`_ticket_payload` 里：

```python
states.append("filed")                       # 已归档进台账
"已办结" if all(s == "done" for s in states) # ← filed 永远不等于 done
```

民政、综治这些业务线**只写台账、不产生工单**。于是居民申请低保复核，
社区早就归档了，居民端还显示"已受理"——等于告诉居民"没人管"。
旁边那个算了一半的 `all_done` 变量（赋了值却没人用）也说明这里改过、没改完。

修法：`done` 与 `filed` 都算办结；整单状态改为"有任何一项推进过就算处理中"，
不再要求必须有工单在 doing。这样"一项已办结 + 一项还没开始"不会退回"已受理"。

### 2.6 置顶排序两端不一致

内部列表按 `pinned_at` 排（后置顶的在前），居民端按 `published_at` 排。
两条置顶件时，社区刚置顶的重点通知在居民端反而排在旧件后面——
"置顶"在居民眼里等于没生效。

修法：居民端与内部同键排序。同时发现老库里有置顶位为真但 `pinned_at` 为空的行
（早期 `_apply_pin` 只翻布尔值），于是把回填做成**每次启动幂等执行**，
而不是只在"刚加列"那一次跑——那批行恰恰是在列加好之后产生的。

### 2.7 管理员被当成了"受派方"：登录后工单页一条都没有

`tasks._scoped()` 写的是黑名单：

```python
if u and u.role != "street":                       # 除街道外，一律按受派方收窄
    q = q.filter(Task.assignee_role == u.role)     # admin 进来就是 == "admin"
```

任务表里**不存在 `assignee_role = "admin"` 的行**——admin 是平台运维，不是
业务受派方。于是管理员登录后工单页恒为空、统计卡片全 0；而物业账号反倒能看到
自己的 5 条。更矛盾的是 `ROLE_PERMS["admin"] = set(PERMS)`：权限是满的，
列表却是零条。

同一形态在 `supervise.py` 有一份拷贝（`if role and role != "street"`），
表现为管理员打开督办**永远"无告警"**——不是没超时，是查错了范围。

`notices.todo_filter()` 是第三种写法，也更隐蔽：它按 `"notice.receive" in user_perms(u)`
判断，admin 持有全量权限所以命中，接着拿 `u.org`（"平台运维"）去比收文单位，
待签数恒为 0。

修法：三处统一改成**白名单**——受派方只有 `community` 和 `property`，
收窄只对这两个角色生效，`street` / `admin` 看全量；公告那处显式排除 admin。
选白名单不是写法偏好：黑名单每加一个角色就要回头检查一遍所有过滤点，
而这已经漏了两次（tasks、supervise）。

## 3. 数据层自洽检查

代码对了不代表库里已有的数据也对。`scripts/check_integrity.py`
在**副本**上逐项比对"同一事实的两处存放"：

| 检查 | 说明 |
|---|---|
| `ledger.search_text` ↔ `content_json` | 绕过 ORM 的写入会让检索文本漂移，表现为"这条搜不到" |
| 工单状态 ↔ 流转链末步 | 状态被改但没留痕，追责链断在中间 |
| 已办结工单有 `done_at` | 缺了就算不出处理时长 |
| 置顶公告有 `pinned_at` | 缺了排序退化 |
| 已签收公告有签收人/时间 | 缺了签收就不成立 |
| 任务状态 ↔ `closed_at` | 两者必须同真同假 |
| 报表版本号 ↔ 历史份数 | 版本号是归档件标识，对不上说明丢过版 |
| 居民单状态 ↔ 明细推进 | 单据状态必须由明细算出来 |

首次运行只报出 1 类：1 条早期置顶件缺 `pinned_at`，回填后全部自洽。

## 4. 回归

新增 `scripts/smoke_logic.py`（46 项），按 A~H 分组，每条对应上面一个缺陷。
它不是功能测试——功能测试问"这个功能能不能用"，它问"两处算法会不会打架"。

`[H]` 组专测 admin 视角：admin 要能看到全量任务、全量督办告警、待签数不为 0；
物业和社区仍只能看到自己的，街道仍是全量。四种身份在同一份数据上互相对照。

全套 **25 套 1288 项**全绿（logic 从 34 涨到 46）。

线上发布的一次事故也记在这里：发布后我用 `POST /api/tasks/<id>/done` 去验越权，
把 3 条**演示任务**真办成了已完成（接口把 403 放在响应体 `code` 里、HTTP 仍是 200，
脚本按状态码判，于是以为"全放行了"，实际有放行有拒绝）。
教训：**核验线上的写侧隔离，不能用生产演示数据做写操作**。
写侧隔离已经在 `smoke_logic[B]` 用独立库验证过，线上只做只读比对
（wang 可见集合 ⊂ admin 可见集合、角色一致）。`_verify_online.py` 现在不含任何写请求。

## 5. 看到但没改的（如实记录）

| 现象 | 为什么不改 |
|---|---|
| `GET /api/reports`、`/api/kb/docs`、`/api/admin/users`、`/api/audit/agents` 返回裸数组 | 与"列表统一 `{items,counts}`"的约定不符，但这几个接口已被页面和 4 套回归依赖，改形状要同时动模板与测试，收益低于风险。下一轮统一时一起改 |
| `_LOGIN_FAIL` 按用户名无限增键 | 只有内存压力，没有正确性问题；真正的修法是接 Redis，属于部署形态变更 |
| 物业账号 `org` 为空时，工单/公告的隔离会放宽 | 演示账号都有 org；管理员建号时 org 必填。留作边界说明，不在代码里加隐式兜底 |
| 报表 `line` 只支持"街道"一档 | 当前业务只有街道上报，多档需要产品口径，不是代码问题 |
