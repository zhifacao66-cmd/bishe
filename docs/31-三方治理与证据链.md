# 三方治理：仲裁闭环与证据链

> 2026-10-26。这一轮把定位从"录入减负"扩到"社区多主体协同治理"，
> 并补上**仲裁**与**存证**两块此前在代码里完全不存在的能力。

## 1. 为什么必须补这两块

原来的链路是：居民报事 → 居委会拆解派单 → 物业办结 → （结束）。

问题不在流程画得不全，而在**三方结构里只有两方半**：

| 主体 | 原来能做什么 | 缺什么 |
|---|---|---|
| 居民 | 提交一次，之后凭查询码看进度 | 不能补材料、不能确认"解决了没"、不能表示不服 |
| 物业 | 接单、转派、办结 | 办结即终局，没有人能驳回 |
| 居委会 | 派单、督办告警、出报表 | **没有"裁决"这个动作** |

后果是：物业说办完了，居委会只能接受，居民只能围观。
"博弈"和"仲裁"都还没有发生的地方——**因为系统里不存在"争议"这个对象**。

这一轮补的就是这个对象。

## 2. 仲裁的实质：责任判定，不是满意度打分

加一对"满意/不满意"按钮是最容易做的，但那是**评分**，不是仲裁。

真实社区里三方吵的从来不是"态度好不好"，而是：

> 楼道灯坏了，物业说"这是业主自用部分不归我"，居民说"我交了物业费"，
> 居委会要判的是**这笔钱谁出、这件事谁干**。

所以裁决落在四个结论上（`app/arbitration.py:VERDICTS`）：

| 结论 | 动作 | 含义 |
|---|---|---|
| `property_fault` 物业责任 | **退回重办** | 属物业服务合同约定范围，应返工 |
| `owner_duty` 业主自用部分 | 维持办结 | 专有部分维修由业主自行承担 |
| `public_duty` 公共部位 | 维持办结 | 费用由公共收益或维修资金列支 |
| `escalate` 超出社区权限 | 维持办结 | 需上级或专业单位处置，已移交 |

前三个里只有一个会导致工单退回。**这个比例本身是有信息量的**：
驳回率过高说明物业在糊弄或派单派错了，两者都值得预警。

## 3. 两条写进代码的铁律

### 3.1 回避原则：物业不能裁自己的单

`order.verdict` 权限点**故意不发给物业**，同时 `can_judge()` 里再硬判一次角色。

为什么做双保险：权限点是可以被管理员勾选的。只靠配置，一次误操作就把制度破了。
`smoke_arbitration` 里专门造了一个"管理员误把裁决权勾给物业"的账号，
验证代码层的回避仍然生效（返回 403，理由写明"回避原则"）。

这条不只是技术约束，它正好解释了现实里一个常见现象——
**小区里投诉物业为什么永远没用**：因为裁判和当事人是同一个。

### 3.2 依据必填：不接受"已协调处理"

`judge()` 里依据少于 8 字直接拒绝。原因是这类话既不能说服居民，
也无法在街道复核时自证。回归里专门断言"已协调处理"会被拒。

## 4. 状态机与数据模型

```
open --accept--> doing --finish--> done
                     ↑                │
                     └── reject ──────┘      居委会驳回，退回重办
                                      │
                                      └── uphold ──> done   维持办结（状态不变）
```

- `reject` 只能从 `done` 出发，且**必须回到 `doing`**。
  只打个"已驳回"标记而不改状态，物业就没有重办入口，业务流程上什么也没发生。
- `uphold` 是 `done → done`。`from == to` 在这里合法（记录一次判定但状态不变），
  但起始状态写死 `done`，避免被误用到 `doing` 的单上变成"维持一个还没办完的结果"。

字段（`WorkOrder`）：

| 字段 | 作用 |
|---|---|
| `dispute_type` | 责任归属 / 费用承担 / 质量不达标 / 超期未办 |
| `verdict` | 裁决结论（见上表） |
| `verdict_basis` | 裁决依据，必填 |
| `verdict_by` / `verdict_at` | 谁在什么时候判的 |
| `confirm_status` | 居民表态：空 / `ok` 已解决 / `disputed` 不服 |
| `confirm_note` / `confirm_at` | 居民原话与时间 |

**`status` 与 `confirm_status` 是两条独立的线**：工单可以 `done` 而居民 `disputed`，
这正是需要仲裁的状态。不能因为 `done` 就把 `disputed` 洗掉。

同样地，居委**维持办结**之后，居民的 `confirm_status` 仍然是 `disputed`——
居民本人并没有确认解决，替他改口等于伪造居民意愿。这一条有专门断言。

## 5. 证据链：能证明什么，不能证明什么

### 5.1 能力边界（答辩时必须这么说）

- **能证明**：这条链从某一条之后没有被改过、没有中间插过、没有删过某条。
- **不能证明**：记录内容本身是真的；也防不住有人拿到 sqlite 文件后重算整条链。

所以对外一律说"**可验证未被篡改**"，不说"不可篡改"，更不说"区块链"。
用词差一个字，被追问时的处境完全不同。

为什么不上区块链：单机 SQLite、每天几十条记录，引入链平台等于给 2C2G 的服务器
加一个必须常驻的外部依赖，可用性反而下降。要的只是"事后能证明没改过"，链式哈希就够。

### 5.2 锚点，以及它的边界

只存链头没用——改库的人可以连链头一起改。所以 `ChainAnchor` 每次锚定都记
`(seq, hash, total)`，**并同步写一条 `audit_log`**。审计日志另有每日备份路径，
两条线同时被改的概率远低于改一条。

锚定权给居委会、街道、管理员三方，**物业不能锚**（当事方不保管证物）。
多方各自留一份才是交叉验证；只有管理员能锚，它就退化成运维脚本的一次执行。

**锚点的边界**（这一点很容易说错）：

| 篡改方式 | 是否被发现 | 报出的原因 |
|---|---|---|
| 改内容，不重算哈希 | 是 | `hash_mismatch` |
| 删掉中间一条 | 是 | `seq_gap` |
| 改**链头**并重算哈希 | 是 | `anchor_mismatch`（锚点抓出） |
| 改**中间**某条并重算哈希 | 是 | `prev_mismatch`（下一条的前序对不上） |

最后一行是关键：锚点只钉链头，改中间不会触发锚点比对，但会让下一条的
`prev_hash` 对不上——**仍然被发现**，只是诊断措辞是"被删或插"而非"被改"。
四种都写进了回归，谁也不靠嘴说。

校验顺序也因此固定：**锚点先比、链内自查后比**。反过来的话，
"改链头并重算"会先在下一条报 `prev_mismatch`，看起来像"记录被删了"，
实际是"内容被改了"，诊断就错了。

### 5.3 存什么、不存什么

链上 `payload` 存的是**脱敏后的快照**（`evidence.mask_payload()`），不是原文。
理由：如果为了举证清楚把诉求原文原样塞进去，等于在 `evidence_chain` 里
又存了一份含手机号的明文，绕过 `security` Agent 和 `field_security` 的字段管控。
原文本体仍在 `resident_ticket.raw_text`（已脱敏），链的作用是**证明它没被改**。

附件同理：每张算 SHA-256 进链，**落盘用随机名**。
居民的照片常叫「3栋201身份证.jpg」，原名一旦随目录泄漏（备份打包、同步脚本），
等于把门牌和证件类型一起送出。原名只在库里留一份，与随机名对应。

## 6. 附件上传的四个必须

`data/evidence/` 落盘，`MAX_PHOTOS=5`、单张 5MB。

1. **按文件头判类型，不认扩展名**。把 `.php` 改名成 `.jpg` 一样能过扩展名检查。
   回归里就是这么测的（塞一段 PHP 代码、命名 `shell.jpg`，必须被拒）。
2. **`MAX_CONTENT_LENGTH` 必须设**。Flask 默认不限，而居民端是公网匿名入口，
   不设的话一个 500MB 的 POST 就能吃干 2C2G 的内存——而且 Flask 会先把整个
   body 读进内存再交给视图，拦不住。
3. **落盘用随机名**，原名只回显。
4. **不能放 `app/static/`**。放那里等于把居民照片变成可直接访问的静态资源。

## 8. 验收

- `smoke_arbitration` **79 项全绿**：状态机 9、回避原则 6、依据校验 5、维持办结 4、
  居民表态 12、附件 11、证据链 18、越权与口径 14
- 全量 **30 套回归逐套独立建库单跑全绿**（1584 项 + 数据完整性 16 = 1600）
- 实测：改 payload → `hash_mismatch`；改内容并重算哈希 → `anchor_mismatch`；
  删中间一条 → `seq_gap`；改中间并重算 → `prev_mismatch`。四种篡改无一漏网

## 9. 四个重点功能的现实判断（后续）

用户提出的四个方向，现状评估与建议顺序：

| 重点 | 现状 | 关键约束 |
|---|---|---|
| **异构文档 OCR 抽取** | 完全空白（无上传、无 OCR） | 服务器是 Server 2025 **Core**，没有 OCR 组件，2C2G 也装不了 PaddleOCR；本机有 PIL 但**没有 OCR 引擎**。可行路径只有**离线批处理**：本机 OCR → 抽取 → 生成评测报告。"报告准确率"本来就需要离线标注集，这条路反而更学术。**手写体基本没戏**，只能做印刷件 |
| **ABAC 保密管理** | 已有 7 处硬编码的访问规则（工单按单位、公告按 scope、公文按密级、字段按 level） | ABAC 的价值是**把这 7 处收敛成一个决策点并留 reason**，治的正是 `docs/26` 里"scope 四处口径"那类病。不是"替代 RBAC"——准确说法是 **RBAC 管能不能进这个功能，ABAC 管进了之后能看哪几条** |
| **流程监控（流程挖掘）** | 数据基础好：`work_order_log` 有 action/from/to/actor/org/时间戳 | 但样本只有 18 张单、44 条记录、3 次转派。能算每步停留时长和转派次数，**不能算 P90 瓶颈、不能做异常检测**。样本量必须如实标注 |
| **长尾风险预警 + 文本聚类** | 诉求 1 条 | 聚类没有可聚类对象。必须先让居民端能反复报事、能补材料（本轮已通），数据才长得出来 |

建议顺序：**本轮（仲裁 + 存证）→ ABAC 收敛 + 保密管理 → 流程监控（诚实标注 N）→ OCR 离线评测**。
长尾预警依赖真实使用数据，放在有数据之后再做。

## 10. 遗留

1. **`data/evidence/` 未纳入备份**。`scripts/backup_db.py` 目前只备数据库，
   附件目录要一起备，否则"链在、图没了"，链就失去意义。待办。
2. **链的清理策略未定**。`evidence_chain` 只增不删，长期会膨胀。
   按"每日锚点 + 90 天归档"设计比较合理，但归档后的链校验需要单独实现。
3. **居民端限流按 ticket 而非按人**。攻击者换 ticket 可绕过，
   不过 confirm/attach 都需要先持有该 ticket 的 session，实际风险低。
4. **`docs/29` 的数字要同步**：代码 1.9 万行 / 83 个 API / 23 个功能点 / 30 套 1584 项。
