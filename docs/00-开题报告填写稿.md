## 1. 选题的理论意义或应用前景

（约 1600 字，可按学校字数上限删减小节）

### 一、现实背景

基层治理长期存在"上面千条线、下面一根针"的结构性矛盾。社区工作者面对综治、民政、卫健、城管、物业等多条业务线，同一户居民的基础信息要在不同系统中反复录入，形成"一数多填、一表多报"的重复劳动；台账口径不统一，巡查、走访、调解均需手工留痕；社区与街道、物业之间的协同依靠微信群，事项易丢失、责任难追溯。2024 年中办、国办印发的《整治形式主义为基层减负若干规定》明确要求精简报表、清理重复填报，但当前主流的减负手段仍停留在"减表"层面——压缩表格数量，并未触及"同一数据在多个系统中重复录入"的机制性根源。

与此同时，居民身份证号、健康状况、门牌住址、调解隐私等内容受《个人信息保护法》约束，不允许上传公有云大模型。这一硬约束使得通用 SaaS 类智能助手在基层场景难以落地：能力最强的模型用不了，能用的模型能力不足。

### 二、理论意义

**（1）提出并验证"首录单点 + 智能体分发"的数据复用范式。**
本文将基层一次工作事项抽象为"非结构化自然语言 → 结构化业务项集合 → 按业务线路由"的三段映射，用多智能体协作替代人工在多系统之间搬运数据。其理论价值在于回答一个具体问题：大语言模型能否承担"业务理解 + 事项分拣"这一原本完全依赖人脑判断的中间层。实验表明，在 43 条标注语料上业务项拆解的数量准确率达 97.7%、类型 F1 达 99.0%，说明该中间层具备工程可用性。

**（2）探索隐私强约束下本地大模型的可用性边界。**
政务信息化的技术路线与公有云大模型相反：前者要求数据不出域，后者追求能力上限。本文在 8GB 显存的消费级 GPU 上部署 8B 参数量化模型，量化了本地模型在结构化信息抽取任务上的能力上限，并给出"约束解码比模型规模更关键"的实证结论——引入 JSON Schema 约束解码后数量准确率由 86.0% 提升至 97.7%（+11.7pp），而单纯启用思维链使耗时增至 9.1 倍且质量下降。这为内网环境下的模型选型与提示策略提供了可复用的判据。

**（3）建立"模型指标—业务指标"两层评测框架。**
现有大模型应用研究多止步于 benchmark 分数。本文的端到端实验证明，模型拆解 F1 达 97.9% 并不等价于业务正确：拆对了仍可能漏派单、派错业务线、重复建档或泄露敏感信息。据此本文提出并实现了覆盖漏派单率、误派单率、多建档率、敏感信息召回率、库内明文数、任务闭环率、报表一致性七项指标的业务层评测，与模型层指标形成互补。该框架可推广至一切"模型输出直接驱动下游业务动作"的系统。

**（4）揭示"同步调用大模型"的架构代价。**
通过并发阶梯实验，本文测得单卡串行推理的吞吐天花板为 0.62 请求/秒，与并发数无关；16 并发时 P95 延迟升至 24.2 秒，而同期框架层（Flask + SQLite）可达 275 QPS。二者相差 440 倍，说明瓶颈完全在推理侧，且"让用户 HTTP 连接等待完整条模型链路"是架构缺陷而非性能问题。这一结论为"大模型应用必须异步受理"提供了可复现的实验依据。

### 三、应用前景

**（1）直接应用。** 面向社区与街道，可覆盖综治、民政、卫健、城管、物业五条业务线，将一次录入的人工操作次数由 59 次降至 24 次（−59.3%），单次受理 P50 耗时 2.14 秒。

**（2）可迁移场景。** 凡存在"一份信息多头上报"的组织均存在同构问题：民政救助、应急管理、网格化治理、企业内部的 ERP/CRM 双录等，其"理解—拆解—路由—留痕"的技术骨架可直接复用。

**（3）信创适配。** 全栈可由国产化组件构成（开源模型 + Ollama + MySQL + 国产操作系统），无外网依赖，适合政务内网与涉密单位部署；单张 8GB 消费级显卡即可支撑一个街道（3~10 名社工在线）的日常负载，部署成本远低于私有化大模型方案。

**（4）方法论价值。** 本文形成的 Agent 契约设计、保密审查流水线、三层评测脚本与工程加固方案，可作为同类"本地大模型 + 多智能体"项目的参考实现。

## 2. 研究思路、方法、技术路线

（约 1700 字）

### 一、研究思路

本文采取"从业务流程反推技术方案"的路径，而非"先选模型、再找场景"。具体分三步推进：

**第一步，从一线流程确定唯一入口。** 通过梳理社区—街道—物业三方的业务流转关系，识别出"重复劳动"的真正根源不在于表格多，而在于**同一份数据存在多个录入点**。据此确立 FDE（First Data Entry，首录入口）作为全系统唯一的业务数据第一录入点，所有下游系统只消费、不重复采集，从机制上实现"一次录入、多方复用"。

**第二步，把"人怎么判断"翻译成 Agent 契约。** 将社区工作者的隐性判断拆成七个可枚举的职责：拆解、保密审查、派单、填报、台账、报表、督办。每个 Agent 的输入、输出均定义为固定 JSON Schema，由 Orchestrator 统一调度，异常一律降级到人工确认，不允许静默出错。

**第三步，用业务指标而非模型指标验收。** 模型层评测回答"拆得对不对"，业务层评测回答"事情办成没有"，工程层测试回答"多人同时用会不会崩"。三层同时达标才算完成。

### 二、研究方法

1. **文献调研与政策分析法**：梳理多智能体协作、检索增强生成、约束解码、RBAC 等方向的代表性工作，同时研读基层治理与个人信息保护相关政策法规，确定合规边界。
2. **领域建模与需求分析法**：建立"角色 × 权限"矩阵（社区 8 项权限点、街道、物业三类角色）与七类业务项类型体系，完成实体关系建模与状态机设计（工单 open→doing→done）。
3. **原型迭代法**：先以静态 Demo 确定交互形态与视觉规范，再搭建 Flask 应用工厂骨架，随后以 F1~F10 功能为单位增量交付，每个功能完成后立即冒烟测试，避免缺陷累积。
4. **实验研究法（控制变量）**：评测固定语料、固定硬件、固定解码参数，同一配置重复三次取均值与范围；消融实验设置 5 组配置，逐项剥离提示策略、约束解码、思维链、预分句重试等因素。
5. **对比实验法**：WAL 与 rollback journal 的并发对比、约束解码与 `format:"json"` 的稳定性对比、推理闸门并发度 1/2/4 的标定对比。
6. **压力测试与长稳测试法**：并发阶梯 1/2/4/8/16 采集 P50/P90/P95/P99 与吞吐，长稳测试连续运行并周期采样进程内存、显存、数据库体积与窗口延迟分位。

### 三、技术路线

系统采用五层架构，自下而上依次为：

```
┌──────────────────────────────────────────────────────────┐
│ 评测层  模型层(43条/消融) → 业务层(24条×3次) → 工程层(并发/长稳) │
├──────────────────────────────────────────────────────────┤
│ 应用层  Flask + Jinja2 + Tabler + ECharts                 │
│        首录台│任务看板│工单中心│台账中心│报表│审计日志        │
├──────────────────────────────────────────────────────────┤
│ 安全层  保密审查(三级脱敏) │ RBAC(10权限点) │ 审计留痕(只追加)  │
├──────────────────────────────────────────────────────────┤
│ 协作层  Orchestrator 调度器                                │
│  拆解│保密│派单│填报│台账│报表│督办  (7 个单职责 Agent)       │
├──────────────────────────────────────────────────────────┤
│ 模型层  Ollama + qwen3:8b (本地, 零外网) + BM25 知识库        │
├──────────────────────────────────────────────────────────┤
│ 数据层  SQLite(WAL)/MySQL │ 审计库 │ 文件存储               │
└──────────────────────────────────────────────────────────┘
```

**核心业务链路：**

```
工作者口述一段话
   → ① 保密审查 Agent：识别身份证/手机号/门牌等，按三级策略脱敏
   → ② 落库原文（脱敏后）并提交事务          ← 关键：先提交，后调模型
   → ③ 拆解 Agent：JSON Schema 约束解码，输出业务项列表
   → ④ 按业务线分流：
        ├ 物业类 → 派单 Agent → 脱敏工单 → 物业接单/反馈/闭环
        └ 政务类 → 填报 Agent → 查重复用 → 台账入库
   → ⑤ 报表 Agent 按月汇总（街道端，仅汇总值）
   → ⑥ 督办 Agent 监控 SLA，超时告警
   → ⑦ 全流程写入审计日志（操作者、Agent、时间、输入输出摘要）
```

**四项关键技术决策：**

| 关键点 | 方案 | 依据 |
|--------|------|------|
| 结构化输出稳定性 | JSON Schema 约束解码（Ollama structured outputs） | 数量准确率 86.0%→97.7%，远优于 `format:"json"` |
| 敏感信息识别 | 强特征优先 + 数字边界断言（18 位身份证先于 11 位手机号匹配） | 修复"身份证被手机号正则截断"缺陷后召回率升至 100% |
| 知识检索 | 字符二元组 BM25 + 标题/小节加权（可选 bge-m3 混合） | 零显存占用，8GB 卡上可与推理共存；中文短文本场景优于稠密向量 |
| 并发控制 | BoundedSemaphore 推理闸门 + 排队超时降级；SQLite 开 WAL | 闸门并发度 1 与 2 实测等价（Ollama `runner.parallel=1`），超时降级为规则兜底保证可用性 |

**评测体系（三层递进）：**

- **模型层**：43 条标注语料，评数量准确率、类型 F1、去向准确率，配合 5 组消融实验。
- **业务层**：24 条端到端语料 × 3 次重复，走真实 HTTP 链路（登录→首录→派单→接单→结单→报表），评漏派单率、多建档率、敏感信息召回率、库内明文数等七项。
- **工程层**：并发阶梯 + 长稳测试，评吞吐、延迟分位、错误率、内存/显存漂移、落库一致性。

### 四、可行性分析与风险对策

| 风险 | 应对措施 |
|------|----------|
| 本地模型能力不足，拆解不准 | 约束解码 + 规则兜底双保险；实测 F1 99.0%，已达可用水平 |
| 8GB 显存不足 | 采用 Q4_K_M 量化（4.7GB）+ `num_ctx=4096`，实测峰值占用 7566/8188MB |
| 真实居民数据不可获取 | 全部使用构造语料与已脱敏样本，不涉及真实个人信息，符合合规要求 |
| 并发下数据库锁冲突 | 已定位并修复事务边界缺陷；SQLite 开 WAL + busy_timeout，16 并发零错误 |
| 进度风险 | 功能按 F1~F10 拆分，每个功能独立可演示，任何阶段中断均有可交付成果 |

## 3. 总体安排、进度计划

（约 1500 字；按 2027 年 6 月答辩编排，若学院节点不同请整体平移。以下为纯文本段落，可直接粘贴到输入框。）

课题总体按"调研—设计—实现—验证—成文"的思路推进，自 2026 年 10 月起至 2027 年 6 月止，共约八个月，划分为十个阶段，每个阶段均设定明确的工作内容与交付物，便于自查与导师检查。

第一阶段为选题与开题准备，时间为 2026 年 10 月上旬至 10 月底。主要工作是围绕多智能体协作、本地大模型部署、检索增强生成等方向开展文献调研，研读基层治理与个人信息保护相关政策文件，了解社区工作者在报表填报、台账整理、跨部门协同中的实际流程与痛点，据此论证选题的必要性与技术可行性，完成文献综述与开题报告。

第二阶段为需求分析与总体设计，时间为 2026 年 11 月。重点完成三方面工作：一是梳理社区、街道、物业三方的业务流转关系，建立角色与权限对应矩阵；二是归纳综治、民政、卫健、城管、物业等业务线的事项类型，形成业务项类型体系与字段规范；三是设计数据模型与各 Agent 的输入输出契约，并制作交互原型以确定界面形态。本阶段成果为总体设计文档与可点击原型。

第三阶段为系统骨架与首录主线开发，时间为 2026 年 12 月。完成 Flask 应用工厂搭建、蓝图分层、统一响应格式与全局异常拦截，并实现首录入口的原始文本接收、敏感信息识别与脱敏、业务项自动拆解三项核心功能，打通"一句话进、多条业务项出"的主链路。

第四阶段为业务闭环开发，时间为 2027 年 1 月。实现派单 Agent 与物业工单模块，包括工单生成、物业端列表展示、接单与反馈闭环；实现填报 Agent 与台账模块，包括按业务线自动建档与重复事项复用；同时完成工单状态机（待处理、处理中、已完成）的设计与非法流转拦截。

第五阶段为管理与治理模块开发，时间为 2027 年 2 月。实现报表 Agent（按月汇总并向街道端输出）、督办 Agent（依据 SLA 规则做超时告警）与审计日志模块（全流程留痕、只追加不可修改）；同期完成本地大模型的环境部署、模型选型与推理参数调优，使核心链路摆脱规则兜底、真正由模型驱动。

第六阶段为效果评测与中期检查，时间为 2027 年 3 月上旬至 3 月中旬。构建覆盖七类业务事项的标注评测集，完成业务项拆解的数量准确率、类型 F1 与去向准确率评测，并设计多组消融实验，逐项验证约束解码、提示策略、思维链等因素的贡献；同期实现社区、街道、物业三角色的登录与权限控制。本阶段形成评测报告，作为中期检查的主要材料。

第七阶段为功能增强与端到端验证，时间为 2027 年 3 月下旬至 4 月上旬。接入检索增强知识库，使系统能够依据社区政策与业务规范作答；构建端到端评测语料，走真实登录与业务链路重复多次运行，统计漏派单率、重复建档率、敏感信息召回率、任务闭环率等业务指标，并针对评测暴露的缺陷逐项修复。

第八阶段为工程加固与系统联调，时间为 2027 年 4 月中下旬。开展并发压测与长时间稳定性测试，采集吞吐量、延迟分位数、错误率、内存与显存漂移等指标，定位并修复事务边界、数据库锁竞争等工程问题；编写全流程演示脚本，确保系统在演示环境下稳定可复现。

第九阶段为论文撰写，时间为 2027 年 5 月上旬至 5 月下旬。完成论文初稿，整理系统架构图、业务时序图、减负成效对比图与各阶段实验数据表，随后进行查重、修改与定稿。

第十阶段为答辩准备，时间为 2027 年 5 月底至 6 月初。完成演示环境部署、答辩幻灯片制作与预答辩演练。

在进度控制上设置三个关键检查点：2026 年 11 月底完成总体设计评审；2027 年 3 月中旬中期检查时，核心链路（首录、拆解、派单、台账）须可完整演示；2027 年 4 月底完成全部实验数据采集，确保论文撰写阶段不再依赖新增实验。若某一阶段出现延期，优先保证核心链路完整与评测数据真实，将界面美化等非关键工作适当后置。
