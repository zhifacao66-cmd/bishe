## 1. 先说清一件事：不是"用 ABAC 替代 RBAC"

题目里的原话是「用 ABAC 替代简单角色控制」。这个说法在工程上不成立，写进论文会被追问。

| | RBAC（本项目 23 个权限点） | ABAC（本文件） |
|---|---|---|
| 回答的问题 | **能不能进这个功能** | **进来之后这一条能不能看** |
| 粒度 | 页面 / 接口 | 行 / 字段 |
| 例子 | 有没有 `order.view` | 同持 `order.view` 的社区与物业，看到的是不同批工单 |
| 管不住的 | 列表里哪几行该隐藏 | 有没有资格进这个页面 |

**两层并存，缺一层都漏：**

- 只有 RBAC：给物业 `order.view` 之后，它能拿别家工单号按 id 直取（工单号 `W+日期+序号` 可枚举）。
- 只有 ABAC：属性算得再细，也构不成"这个人有没有资格进工单页"这个功能级授权。

准确表述是：**在 RBAC 之上叠加 ABAC 做行级与字段级收窄，把原先散落在 7 处的硬编码判断收敛成一个决策点。**

## 2. 改造前是什么样

"这条数据该不该让他看"被手写在七个地方，各自实现：

| 位置 | 判断 |
|---|---|
| `api/orders.py:_scoped()` | `role == "property"` → `property_co == org` |
| `api/tasks.py:_scoped()` | `role in (community, property)` → `assignee_*` |
| `notice/ingest.py:staff_query()` | `scope in ("all", role)` |
| `notice/ingest.py:can_view()` | 同上，**另一份实现** |
| `api/docs.py:196` | 密级 in (内部·敏感, 秘密, 机密) → 403 |
| `views.py:208` | 同上，**另一份实现**（页面层） |
| `api/evidence.py` | `property_co != org` → 403 |

它们当时能对上，靠的是每次改都记得把七处一起改。这不叫设计，叫运气。并且已经出过事：
`docs.py` 挡住了、`views.py` 还在渲染——**接口 403、页面照常显示**。

改造后：这七处全部改为调用 `policy.py`，规则表只有一份。

## 3. 四类属性

ABAC 的定义要求"四类属性参与决策"，缺一类就只能叫"带条件的 RBAC"：

```
主体 subject ：role 角色 / org 单位 / status 账号状态 / perms 权限点
资源 resource：kind 类型 / secret 密级 1–5 / scope 可见范围 / owner_org 归属单位 / status 发布状态
动作 action  ：read 读 / list 列表 / export 导出 / write 改 / judge 裁决
环境 env     ：channel 内部站·居民端 / export_fmt 导出格式
```

密级映射（库里存中文串，代码里转整数比较）：

| 中文 | 空串 | 公开 | 内部 | 内部·敏感 | 秘密 | 机密 |
|---|---|---|---|---|---|---|
| 数值 | **2** | 1 | 2 | 3 | 4 | 5 |

两个方向的兜底都要说清：

- **空串按"内部"（2）处理，不是按"公开"。** 老数据大多是空串；当公开处理等于让"忘了标密"变成"对全网可见"。
- **认不出的密级兜到 5（机密），不兜到 1。** 新增一种标识（如"内部·敏感（含居民信息）"）而忘了登记，往下兜就是直接泄漏。

## 4. 规则表（顺序即优先级）

顺序是硬约束：**"拒"的规则必须排在"允许"之前**。R7 一旦排到前面，后面所有限制永久失效，而接口照样 200、页面照样好看——不会自曝。

| 编号 | 规则 | 判定 |
|---|---|---|
| R1 | 账号状态 | `status != active` 且走内部站 → 拒。最靠前，因为它比"角色有没有权限"更根本 |
| R2 | 居民端密级 | `channel == portal` 且密级 ≥2 → 拒 |
| R3 | 跨单位 | `owner_org` 与 `subject.org` 不同，且角色不是街道/管理员 → 拒 |
| R4 | 密级上限 | `secret > ROLE_SECRET_CEILING[role]` → 拒 |
| R5 | 公告范围与状态 | scope 不含本角色，或资源未发布 → 拒 |
| R6 | 导出归属 | 密级 ≥3 的文件只有归属单位与监督方能导出；**导出一律强制水印 + 审计** |
| R7 | 默认允许 | 未命中 → 放行（规则表是黑名单式收窄） |

角色可见上限：

| 角色 | resident | property | community | street | admin |
|---|---|---|---|---|---|
| 上限 | 公开(1) | 内部(2) | 机密(5) | 机密(5) | 机密(5) |

物业 = 2 是**沿用改造前的行为**（`docs.py` 原本就挡 3/4/5），不是新加的收紧。收紧到 1（连"内部"都看不到）会让物业看不到物业费调价通知——那不叫保密，叫瘫痪。

> 社区上限是 5 而不是 4 的原因：`秘密/机密` 只可能来自**上级来文**（见 `docflow.SECRET_LEVELS` 注释），社区要签收、要办文，看不到就没法办。

## 5. 决策输出：`Decision` 而不是 `bool`

```python
@dataclass
class Decision:
    allow: bool
    rule: str        # 命中的规则，如 "R4 密级上限"
    reason: str      # 人话，直接进 403 body 与审计
    mask: bool       # 是否需要字段级脱敏
    watermark: bool  # 是否必须加水印
    log: bool        # 是否必须写审计
    attrs: dict      # 现场属性快照
```

`reason` 有三个用处，都不是装饰：

1. **给人看**：`"该内容密级为「内部·敏感」，你的角色「property」可见上限为「内部」"` —— 比"无权查看"多告诉了他该找谁要权限。
2. **审计留痕**：拒绝本身要记，记的是"谁在什么属性组合下被哪条规则挡住"。
3. **答辩可检验**：`/security/policy` 页面现场改一个属性，立刻看到命中哪条、被哪句话挡住。

## 6. 水印：三道，能力边界必须讲清

| 载体 | 做法 | 强度 |
|---|---|---|
| 内部站页面 | SVG 背景平铺 | 真水印，截哪一块都带痕 |
| xlsx | 打印页眉 + 数据区末行 | 前者仅打印可见，后者屏幕可见 |
| docx | 页眉段落 | Word 里可见，摘成纯文本会丢 |
| md / txt | front matter 键 / 首尾两行 | 可被直接删掉，**几乎不构成证据** |

水印文案四个要素缺一不可，`姓名 · 单位 · 时间 · 动作`：

- 姓名 → 追到人（只写单位等于只知道"社区导的"）
- 单位 → 归属（同名的人不罕见）
- 时间 → 对上审计日志那条记录的唯一线索
- 动作 → 区分"导出"与"打印"，两种行为责任不同

**三条必须承认的边界（写论文时别越界）：**

1. **Excel 的"真水印"做不到。** openpyxl / 自研写入器都不能往工作表里插艺术字或图片背景；硬造会让文件在 Excel/WPS 里报"内容有问题"。所以 xlsx 是页眉 + 末行。**页眉在屏幕上完全看不见**——当众说"Excel 导出带水印"而对方截图看不到，比不做更伤人。
2. **docx 只能动页眉，不能动页脚。** 页脚被 `_page_number()` 占着放 `- 1 -`，塞水印会盖掉页码；公文没页码是硬伤（GB/T 9704）。
3. **水印提高追溯概率，不阻止泄露。** 它可以被裁剪、被 P 掉。真正起作用的证据是审计日志里那条导出记录——水印与审计必须成对，只有水印查不到人。

## 7. 对标《个人信息保护法》与等保 2.0

不说"符合"，只说"对应到哪一条、做了什么"：

| 要求 | 本项目的落地 | 局限 |
|---|---|---|
| 个保法 §51 分类管理 | `field_security` 三级（明文/脱敏/加密）+ `secret_level` 五档 | 定密靠规则判定，不是人工逐份定 |
| 个保法 §51 加密脱敏 | 身份证/手机号正则脱敏；证据链只存脱敏快照 | **未做存储加密**，SQLite 文件级无加密 |
| 个保法 §55 影响评估 | 本文件即是 | 无独立评估报告 |
| 等保 2.0 访问控制 | RBAC + ABAC 两层，最小权限（`"[]"` 语义） | 未做强制访问控制（MAC） |
| 等保 2.0 审计 | `audit_log` 只追加；拒绝与导出都留痕；证据链锚定 | 日志未外送独立审计服务器 |
| 等保 2.0 数据完整性 | sha256 哈希链 + 外锚 | 防不住拿到 sqlite 重算全链 |
| 等保 2.0 剩余信息保护 | 导出件水印 + 外传警示 | 内存中的明文不做擦除 |

**没做的不写进论文的"已完成"里。** 最能被追问的三项：存储加密、日志外送、人工定密流程。

## 8. 演示动线（约 90 秒）

1. 管理员登录 → 侧栏「访问策略」→ 规则表 7 条、角色上限 5 档。
2. 试算器选 `property` / `read` / `doc` / 密级 `内部·敏感` → **拒绝，命中 R4**，原因写着"上限为「内部」"。
3. 把角色换成 `community`，只改这一个属性 → 立刻变成**允许**。这一步说明"变的是属性，不是权限点"。
4. 把动作改成 `export` → 允许，但附加动作出现"强制水印 · 写审计"。
5. 切到发文台，导出同一份文件，打开 docx → 页眉有 `王社工 · 幸福社区 · 2026-10-26 14:32 · 导出公文`。
6. 回审计页 → 最后一条就是这次导出。

反例（老师最爱问的一个）：**"物业把权限点全勾上能不能看到社区内部公告？"**
答：`p_li2` 这个账号 `perms_json="[]"` 反而不够——真正要证明的是**属性判定不靠权限点**。R4/R5 用的是角色与密级，管理员把物业的权限点全勾满，`decide()` 依然返回拒绝。这一条在 `smoke_policy.py` ③ 段有断言。
