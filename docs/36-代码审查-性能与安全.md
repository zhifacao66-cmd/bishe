# 代码审查：性能与安全隐患（2026-10-27）

审查范围：`app/`（72 py / 37 html）+ `config.py` + `run.py`。按"能在答辩现场/公网上真出事"排序。
结论：**工程质量明显高于同类毕设**（参数化查询、上传魔数校验、CSP+输出转义、健康检查分档、密钥文件化都做到位了）。
下面的问题集中在三处系统性薄弱点：**公网入口的同步模型调用**、**代理头采信**、**HTTP 状态码语义缺失**。

## P0 — 建议答辩前必修

### 1. 公网匿名入口同步调大模型，全局无拒绝上限（DoS）

**位置**：`app/api/portal.py:206-234`（`/api/portal/report`）→ `Orchestrator().handle_fde()` → `app/llm/client.py:chat()`

**现象**：

- 三档限流全部是**维度限流**，没有全局闸：`report:phone:{phone}` 5 次/60s、`report:ip:{ip}` 30 次/60s。
- 手机号可以随便换，IP 维度依赖 XFF（可伪造，见问题 2）⇒ 两个维度都能绕过。
- `run.py:47` 是 `threaded=True`，Werkzeug **每请求起一个线程**，没有线程上限。
- `LLMGate` 的语义是"排队"（`LLM_QUEUE_TIMEOUT=40`），不是"拒绝"。

**后果**：一串脚本 ⇒ 几百个线程各自阻塞 40s 排队 + 60s 推理 ⇒ 2C2G 机器内存与线程双爆，
同时所有正常用户（含工单接入）的模型调用全部退化到规则桩。这是**一个人能打瘫整个演示**的唯一路径。

**改法**（最小改动，不动现有维度限流）：

```python
# app/api/portal.py  report() 开头，紧接现有两条限流之后
if not _rate_ok("report:global", 30, 60):
    return fail("系统当前提交繁忙，请稍后再试", 429), 429
```

再加一条硬闸：`/api/portal/report` 的 LLM 排队超时压到 8s（居民端不值得为它等 40s，快速降级成规则桩体验更好）：

```python
# Orchestrator.handle_fde(..., queue_timeout=8) 透传给 gate.acquire(timeout=8)
```

> 顺带把 `/api/portal/report` 的耗时预期写进前端提示。规则降级已经存在（消融基线），不会崩。

### 2. 直接采信 `X-Forwarded-For`，IP 维度限流形同虚设

**位置**：`app/api/portal.py:82-84`、`app/auth.py:330-333`

```python
fwd = request.headers.get("X-Forwarded-For", "")
return (fwd.split(",")[0].strip() if fwd else request.remote_addr) or "unknown"
```

**现象**：注释里已经诚实写了"XFF 可伪造、不构成安全依据"，但代码仍然把它当**唯一** IP 来源。
攻击者带 `X-Forwarded-For: 1.2.3.4` 就能让 `report:ip:*`、`query:ip:*`、`login ip` 三条限流全部从零计数。

**后果**：问题 1 的兜底失效；`_deny_log` 与登录失败审计里的"来源 IP"也是假的（取证价值归零）。

**改法**（两条都要）：

```python
# app/__init__.py  create_app 内，install_fast 之前
from werkzeug.middleware.proxy_fix import ProxyFix
if app.config.get("TRUST_PROXY"):
    # x_for=1 = 只信任最近一层代理追加的那一段，攻击者塞的左侧段被丢弃
    app.wsgi_app = ProxyFix(app.wsgi_app, x_for=1, x_proto=1, x_host=0)
```

```python
# 两处 _client_ip 统一成：只读 remote_addr（ProxyFix 已经把可信 IP 写进去了）
return request.remote_addr or "unknown"
```

`TRUST_PROXY` 走环境变量（本机直连=0，ECS/沙箱=1）。**不要**保留"读 XFF 第一段"的兜底——
有了 ProxyFix 之后还读 XFF，等于把刚修好的洞又开回来。

### 3. GET 请求里有写库 + 典型 N+1

**位置**：`app/api/portal.py:167-169`、`119-124`、`321-330`

```python
if t.status != overall:
    t.status, t.updated_at = overall, datetime.now()
    db.session.commit()          # ← GET /api/portal/ticket 里的写
```

**三个独立问题叠在一起**：

1. **GET 有副作用**。`/ticket`、`/ticket/<id>`、`/my` 三个 GET 都会走到这里。
   - 与 `app/fast.py:98` 的 `no-store` 只保护了缓存层，防不住**并发 GET 争 SQLite 写锁**；
   - 违反 HTTP 语义，预取/重试/爬虫都会产生写；
   - `test_client` 连续 GET 会让"读接口"在审计上看不出来是读。
2. **N+1**：`_ticket_payload` = 1 次（items）+ 每项 2 次（orders、ledgers）。一张诉求拆 3 项 = **7 次查询**；
   `/my` 循环 10 张票 = **70 次查询**，且每张票可能各 commit 一次。
3. **渲染函数自己掌握事务边界**：现在 `confirm_ticket` 里是 `commit()` 之后才调 `_ticket_payload`，
   所以暂时没出错；但这是个"谁先谁后决定对不对"的耦合——任何新调用方一旦把 `_ticket_payload`
   放在自己的事务中间，它就会**提前提交**半截写入，之后回滚不掉。
   渲染函数不该有 `commit()`，这是可维护性问题，不是当下的 bug。

**改法**：

- 把状态回写从 `_ticket_payload` 里摘出去，放进**写接口**（`report` / `confirm_ticket`）调用；
  读接口只读。真需要"读时校正"，用一次 `UPDATE ... WHERE status != ?` 单语句，别在渲染函数里 commit。
- `_ticket_payload` 改成批量取：先收集所有 `item_id`，一次 `IN` 查 orders + 一次 `IN` 查 ledgers，在内存里分组：

```python
ids = [it.id for it in items]
orders = {}   # work_item_id -> [WorkOrder]
for o in WorkOrder.query.filter(WorkOrder.work_item_id.in_(ids)).all():
    orders.setdefault(o.work_item_id, []).append(o)
```

`/my` 再把 10 张票的 fde_id 一起 `IN` 查一次 —— 70 次降到 4 次。

### 4. 137 处 `return fail(...)`，只有 10 处带 HTTP 状态码

**位置**：`app/api/*.py`（统计：`grep -c "return fail("` = 137，带 `code=` 的仅 10）

`fail()` 只构造 body（`app/api/__init__.py:8`），漏写第二返回值时 Flask 用 **200** 发出。
`app/api/portal.py` 最典型：

| 行 | 语义 | 实发状态码 |
|---|---|---|
| 217 / 219 / 305 / 307 / 312 | 限流 / 锁定 | 200 |
| 338 / 373 | 越权（应 403） | 200 |
| 316 | 查询不匹配（应 404 或 400） | 200 |

**后果**（这是你们自己的红线 #2，实测确实漏了）：

- 前端 `window.api()` 靠 `code` 字段能正确弹提示，**功能上不炸**；
- 但网关/监控/压测脚本按 HTTP 码统计时，把"被限流"读成"成功"，把"越权"读成"放行"——
  等于**安全事件在监控上看不见**；
- 线上核验用 HTTP 码判路由存在性（docs/27）时，这类接口会给出错答案。

**改法**：本轮只修"安全语义"的 4 类，不必 137 处全改：

```python
# 限流
return fail("提交太频繁，请稍后再试", 429), 429
# 越权
return fail("无权查看该记录", 403), 403
# 资源不存在
return fail("没有查到对应记录", 404), 404
```

`fail(msg, code)` 的 `code` 与 HTTP 码保持一致（现在 `code=404/403` 已经在用，只是 HTTP 码没跟）。

## P1 — 值得修，答辩不致命

### 5. 工单列表的"超期数"用 Python 全量遍历算

**位置**：`app/api/orders.py:209`

```python
overdue = sum(1 for o in base.filter(WorkOrder.status != "done").all()
              if SuperviseAgent.is_overdue(o))
```

`.all()` 把**所有未办结工单的整行**实例化成 ORM 对象再逐条比时间。演示库 41 条看不出来，
量级到 5k 未办结时，**每刷一次列表页**就 hydrate 5k 对象（这条接口还是前端每次筛选都会打的）。
注释里写的"量级远小于全表"只是当下成立。

**改法**：把判据下推到 SQL，只 `count`。`is_overdue` 的阈值必须仍从 `SuperviseAgent` 取（口径唯一）：

```python
now = datetime.now()
overdue = base.filter(
    WorkOrder.status != "done",
    WorkOrder.sla_hours.isnot(None),
).filter(func.datetime(WorkOrder.created_at,
                       func.printf('+%d hours', WorkOrder.sla_hours)) < now).count()
```

若嫌 `datetime()` 在 SQLite 下不好索引，改为"先查阈值分档再 count"：
`for h in (4, 24, 72): count += base.filter(... created_at < now - h).count()` —— 4 次 count，零 hydrate。

### 6. `docs.py` 的 LIKE 没有转义通配符

**位置**：`app/api/docs.py:116-117`

```python
q = q.filter(or_(Notice.title.like(like), Notice.doc_no.like(like), Notice.to_org.like(like)))
```

`app/search.py:62-70` 已经把"`%`/`_` 必须转义 + `escape='\\'`"写成规范（并且写了详细理由），
但这里绕过了它。用户搜 `%` 就变成 `LIKE '%%%'` ⇒ 命中全表 + 索引失效。
同类还有 `app/agents/riskreview.py:250/279` 的 `like(f"%{p}%")`。

**改法**：

```python
from app.search import like_all
cond = like_all([Notice.title, Notice.doc_no, Notice.to_org], kw)
if cond is not None:
    q = q.filter(cond)
```

`riskreview` 那边探针词是内部生成的，风险低，但仍应统一走 `like_any()`，避免下次有人把用户输入接进去。

### 7. 两个列表接口完全没有分页

| 位置 | 查询 |
|---|---|
| `app/api/admin.py:96` | `qs.order_by(User.id).all()` —— 账号列表 |
| `app/api/kb.py:62` | `docs = q.order_by(KbDoc.id).all()` —— 知识库列表 |

### 8. `audit_log` 缺 `(actor, action, created_at)` 索引

**位置**：`app/models.py:213-222`（无 `index=True`），实际库里只有 `ix_audit_created_id(created_at, id)`

`audit_log` 是全站写入最频繁的表（每次 Agent 调用、每次 deny、每次 500 都写），
而 `app/api/portal.py:65-72` 的 `_query_locked()` **每次查进度**都要:

```sql
SELECT count(*) FROM audit_log WHERE actor=? AND action=? AND created_at>=?
```

现在能靠 `created_at` 索引缩小到 30 分钟窗口，勉强够用；但 30 分钟窗口在高频演示下也有几百行，
而这条路是**公网匿名**可触发的。

**改法**：`CREATE INDEX IF NOT EXISTS ix_audit_actor_action_time ON audit_log(actor, action, created_at)`，
放在 `app/auth.py` 现有的 `_ensure_indexes()` 里（那里已经有 `ix_audit_created_id` 的同款写法）。

### 9. 查询码生成的三个边界

**位置**：`app/api/portal.py:91-96`

```python
for _ in range(30):
    code = f"{secrets.randbelow(10 ** 6):06d}"
    if not ResidentTicket.query.filter_by(code=code).first():
        return code
raise RuntimeError("查询码生成失败")
```

1. **循环 30 次 = 最多 30 次查询**（且是在 `_ticket_payload` 那个事务里的额外往返）；
2. 30 次全撞（6 位码全局唯一，票据数逼近 10^6 时）抛 `RuntimeError` → 外层 `except Exception`
   → 返回 `提交失败：RuntimeError`，用户看不懂，而诉求其实已经录进去了（只是没票号）；
3. **全局唯一**而不是"按手机号唯一"，把码空间白白压到 10^6。

**改法**：改成"按手机号维度唯一 + 一次查询取已用集合"：

```python
def _gen_code(phone: str) -> str:
    used = {c for (c,) in db.session.query(ResidentTicket.code)
            .filter(ResidentTicket.phone == phone).all()}
    for _ in range(50):
        code = f"{secrets.randbelow(10 ** 6):06d}"
        if code not in used:
            return code
    raise RuntimeError("该手机号可用查询码已用尽，请联系社区")
```

## 已经做对、请不要在重构中弄丢

这几处是同类项目里最容易做错而你们做对了的，改动代码时要小心别退化：

1. **SQL 全部参数化**：全仓 `grep` 无 `eval/exec/pickle/os.system/subprocess`；
   `text()` 仅用于启动期 DDL 与 `SELECT 1`，且 `f"ALTER TABLE {col} {ddl}"` 的 `col` 来自代码常量表，不是用户输入。
2. **上传防线完整**：`evidence.save_photos()` 依次做 数量上限 → 5MB → **魔数嗅探**（不是看扩展名）→
   **随机文件名落盘**（原名只回显，防止"3栋201身份证.jpg"被目录列出）→ sha256 进证据链。
   再叠加 `MAX_CONTENT_LENGTH=28MB`（Flask 默认不限，这条很关键）。
3. **XSS 双层**：`app/notice/render.py` 全量 `html.escape` 后再套标签 + `app/fast.py:137` 的 CSP
   （`frame-ancestors 'none'` / `object-src 'none'` / `base-uri 'self'`）。
   4 处 `{{ body|safe }}` 依赖 render 是唯一出口——**新增任何"服务端渲染富文本"的入口，必须过 render.py**，
   否则 CSP 里 `script-src 'unsafe-inline'` 会放行内联脚本。
4. **健康检查分档**：`app/api/health.py:232-247` 匿名只给 `status/uptime/db.ok/llm.available`，
   通道地址、pid、`db.error`（常带绝对路径）、`boot_error.log` 全部要登录才给。这条做得很对。
5. **密钥不落代码**：`config.py:18-47` 生产用 `.secret_key` 文件（0600）而非公开默认值，
   且解释了"为什么不用每次随机"（会踢掉所有登录）。
6. **导出件无公式注入**：`app/xlsx.py:139` 所有字符串走 `t="inlineStr"` + XML `escape()`，
   `=cmd` 不会被 Excel 当公式执行；水印/审计也在。
7. **LLM 客户端复用 `requests.Session()`**（`app/llm/client.py:30-32`），而不是每次新建 TCP+TLS。
