## 1. 这一稿修什么

`docs/36` 在 2026-10-27 以"能在答辩现场/公网上真出事"为标准，给公网匿名入口开了 4 个 P0：

| 编号 | 问题 | 后果 |
|:--:|------|------|
| P0-1 | `/api/portal/report` 同步调模型，只有手机号/IP 两个维度限流，没有全局拒绝上限 | 换手机号 + 换 IP 的脚本可占满线程与模型队列，一个人能打瘫演示 |
| P0-2 | `_client_ip()` 直接取 `X-Forwarded-For` 第一段 | 客户端可伪造 IP，IP 限流与审计来源同时失真 |
| P0-3 | `_ticket_payload()` 在渲染函数里改状态并 `commit()`，且逐项查工单/台账 | GET 有副作用、并发 GET 争 SQLite 写锁、`/my` 一页 70 次查询 |
| P0-4 | `fail()` 只构造 body，限流/越权/不存在大量以 HTTP 200 发出 | 网关与监控把"被限流"读成成功，把"越权"读成放行 |

这一稿只修这 4 项，不动业务状态机，不引入 Redis/队列等新基础设施。

## 2. 改法

### 2.1 P0-1：公网提交的三层闸门

`app/api/portal.py:259` 起：

```python
if not _rate_ok("report:global", 30, 60):          # 全局：换手机号/换 IP 也绕不过
    return fail("系统当前提交繁忙，请稍后再试", 429), 429
if not _rate_ok(f"report:phone:{phone}", 5, 60):   # 手机号：真实约束
    return fail("提交太频繁，请稍后再试（同一手机号每分钟最多 5 次）", 429), 429
if not _rate_ok(f"report:ip:{_client_ip()}", 30, 60):  # IP：兜底
    return fail("提交太频繁，请稍后再试", 429), 429
```

在调用 `Orchestrator` 之前再加一道**非阻塞准入**：

```python
_REPORT_SLOTS = threading.BoundedSemaphore(4)   # app/api/portal.py:60
REPORT_QUEUE_TIMEOUT = 8.0                      # app/api/portal.py:63

if not _REPORT_SLOTS.acquire(blocking=False):
    return fail("系统当前提交繁忙，请稍后再试", 429), 429
try:
    result = Orchestrator().handle_fde(..., queue_timeout=REPORT_QUEUE_TIMEOUT)
finally:
    _REPORT_SLOTS.release()
```

- **为什么不是只加全局限流**：30 次/分钟仍然可能对应 30 个并发线程，各自在模型闸门里等 40 秒；线程和内存照样被占住。4 个槽位把"排队"变成"快速拒绝"。
- **为什么匿名请求只等 8 秒**：社区内部可以等 40 秒；居民提交不值得。8 秒拿不到模型就走规则兜底，链路仍然完整。
- 参数链：`portal.report()` → `Orchestrator.handle_fde(queue_timeout=8)` → `ParserAgent.run()` → `llm.client.chat(queue_timeout=8)` → `LLMGate.slot(timeout=8)`（`app/llm/gate.py:103`）。内部入口不传该参数，保持全局 `LLM_QUEUE_TIMEOUT`。

### 2.2 P0-2：只信一层反代写入的 IP

`config.py:66` 新增 `TRUST_PROXY`（默认 `0`），`app/__init__.py:168`：

```python
if app.config.get("TRUST_PROXY"):
    from werkzeug.middleware.proxy_fix import ProxyFix
    app.wsgi_app = ProxyFix(app.wsgi_app, x_for=1, x_proto=1, x_host=0)
```

三处客户端 IP 统一改为只读 `remote_addr`：

- `app/api/portal.py:92`
- `app/auth.py:337`
- `app/admin.py` 注册限流

部署口径：

- 本机直连：不设 `TRUST_PROXY`（默认）。
- ECS / 沙箱在 nginx、网关后面：设 `TRUST_PROXY=1`，由 ProxyFix 只取**最近一层代理**追加的那一段；客户端自己塞在左边的伪造段会被丢弃。
- **不要**在业务代码里再读 `X-Forwarded-For` 第一段，否则等于把刚堵上的洞重新打开。

### 2.3 P0-3：渲染函数只读，状态回写走写路径

`_ticket_payload()` 拆成三层（`app/api/portal.py:117` 起）：

1. `_batch_load(tickets)`：一次取齐多张票的事项、工单、台账；
2. `_payload(...)`：纯组装，**不写库、不 commit**；
3. `_ticket_payload()` / `_ticket_payload_many()`：单张 / 批量入口。

状态回写新增 `app/itemstate.py:90` 的 `sync_ticket_status(fde_id)`，只在写路径调用：

| 写路径 | 位置 |
|------|------|
| 建单 | `portal.report()` 落库后 |
| 居民表态 | `portal.confirm_ticket()` 提交前 |
| 工单流转 | `orderflow.push()`（全站唯一状态变更入口） |

这样：

- GET / 页面渲染不再产生写锁与副作用；
- `/my` 一页 10 张票从约 70 次查询降到 3 次批量查询；
- 居民端展示仍按事项实时计算，不依赖 `resident_ticket.status` 是否及时；
- 分析口径（`risk.py`、`textmine.py` 读 `status`）由写路径保持新鲜。

### 2.4 P0-4：HTTP 状态码与业务码同源

`app/api/portal.py` 的限额/越权/不存在全部补真实状态码：

| 场景 | 改前 | 改后 |
|------|:--:|:--:|
| 提交限流 / 全局繁忙 | 200 | **429** |
| 查询码锁定 | 200 | **429** |
| 非法手机号 / 空内容 / 超长 | 200 | **400** |
| 单据不存在 | 200 | **404** |
| 无权查看 / 无权操作 | 200 | **403** |
| 提交内部异常 | 200（还回显异常类名） | **500**（只回通用文案） |

前端 `window.api()` 只把"非 JSON / 超时 / 断网"当通道失败，HTTP 非 2xx 仍返回 `{code,msg,data}`，因此页面提示逻辑不需要改。

## 4. 已知边界（这一稿不假装解决）

1. **限流与准入都是进程内内存**。多 worker / 多机部署时每个进程各有一份，限额会乘以进程数。当前项目单进程运行；真要横向扩展需换 Redis 令牌桶或独立队列（与 `docs/07` 的结论一致）。
2. **4 个槽位、30 次/分钟是保守默认值**，面向 2C2G 演示机。真实社区按并发调整；不要为了"看起来快"把准入槽位调大，模型吞吐仍由单卡决定。
3. **仍没有 CSRF token**。当前依赖 `SameSite=Lax` + `Sec-Fetch-Site` 拦截跨站写；GET 去写库后，Lax 对顶层 GET 导航的放行不再能被"GET 有副作用"放大。
4. **会话 8 小时硬过期、无滑动续期**，属于演示安排，不是本次 P0。
5. **`_HardenedWSGI` 仍会读 `X-Forwarded-Proto` 给 Cookie 补 Secure**。它只影响"是否给 Cookie 加 Secure 位"，不参与限流与鉴权；HTTPS 部署时与 `TRUST_PROXY=1` 一起使用即可。
6. **MySQL 仍未实测**，与本次改动无关。
7. `smoke_kb` / `smoke_tasks` 的模型依赖未消除；答辩前请拉取 `qwen3:8b` 后复跑，确认 `llm_used=true`。
