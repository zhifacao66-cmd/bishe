# 28 · 安全体检与运维自动化

> 关联：`docs/20`（六类安全问题的修法）、`docs/26`（工程踩坑）、`docs/04 §7.3`（生产与环境边界）
> 脚本：`scripts/audit_all.py`、`scripts/backup_db.py`、`scripts/rotate_password.py`、
> `scripts/git_hooks/pre-commit`

## 1. 为什么要把检查收成一条命令

改造前，"上线前该看什么"散在六个脚本里：

| 脚本 | 管什么 |
|---|---|
| `_review_probe.py` | 逐角色越权（113 项） |
| `smoke_security.py` | 会话 / 限流 / 审计（32 项） |
| `smoke_security_hard.py` | 导出 / XSS 回显（62 项） |
| `_audit_xss.py` | 模板转义（报告"存疑 65 处"） |
| `check_integrity.py` | 数据自洽（16 项） |
| 若干 SQL 手查 | 工单流转 / 事件链 |

问题不是检查不存在，而是**没有一个人会在改动后主动跑六遍**。于是"检查过"慢慢
变成"上个星期检查过"。更糟的是 `_audit_xss.py` 报"存疑 65 处"——一份每行都写
"存疑"的报告，读三行就会被关掉，等于没检查。

所以新加的目标不是"更多检查"，而是**一个能跑、结论可信、几秒出结果的入口**。

```bat
python scripts\audit_all.py                  :: 本机全量
python scripts\audit_all.py --target ecs     :: 线上只读体检
python scripts\audit_all.py --offline        :: 不碰网络
python scripts\audit_all.py --json           :: 给 CI / 存档
```

退出码：有 FAIL 返回 1，否则 0。可以直接挂钩子。

## 2. 五组检查与判定口径

`PASS / WARN / FAIL / SKIP` 四级，**WARN 必须附原因与代价**，SKIP 不算通过。

| 组 | 内容 | 项数 |
|---|---|---|
| A 凭据与密钥 | `.gitignore` 覆盖、已跟踪文件无凭据、源码无硬编码、真实令牌未进文档、`SECRET_KEY` 强度 | 5 |
| B 会话与传输 | HttpOnly / SameSite / Secure 位、生产 DEBUG、生产密钥不回落默认 | 5 |
| C 权限 | 路由守卫覆盖、权限点双向对账、防管理员自锁、**导出三件套**（ABAC 判定 + 水印 + 审计，按 URL 含 `export` 定位端点，函数体内须同时出现 `decide(` / `wm_text(` / `log_export(`） | 4 |
| D 前端 | 模板转义、不重复定义 `esc()`、请求走统一入口、不用原生 Promise 上没有的 `.fail`、`getElementById` 目标存在、每处 `await api` 都有 try/catch 兜底 | 6 |
| E 数据与流程 | 数据自洽 16 项、流转合法性、事件链完整、无重复接单/办结 | 4 |
| F 线上（只读） | 健康、默认口令、传输加密、CSP | 4 |

六组合计 **28 项**。

### 2.1 判定口径的三处修正（都是先错后改）

**① 凭据忽略：不能拿文件名去 `.gitignore` 里搜字符串**

第一版这么写，`llm.json` 与 `data/community.db` 立刻误报 FAIL——因为
`.gitignore` 里写的是 `data/*.db` 这类通配。改成让 git 自己解释：

```python
subprocess.run(["git", "check-ignore", "--no-index"] + paths, ...)
```

修完立刻抓到一个**真缺口**：`llm.json` 确实没被忽略。它存的是发布副本的
隧道地址 + 令牌，一旦在项目根生成就会跟着提交。已补进 `.gitignore`。

**② 权限覆盖：不能用正则看装饰器在哪一行**

`@perm_required` 写在 `@bp.get` **下面**、紧贴函数，所以"只看上方两行"的
正则把 81 个路由全报成裸接口。改用 AST 解析 `decorator_list`，再补一条
"函数体内有 `current_user()` / `APP_TEST` 判断也算守卫"（`/api/admin/me` 与
`/api/health/dbwrite` 就是这种写法）。结果：81 个路由，装饰器守卫 66、
内联守卫 7、裸路由 0。

> **2026-11-03 补全口径（原来的覆盖面是假的）**：`_routes()` 只扫
> `app/api/*.py` + `views.py` + `admin.py`，漏了 `app/portal.py`（居民端 9 条）
> 和 `@bp.patch`（3 条真的改状态：`docs` / `notices` / `weekly`）——134 条路由
> 里只复核了 122 条，"裸路由 0"只对那 122 条成立。改成扫 `app/**/*.py` 并把
> `patch` 纳入方法判断后：**134 个路由，装饰器守卫 108、内联守卫 14、裸路由 0**。
> 同时白名单从"按函数名放行"改成"文件:函数"精确匹配：`report` / `notices` /
> `contacts` / `health` / `me` 在 api 层与页面层是同名函数，按裸名放行等于给
> 同名路由开后门。补全后当场抓到 `/portal/query`（纯表单页，确认公开，已入白名单）。

**③ 模板转义：不能"没看见 esc( 就算存疑"**

`${o.id}`（主键）和 `${l.feedback}`（用户反馈）性质完全不同，前者永远安全。
按字段语义分四类后：

| 类别 | 处数 | 例 |
|---|---|---|
| `esc()` 包裹 | 52 | `${esc(o.feedback)}` |
| 数字 / 枚举字段 | 25 | `${o.id}`、`${t.overdue_hours}` |
| 三元且两分支都是字符串字面量 | 8 | `(S.q \|\| S.line) ? '没有符合条件的…' : '暂无…'` |
| 纯标识符 / 算术 | 26 | `${i}`、`${v}` |
| **真风险** | **0** | — |

第三类值得单独说：`(S.q || S.line) ? '没有…' : '暂无…'` 里的 `S.q` 只参与**条件**，
输出的是固定中文。上一版把它算风险，人复核两遍才敢确认——这类噪声正是
报告被放弃的原因。现在规则化：三元表达式的两个分支都是字面量就判安全。

**这个判断器是验过能失败的**：往 `app/templates/` 放一个
`innerHTML = \`<b>${l.feedback}</b>\`` 的临时模板，D 组报
`1 处用户字段未转义：__audit_probe.html:3 feedback`，退出码 1；同文件的
`${o.id}` 不报。**恒绿的检查比没有检查更危险**，所以每加一条规则都要验证它能红。

### 2.2 一个刻意留着的 WARN

`B3 Cookie Secure 位` 在 HTTP 环境下必然为"未开启"。这不是配置错误：设成 1
浏览器根本不回传 Cookie，登录会假死。报 WARN 而不是 PASS，是为了让"我们还没上
HTTPS"这件事每次体检都被看见一次，而不是被悄悄归类成通过。

## 3. 数据库备份：不能直接复制 .db

`scripts/backup_db.py`。

### 3.1 为什么必须用 `sqlite3.backup()`

SQLite 开了 WAL 后，最近的事务还在 `-wal` 里没 checkpoint。用文件管理器复制
`community.db` 得到的是"上次 checkpoint 时的库"——能打开、看起来正常，但少掉
最新几条工单和审计。**坏备份比没有备份更危险**，因为它让人以为有退路。

`Connection.backup()` 走 SQLite 在线备份协议，WAL 里未落盘的内容一并搬过去。
项目里 ECS 同步和发布快照用的也是它（红线：不替换 `.db` 文件）。

### 3.2 每份备份都过三道自检，不过就删

1. `PRAGMA integrity_check` 必须 `ok`
2. 七张关键表行数与源库**逐个相等**：`work_item / work_order / ledger /
   audit_log / fde_record / field_security / resident_ticket`
3. 能被独立连接打开并查询（模拟恢复时真的读一遍）

任何一项不过就**删掉并报错**，不留下"看起来有"的坏备份。

**这里踩了一个和"镜像断言"同源的坑**：第一版把表名写成 `field_report`
（实际叫 `fde_record`），取数失败返回 -1；源库 -1、备份也 -1，"相等"就通过了。
等于七项里有一项从来没检查过。修法是单独判 `-1`：

```python
broken = [t for t in KEY_TABLES if want[t] < 0 or got[t] < 0]
if broken: 删除并报错
```

> 教训与 `docs/26` 里那条一致：**两边都错就相等，断言等于没有**。
> 表名要以 `sqlite_master` 实查为准，不能凭印象写。

### 3.3 轮转与计划任务

```bat
python scripts\backup_db.py                  :: 备份一次 + 自检 + 轮转（保留 14 份）
python scripts\backup_db.py --list           :: 列出现有备份与完整性
python scripts\backup_db.py --verify         :: 验证最近一份能否恢复
python scripts\backup_db.py --install-task   :: 注册每日 02:00 计划任务
python scripts\backup_db.py --restore <file> :: 复制到 restored-<ts>.db
```

`--restore` **只生成新文件，绝不覆盖现网库**：运行中的 SQLite 文件句柄被占用，
替换会失败或写坏，连接池里还指着旧 inode。恢复是"先验证、再停服、再换文件"
的人工动作，脚本只负责把验证过的文件摆好。

备份目录 `data/backups/` 与 `data/_new_password.txt` 都已进 `.gitignore`——
备份里是完整业务数据，不能进仓库。

## 4. 默认口令：默认只预演

`scripts/rotate_password.py`。

体检的 F2 项会报 `admin/admin123 仍可登录`。这是**真问题**，但直接改会把人锁在
门外（老师正在用这个口令看演示）。所以脚本默认只探测：

```bat
python scripts\rotate_password.py                       :: 预演，不改
python scripts\rotate_password.py --target ecs          :: 预演线上的
python scripts\rotate_password.py --target ecs --apply   :: 真改（交互确认）
```

约束：

- 只走应用自己的 `POST /api/admin/users/<uid>/password`，**不直接改库**——
  改库会绕过审计与哈希逻辑
- 改前先确认旧口令能登录；改后立刻用新口令登录一次，再确认旧口令已失效
- 新口令写到 `data/_new_password.txt`（已忽略），同时打印

**实测过 `--apply`**：副本库 + 独立端口（5010）跑一遍，新口令登录成功、旧口令
失效。改密工具如果没测过就交给用户，等于让人拿真实后台试错。

## 5. 流程：状态机只有一处定义

改造前四个端点各自校验起始状态（`accept` 要 `open`、`finish` 要 `doing`），
`orderflow.push()` 本身不校验。这在当下是对的，但意味着**每个新调用点都要
重新记得校验一次**。将来加个批量办结、或某个 Agent 想直接推进状态，漏写一句
就出现 `done→done` 的重复办结，而流转记录本身看不出异常（它如实记录了两次）。

现在把允许的迁移收进 `push()`：

```python
ALLOWED_FROM = {
    "dispatch": {None, "open"},   # None = 新单尚未落库
    "accept":   {"open"},
    "transfer": {"doing"},
    "finish":   {"doing"},
}
```

非法迁移抛 `ValueError`（编程错误，不降级、不静默修状态）。回归验证：
`smoke_order_flow` 93/93、`smoke_logic` 46/46、`smoke_portal` 80/80、
`smoke_tasks` 32/32 全绿，改动没有误伤。

真实数据侧的体检（E2~E4）用 SQL 直接查，不复用实现逻辑：

- 44 条流转全部落在允许的迁移上
- 事件链 0 处断裂（上一步 `to_status` = 下一步 `from_status`）
- 0 张重复接单 / 重复办结

## 6. 接入点：让检查自己找上门

### 6.1 提交前钩子

`scripts/git_hooks/pre-commit`，启用一次即可：

```bat
git config core.hooksPath scripts/git_hooks
```

只跑 A、D 两组（凭据 + 前端），**实测 0.5 秒**。不跑全量是刻意的：每次都跑
数据一致性，人就会开始用 `--no-verify`，钩子随即形同虚设。挡的就是"把密钥
提交进历史"这种删不干净的错。

### 6.2 生成提交包前

`make_submit.py` 在拷贝之前先跑 `audit_all.py --only A,D`，FAIL 直接中止。
检查放在拷贝**之前**：包已经生成再发现问题，通常会"反正都打了就这样吧"。
`--skip-audit` 可以跳过，但会在日志里留痕。

## 8. 已知边界

- **F2 有副作用**：验证默认口令必然产生登录审计（成功一条 / 失败一条）。这是
  只读体检里唯一的写操作，已在输出口径里写明。其余项都是纯读。
- **Limit 限流是单进程内存**（见 `app/ratelimit.py` 文档串），多 worker 部署时
  限额会变成 `限额 × worker 数`。当前单进程够用。
- **无服务端会话吊销**：Cookie 是签名会话，改密码后旧会话仍有效直到过期。
  要强制下线需要服务端会话表，属另一件事。
- **备份只在被调度的机器上生效**：`--install-task` 注册的是本机计划任务。
  服务器上的备份要在服务器上执行一次（`ecs_deploy_code.py` 不碰计划任务）。
