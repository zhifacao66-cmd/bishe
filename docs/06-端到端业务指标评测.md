# 端到端业务指标评测

> 对应脚本：`scripts/eval_e2e.py`（执行）、`scripts/summarize_e2e.py`（多次汇总）
> 原始数据：`data/e2e_r1~r3.json`、`data/e2e_summary.json`
> 评测时间：2026-10-19　环境：Ryzen 9 7945HX / 16GB / RTX 4060 8GB / Ollama 0.40.5 / qwen3:8b

---

## 1. 为什么单独做端到端评测

`docs/03` 评的是**拆解模型**：给一句话，看业务项拆得对不对（F1 97.9%）。但拆得对不等于业务做对。真实业务链路上还有四个环节可能出错：

1. 拆对了，但**没派单** → 物业不来修，居民投诉
2. 拆对了，但**派错了线** → 工单进了综治，物业根本看不到
3. 建了台账，但**同一户重复建档** → 减负变成加负
4. 全程都对，但**敏感信息在某个环节明文落库** → 保密承诺失效

这些都属于**业务后果**，模型指标看不出来。端到端评测就是测这四件事。

## 2. 评测设计

### 2.1 走真实链路，不做函数级调用

评测不直接调 `Orchestrator.handle_fde()`，而是起一个真实的 Flask 应用，用 `test_client` 登录后走 HTTP：

```
登录(社区) → POST /api/fde
   → 保密审查 → 脱敏落库 → 拆解 → 业务项入库
   → 派单(物业类) ──┐
   → 填报(政务类) ──┤→ 台账
登录(物业) → POST /api/orders/<id>/accept → /finish
   → 物业台账自动归档
登录(社区) → POST /api/reports/generate → 校验报表数字
```

这样权限守卫、数据隔离、状态机、审计留痕都在评测范围内，任何一个环节挂掉都会体现在指标上。

### 2.2 独立数据库，不污染演示数据

脚本在 `import app` 之前把 `DATABASE_URL` 指向 `data/eval.db`，每次运行先删库重建。评测跑的是干净库，演示库 `data/community.db` 一行数据都不动。

### 2.3 语料：24 条，31 个期望业务项

覆盖 7 类业务、6 种句式：

| 类型 | 条数 | 典型样本 |
|---|:--:|---|
| 单事项简单句 | 9 | 「2栋屋顶漏水，物业说上周就报过了还没修好」 |
| 多事项并列句 | 7 | 「11栋电梯困人…；另外消防通道堆了杂物；还有广场舞噪音太大」 |
| 含手机号 | 4 | 「…联系电话13900001111」 |
| 含身份证 | 1 | 「租户赵某身份证320102…，电话137…」 |
| 需复用历史档案 | 2 | 同户二次登记（C03 复用 C01、C22 复用 C13） |
| 跨多条业务线 | 4 | 走访独居老人 + 血压偏高（民政 + 卫健） |
| 纯政务无物业线 | 8 | 街道要台账、低保咨询 |

### 2.4 期望单据由标注推导，避免自相矛盾

人工标注只写业务项和它的去向业务线：

```python
{"type": "报修", "lines": ["物业"], "kw": ["电梯"]}
```

期望单据按业务规则自动推导：

- `lines` 含 `物业` → 1 张工单
- `lines` 中每个非物业线 → 1 条台账（与 `FillAgent` 的实现一致）

这样就不会出现「标注说该派单、但规则说不该派」的矛盾。24 条语料推导出 **11 张工单 + 24 条台账 = 35 张期望单据**。

### 2.5 匹配算法：关键词 + 贪心最大匹配

不做字符串全等——模型生成的 `subject` 措辞每次都会变（「电梯损坏」/「电梯故障」）。改为给每个期望项配 2~3 个**区分性关键词**，按命中数贪心匹配，一条实际单据只能被匹配一次。

对台账额外要求 `line` 相同才算匹配，避免把「民政台账」错配给「卫健台账」。

### 2.6 重复 3 次

`temperature=0.2` 仍有随机性。连续跑 3 次，报均值与范围，不只报最好的一次。

## 4. 逐项解读

### 4.1 漏派单率 0% —— 这是最重要的一个数

拆解 F1 97.9% 是「平均意义上对」，但业务最怕的是**漏**：漏掉一张工单，就是一次没被处理的报修。三次运行、11 张期望工单，**一张没漏、一张没多派**。

原因不是模型运气好，而是结构上排除了这个错误：
- 拆解用 JSON Schema 约束，`target_lines` 是枚举，模型不可能输出「物业公司」这种非枚举值；
- 派单判据是 `"物业" in target_lines`，是确定性代码，不是模型再判一次；
- 因此只要拆解把「物业」判对，派单就不会漏。

**残差风险**：如果模型把报修类误判成「综治」（拆解层错误），派单仍会漏。本次语料中未出现，但这是真实风险，见第 7 节。

### 4.2 误派单率 0% 不等于「永不多派」

误派单率只看工单。台账的多建是 4 条（见 4.3），其中一部分本质上是「同一个事项多送了一条业务线」。工单没出现这个问题，是因为语料里物业线边界清晰（电梯、门禁、漏水、水压）。

### 4.3 多建档率 14.3%：4 条多建，0 条真重复

台账 P 85.7% = 24 TP / (24 TP + 4 FP)。这 4 条多建**必须拆开看**，否则会误判成「系统重复建档」：

| 归因 | 次数（3 次均值） | 业务含义 | 是否缺陷 |
|---|:--:|---|---|
| 拆解过度拆分传导 | 1.3 | 「电梯坏了，老人下不了楼」被拆成报修 + 隐患排查，多出一条综治台账 | 是（可接受的多做） |
| 单事项跨线分派 | 2.7 | 「精神障碍患者情绪不稳」同时落卫健（随访）和民政（救助） | 否（业务上两条线都该有记录） |
| **同线同事项真重复** | **0** | — | — |

关键判据是 `dup_in_fde`：**同一 FDE 内、同一业务线、同一 subject 出现两次以上**。三次运行该值恒为 0，说明复用去重逻辑（`room_key` 特征匹配 + 同线查重）在端到端链路上确实生效，没有出现「减负系统反而让人重复填表」的反效果。

> 论文里应写「多建档 14.3%，其中真重复 0，其余为跨业务线分派与拆解粒度差异」，不能只写 14.3% 一个数。

### 4.4 保密：召回 100%，库内明文 0 处

两个层次都测了：

1. **返回值层**：5 个标注 PII（4 个手机号 + 1 个身份证）在 `masked_text` 中全部被遮蔽，明文泄露 0 处。
2. **存储层**：直接扫库，覆盖 7 个可能落文本的列——`fde_record.raw_text`、`work_order.content/feedback`、`ledger.content_json`、`report.data_json`、`audit_log.input_digest/output_digest`，用手机号/身份证正则全表匹配，**命中 0 处**。

第 2 层是重点。很多系统只测「返回给前端的是不是脱敏文本」，但数据其实已经明文进了库。本系统在**入库前**脱敏（`Orchestrator` 第 ① 步先跑保密审查，第 ② 步才落库），所以存储层也是干净的。

### 4.5 闭环率 100%、孤儿业务项 0

- 11 张工单全部走完 `open → doing → done`，且每张完成后自动生成 1 条物业线归档台账（库内 39 = 28 自动 + 11 归档，账对得上）。
- 32 个业务项全部至少挂上一张单据（工单或台账），**孤儿率 0**——不存在「拆出来了但没人接」的事项。

### 4.6 报表一致性

`POST /api/reports/generate` 生成的月报数字为 24 / 32 / 11，与库内实际计数完全一致（3 次全 True）。报表 Agent 是聚合查询，不是另存一份快照，避免了双重口径。

### 4.7 耗时 2.14s（P50）

拆解本身约 1.5s（`docs/03`），端到端多出约 0.6s，花在：保密正则 + 业务项/工单/台账多次 `commit` + 每个 Agent 写审计。P95 3.88s，最大出现在长句（C16 三事项）。

对社工使用场景，2 秒是可接受的：比手工在 3 个系统里各填一遍快得多，且不用切换界面。

## 5. 评测发现并修复的 3 个真实缺陷

**这部分是本轮评测最有价值的产出**——三个缺陷都不是「指标不够高」，而是逻辑错误，靠模型评测永远发现不了。

### 缺陷 1：身份证被手机号正则截断（保密失效）

首次运行保密召回只有 **80%**，逐条追查定位到：

```
原文：租户赵某身份证320102199003074512，电话13712345678
旧输出：320102199****74512   ← 身份证只遮了 4 位，14 位仍可读
```

原因：手机号正则 `1[3-9]\d{9}` 先执行，命中了身份证中段的 `19900307451`，把它替换成 `199****7451`；身份证被打碎后，`\d{17}[\dXx]` 再也匹配不上，于是只对被破坏的残串做了局部遮蔽。

修复（`app/agents/security.py`、`app/agents/base.py`）：

```python
# 身份证（18位，强特征）必须先于手机号（11位，弱特征）匹配
PATTERNS = {
    "身份证": (re.compile(r"(?<!\d)\d{17}[\dXx](?!\d)"), ...),
    "手机号": (re.compile(r"(?<!\d)1[3-9]\d{9}(?!\d)"), ...),
}
```

修后：`320102********4512` + `137****5678`，召回 100%。

**这个 bug 在演示时肉眼看不出来**——页面上显示的是「已脱敏」，实际仍能看到大部分身份证号。只有把「库内明文扫描 + 逐条 PII 核对」写进评测才会暴露。

### 缺陷 2：工单内容带了整段首录原文（违反最小必要）

原实现把 `masked_text`（整段话）作为工单内容推给物业。问题有两个：

- 一句话里如果同时有「501 室新增租户」和「电梯坏了」，物业会看到人口登记信息，超出工单必要范围；
- 物业端一屏只能看到一张工单，内容却是三件事的混合，现场人员分不清要修哪个。

修复：工单内容改为**本业务项的 `subject`**（如「8栋2单元电梯损坏」），并在 `DispatchAgent` 里加了一层正则兜底脱敏，防止上游漏处理。

### 缺陷 3：审计日志写入未脱敏原文（合规风险）

`BaseAgent._audit()` 把 Agent 的输入原文截断 250 字后直接写 `audit_log.input_digest`。`SecurityAgent` 的输入正是**脱敏前**的原文，于是手机号、身份证明文绕过脱敏进了审计表——等保检查里这是典型的不合格项。

修复：在 `_audit()` 落库前统一做敏感值遮蔽（先脱敏再截断，顺序不能反，否则截断会把号码切半导致漏检）。修复后库内明文扫描 7 个列全部 0 命中。

> 这三个缺陷的共同点：**都不是「模型不行」，而是工程实现没接住**。这也是为什么端到端评测必须单独做。

## 6. 减负成效：口径、公式与边界

### 6.1 口径

不用「节省多少分钟」这类需要访谈取值的指标（无法复现，容易被质疑），改用**可计算的单据动作数**：

| 量 | 取值 | 说明 |
|---|---|---|
| 首录次数 | 24 | 社工对系统说 24 段话 |
| 期望单据数 | 35 | 11 张工单 + 24 条台账（按标注推导） |
| 人工基线 | 24 + 35 = **59 次录入** | 传统方式：先在纸上/群里记一次，再分别填每张表、发每条派单 |
| 系统实际 | **24 次录入** | 一段话一次，后续全自动 |
| 减少 | **59.3%** | 35 / 59 |

用**期望单据**而不是系统实际产出的 50 张做基线，是刻意保守：系统多建的 4 条台账不该被算成「人工本来也要做的事」，否则减负幅度会被虚增到 67.6%。

### 6.2 必须说清的边界

- 这是**录入动作**的减少，**不是工时**的减少。没有测「找政策文件、打电话催办、核对数据」的时间。
- 假设「每张单据传统方式下都需要独立录入一次」。若某社区已有工单系统能自动流转，基线会下降，减负幅度也随之下降。
- 台账跨线分派（一个事项落两条线）在传统方式下也要填两张表，所以计入基线是公平的。

答辩时若被问「59.3% 怎么来的」，直接给 `24 / 35 / 59` 三个数和公式即可，不要含糊成「大概省一半」。

## 7. 稳定性与波动

| 指标 | 3 次是否一致 |
|---|---|
| 工单 F1 / 漏派 / 误派 | 完全一致（100 / 0 / 0） |
| 台账 F1 / 漏建 / 真重复 | 完全一致（92.3 / 0 / 0） |
| 保密召回 / 库内明文 | 完全一致（100% / 0） |
| 闭环率 / 孤儿率 / 报表一致 | 完全一致 |
| 业务项数 | 32 / 32 / 33（波动 1 项） |
| 业务项 F1 | 96.9 ~ 98.4（波动 1.5pp） |
| 耗时 P50 | 2.08 ~ 2.24s（波动 7%） |

结论：**结构性指标（派单、建档、保密、闭环）高度稳定**，波动只出现在「一句话拆几项」的边界判断上（如「老人下不了楼」算不算独立事项）。这与 `docs/03` 的结论一致——拆解粒度的分歧是当前系统唯一的不确定性来源，且方向是「多做」而非「漏做」。

## 8. 局限（如实记录）

1. **语料规模 24 条、单人标注**。比 `docs/03` 的 43 条少，因为端到端每条要跑完整链路。论文定稿前建议扩到 50 条并双人标注。
2. **物业反馈是模拟的**。脚本统一提交「已现场处理完毕」，只验证状态机与归档逻辑，**不代表真实处理时长**。工单闭环率 100% 是「流程能走通」，不是「物业都按时修完了」。
3. **未测并发**。`test_client` 串行执行，单机单用户。真实社区多社工同时录入时，SQLite 写锁、Ollama 请求排队都会影响耗时。
4. **未测长稳**。没有连续运行 24 小时观察内存增长（Ollama 的 `keep_alive` 与 Flask 进程都未做长稳测试）。
5. **台账「多建」的判定依赖标注粒度**。「精神障碍患者」标一条线还是两条线，本身有业务解释空间。本文按「标注线数」严格判定，同时单独给出「真重复 0」，读者可自行取舍。
6. **PII 类型只覆盖手机号与身份证**。地址、姓名、病历号、银行卡号均未纳入正则，真实场景需要扩充规则库（或接 NER 模型）。

## 9. 复现方式

```bash
# 前置：Ollama 已启动且 qwen3:8b 可用
python scripts/eval_e2e.py            # 单次，约 70 秒
python scripts/eval_e2e.py --limit 5  # 调试用

# 3 次重复 + 汇总
for i in 1 2 3; do
  python scripts/eval_e2e.py > logs/e2e_r$i.log 2>&1
  cp data/e2e_report.json data/e2e_r$i.json
done
python scripts/summarize_e2e.py
```

产物：
- `data/e2e_report.json` — 单次完整明细（每条语料的耗时、业务项、单据差异）
- `data/e2e_r1~r3.json` — 3 次原始结果
- `data/e2e_summary.json` — 均值/范围汇总
- `data/eval.db` — 评测库（可随时删除，脚本会自动重建）
