# 状态可见性与启动韧性

这一份记录两个**同源**的问题：界面说了句其实不成立的承诺，以及一次"应用起不来"
导致的发布失败。它们看起来一个在前端、一个在部署，根因却是同一个——
**状态是从别处抄来的，不是从事实算出来的**。

## 1. 左下角那行"本地大模型运行中"

### 1.1 现象

侧栏底部一直是一颗绿点 + "本地大模型运行中 / qwen3:8b · 数据不出内网"。
把 Ollama 停掉、把模型删掉、把隧道断掉，它照样是绿的。

因为它是模板里写死的一行字：

```html
<div class="side-foot"><span class="dot"></span>本地大模型运行中<br>
  {{ config.LLM_MODEL }} · 数据不出内网</div>
```

`config.LLM_MODEL` 只是"配置里写的模型名"，跟"这个模型现在能不能用"没有任何关系。

### 1.2 为什么这比"没有指示灯"更糟

指示灯存在的意义是让人**不必**去验证。它一旦会骗人：

- 模型降级时页面替模型报平安，值班的人会先去怀疑自己的操作，而不是去查通道；
- 演示时评委问"它现在真在跑吗"，你只能说"应该吧"；
- 更隐蔽的：系统里已经有真正的状态（`/api/health` 的 `llm.available`、
  `probe` 的失败原因、`gate` 的槽位），做了一次真实的探活，却在最关键的位置
  显示了一个常量。

所以这条的验收标准不是"有状态灯"，而是**把模型断电后灯必须红**。

### 1.3 改法

`app/api/health.py:llm_badge()` 是唯一的状态出口，页面首屏和轮询接口都用它：

| 状态 | 点 | 标题 | 副标题（本机 / 隧道） |
|---|---|---|---|
| `ok` | 绿 | 本地大模型运行中 | `qwen3:8b · 数据不出内网` / `· 加密隧道回本机 GPU` |
| `bad` | 红 | 模型未连接 · 已降级 | `通道连不上 · 走规则路径` |
| `idle` | 灰（呼吸） | 模型状态检测中 | `qwen3:8b · 等待首次探活` |

三个设计决定：

1. **首屏由服务端渲染**，不是等 JS 才出现。否则刷新瞬间永远是"检测中"，
   等于把"真的"又变成"看起来很真"。
2. **轮询只读缓存**（`GET /api/health/llm`，20 秒一次，`document.hidden` 时不轮）。
   真正的探活放在后台线程里补。远程通道 TLS 握手实测 9~26 秒，把它放进
   渲染路径就是让每个页面都可能卡半分钟——状态晚 20 秒能接受，页面卡 20 秒不行。
3. **后台探活必须带 app context**。`probe()` 经 `channel.resolve()` 读
   `current_app.config`，在线程里没有上下文会抛 `RuntimeError`。第一版就栽在这里：
   异常被 `except` 吞掉，表现是"计时器永远不过期、灯永远检测中"，
   看着像前端坏了，其实是后端没跑起来。

### 1.4 "数据不出内网"这句话要跟通道走

本机 `127.0.0.1` 直连时它成立；线上是"云 Flask → cloudflared 隧道 → 本机 GPU"，
数据确实出了本机，只是**只回自己那台机器**。同一句话在两种部署形态下说，
在答辩现场是会被追问的。所以：

- 本机通道 → `数据不出内网`
- 隧道通道 → `加密隧道回本机 GPU`

宁可句子长一点，也不要一句听起来更漂亮但边界模糊的承诺。

### 1.5 顺手补的两处

- 侧栏多了"查看状态详情 →"（仅 `user.manage`），把 `idle/bad` 之后的下一步给出去了；
- 从 `ok` 掉到 `bad` 时控制台 `warn` 一次，常态轮询不弹窗。

### 1.6 断言

`scripts/smoke_llm_badge.py`（19 项）。核心几条：

- 未登录 401，且响应里不出现模型名；
- 模型不通 → `state=bad`，页面 HTML 里**不能**出现"本地大模型运行中"；
- 模型通 → `state=ok`，且首屏就是绿的（不是等 JS）；
- 隧道通道 → 不许出现"数据不出内网"；
- 缓存过期 + 指向黑洞地址时，接口仍 < 300ms、页面仍 < 800ms。

## 2. 一次发布失败：库坏了，进程就起不来

### 2.1 发生了什么

发布返回 `SITES_START_FAILED`：

> service did not become reachable on port 3000 within 60s

`app stderr` 里是一段 SQLAlchemy 连接池的 traceback。发布沙箱的 `data/` 是
**持久卷**，部署只换代码不换库；卷上的 `community.db` 一旦在写入途中被强杀成
`file is not a database`，下一次启动就会在这里炸。

炸的位置很关键：`create_app()` 里 `tune_sqlite(app)` 的
`engine.connect()` 是**第一个**碰库的地方，而且当时不在任何 `try` 里：

```
tune_sqlite(app)     # ← 这里抛 DatabaseError
init_auth(app)       # ← 后面的建表、补列、种子账号
```

于是 `create_app` 抛异常 → 进程退出 → 平台认为"服务没起来" → 分享链接打不开。

### 2.2 真正的病灶：修库的入口全在应用里

`/api/health/db-check`、`data/.reset_db` 标记、`community.db.seed` 覆盖——
这些自救手段都需要应用**先起来**。应用起不来，它们一个都用不上，
只能改代码重新发布。这是典型的自锁：故障把修复通道一起关掉了。

所以这一条的正确目标不是"别让库坏"（做不到），而是
**库坏了也要先把进程拉起来**。

### 2.3 改法：自愈优先，起不来其次

`app/__init__.py:_boot_database()`：

```
tune_sqlite + init_auth
  ├─ 成功 → 正常启动
  └─ 失败 → 记一行可读结论
       ├─ 错误是"文件坏了/打不开"（malformed / not a database / disk i/o /
       │  unable to open database file）且存在 community.db.seed
       │    → 删 -wal -shm、原库备份为 .bak、种子库覆盖、engine.dispose()、重试一次
       └─ 否则 → 降级启动（不抛）
```

三条约束：

1. **只在"文件本身坏了"时才覆盖**。普通锁冲突、超时、约束错误绝不碰数据——
   自愈的破坏力等于删库，触发条件必须窄到只认文件级损坏。
2. **先备份再覆盖**（`community.db.bak`）。坏库也可能还能捞出数据。
3. **降级启动必须留下证据**：`[db][FATAL] …` 打到 stdout 首行，同时落
   `data/boot_error.log`。因为沙箱只看得到 stderr 的一小段，
   完整 traceback 常被截在中间，真正那句理由正好被切掉——这是这次排查最费时间的地方。

健康接口随之多了一个 `boot` 字段（仅登录后可见）：启动是否自愈过、最近一条结论。
另外 `seed_org_contacts()` / `init_kb_docs()` 也各自包了 `try`，
它们在库不可用时同样会挂，不能在最后一步把进程带走。

### 2.4 断言

`scripts/smoke_boot.py`（18 项），每个用例起**独立子进程**——
`config.py` 在类体里读 `DATABASE_URL`，同一进程里改环境变量改不动它
（第一版就是这么假绿的），必须换进程，这恰好也等于线上的"一次部署"。

- 坏库 + 有种子 → 起得来、库被换成可读的、留了 `.bak`、登录与首录台都 200、
  健康页记得这次自愈；
- 坏库 + 没种子 → **仍然起得来**（退出码 0）、健康检查 200 且如实说 `db.ok=false`、
  `boot_error.log` 里有一行含 `not a database`；
- 好库 → 不生成 `.bak`、不写 `boot_error.log`、表与行数不变；
- `.reset_db` 标记 → 换库、写 `.done`、重复部署不二次重置。

### 2.5 复盘：这次发布为什么"看起来"更难查

1. 失败信息只说"没在端口上响应"，与真正的原因（库坏了）隔了 60 秒和一个进程生死；
2. `app stderr` 是截断的，头部被安装日志占掉，尾部又被 traceback 帧占掉；
3. 本地一切正常——同一份代码、同一个库快照，本机 `PORT=3011 python main.py`
   秒起。差异只在持久卷，而它远端不可见。

所以第 3 节的两条（`boot_error.log` + 健康页 `boot` 字段）不是锦上添花，
是让下一次同样的故障能在**一个 HTTP 请求**里被看清。

## 3. 冷启动：第一次调用会超时

线上第一次真正推理要先把 4.7GB 权重读进显存（`keep_alive=30m`，闲置 30 分钟卸载）。
这一次调用超过托管平台前置网关的 60 秒硬上限，前端看到的是空白/超时；
紧接着再调一次，871ms 就返回（实测 `3栋2单元声控灯故障`）。

**这不是故障，是冷启动**。演示前先点一次「系统状态 → 模型自检」预热，
之后整场都在 `keep_alive` 窗口内。这一点写进 `docs/09-演示脚本.md` 的开场。
