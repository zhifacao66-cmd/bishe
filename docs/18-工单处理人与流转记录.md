# 18 · 工单处理人与流转记录

> 关联：`docs/01` 总体设计、`docs/04` 角色权限、`docs/17` 严谨性加固
> 代码：`app/models.py`（`WorkOrder` / `WorkOrderLog`）、`app/orderflow.py`、
> `app/api/orders.py`、`app/templates/orders.html`
> 测试：`scripts/smoke_order_flow.py`（93 项）

---

## 1. 问题：只知道"物业办的"，不知道"谁办的"

原来的工单表只有 `property_co`（单位）和 `feedback`（一段自由文本）。
一段工地出问题要追责时，能拿到的信息是：

```
工单 W20260904-094051-53  已完成
幸福里物业  已用同色地砖更换并做防滑处理……
```

这句话无法回答三个最基本的问题：

1. **谁**接的单？
2. 中间有没有换人？换给了谁？
3. 谁最终办结的？

`feedback` 里也许写了"张三师傅上门"，但那是**人写的散文**，不是可查询的字段：
按人统计工作量做不到，换班后对了半天账也对不上，出事故时更没有可核验的记录。

所以补两样东西：**处理人字段** + **流转记录表**。

---

## 2. 为什么不能只加几个字段

最省事的做法是给 `work_order` 加 `assignee`（处理人）就完事。但一张单会换手：

- 李经理接单 → 当天请假 → 转给赵师傅 → 赵师傅办结
- 两个人分头处理，最后一个人填反馈
- 办结后居民不满意，重开再办一次

**字段只能记住"最后一个"**。上面第一种情况，`assignee` 最后会变成赵师傅，
"这单原来是谁接的"永久丢失——而追责要的恰恰是每一步。

所以拆成两层：

| 层 | 表 | 存什么 | 回答什么问题 |
|---|---|---|---|
| 当前状态 | `work_order.assignee` / `assigned_at` / `done_at` | 此刻归谁、什么时候接的、什么时候办完 | 列表页扫一眼：这单现在谁在办？ |
| 历史 | `work_order_log` | 每一步 action + 谁 + 什么时候 + 说明 | 追责与对账：这单经历过什么？ |

两者不重复：字段是"现在"，日志是"经过"。转派时字段被覆盖，日志只会多一行。

## 3. 表结构

```python
class WorkOrder(db.Model):
    ...
    assignee    = db.Column(db.String(32))   # 处理人姓名（快照）
    assignee_id = db.Column(db.Integer)      # 账号 id
    assigned_at = db.Column(db.DateTime)     # 接单时刻
    done_at     = db.Column(db.DateTime)     # 办结时刻


class WorkOrderLog(db.Model):
    __tablename__ = "work_order_log"
    id          = db.Column(db.Integer, primary_key=True)
    order_id    = db.Column(db.Integer, db.ForeignKey("work_order.id"), index=True)
    order_no    = db.Column(db.String(32))   # 冗余：查日志不必 join
    action      = db.Column(db.String(16))   # dispatch/accept/transfer/finish
    from_status = db.Column(db.String(16))
    to_status   = db.Column(db.String(16))
    actor       = db.Column(db.String(32))   # 姓名（给页面看）
    actor_id    = db.Column(db.Integer)      # 账号 id（改名/停用后仍可对上人）
    actor_org   = db.Column(db.String(64))
    detail      = db.Column(db.Text)         # 反馈 / 转派说明
    created_at  = db.Column(db.DateTime, default=datetime.now, index=True)
```

两个设计取舍值得说明：

**① 姓名快照 + 账号 id 两个都存。**
只存 id，账号改名后历史记录会跟着变（"当时明明是李经理"）；只存姓名，
两个同名的人就分不开，账号停用后也查不到是谁。两个都存，各管一头。

**② 日志永不 update。**
`work_order_log` 只追加。工单被删也不删日志——删掉的单子恰恰更需要留痕。
这也是为什么 `order_no` 要冗余存一份：工单没了，日志还能独立读。

## 4. 状态变更与留痕绑死

`app/orderflow.py` 是唯一的写入口：

```python
ACTIONS = {
    "dispatch": ("open",  "派单"),
    "accept":   ("doing", "接单"),
    "transfer": ("doing", "转派"),
    "finish":   ("done",  "办结"),
}

def push(order, action, actor="", actor_id=None, actor_org="", detail="", at=None):
    to_status, _ = ACTIONS[action]
    log = WorkOrderLog(... from_status=order.status, to_status=to_status ...)
    order.status = to_status          # ← 改状态
    db.session.add(log)               # ← 留痕，同一行代码里做
```

关键在于**改状态和写日志在同一个函数里**。如果让各处自己写
`o.status = "doing"`，迟早有人只做前一件事：状态变了、日志里查不到是谁推的，
而且**不会报错**——这种"静默断链"是最难查的一类问题。现在代码里没有任何
裸的 `o.status = ...`（`grep -n "o.status =" app/api/orders.py` 只在 push 内部）。

`push()` 不 commit，交给调用方和自己那批写入一起提交，避免出现
"日志写进去了、业务改动回滚了"的鬼记录。

## 5. 三条硬规则

### 5.1 处理人取会话身份，不读前端

```python
o.assignee = u.name          # current_user()，不是 data["assignee"]
```

处理人是追责依据。允许前端指定，等于允许任何人以别人的名义接单办结。
`smoke_order_flow` 里有一条专门测这个：请求体里塞 `{"assignee": "冒名的人"}`，
落库必须是登录者本人。

首录的 `creator`、审计的 `actor` 都是同一个道理。

### 5.2 转派只转给本单位在职的人

```python
_find_handler(o, name)  # role=property + status=active + org == o.property_co
```

自由文本填转派对象，一个错字就让单子转给"不存在的人"：之后既没人认领，
也查不到是谁转的（`docs/17` 里任务受派单位踩过同一个坑）。
转派失败时接口会把可选的人列出来，不让用户猜。

还有两个坑写进了代码：

- `User.org == o.property_co` 在 `property_co` 为 `None` 时会变成 `IS NULL`，
  把"没填单位"的账号全匹配进来 → 先判断 `property_co` 非空。
- 转给自己 → 明确拒绝"无需转派"，而不是默默写一条没有变化的日志。

### 5.3 转派不动接单时间

`assigned_at` 记的是"这张单什么时候开始被处理"。转派时**不重置**，
否则换个手 SLA 就自动复活，超期统计直接失真——这是 `docs/14` 那类
"数字静默出错"的又一变种。

同理，办结时如果办结人 ≠ 接单人（交接班），`assignee` **保留接单人**，
办结人写在流转记录的 `actor` 里。字段记"谁接的"，日志记"谁办的"，两者都对。

## 6. 处理时长的口径

```python
handle_hours = (done_at - assigned_at).total_seconds() / 3600
```

**只在两个时刻都存在时才算**，缺一端返回 `null`，前端显示不显示都行。
绝不拿 `created_at` 顶上去——那算的是"从派单到办结"的总时长，
和"维修工干了多久"是两个指标，混用会让"平均处理时长"虚高一截。

老工单（升级前办结的）没有 `assigned_at`，所以耗时是 `null` 而不是 `0.0`。
`0` 会被平均进去，变成"平均 3 分钟办结"这种明显的假数据。

## 7. 接口

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/orders` | `order.view` | 列表，`items` 里带 `assignee` / `assigned_at` / `done_at` / `handle_hours`；`q` 支持按处理人搜 |
| GET | `/api/orders/<id>` | `order.view` | 详情 + `events`（完整流转链，按时间正序） |
| GET | `/api/orders/handlers` | `order.handle` | 可转派的人（本单位 property + active），回 `{items, counts}` |
| POST | `/api/orders/<id>/accept` | `order.handle` | open → doing，落 `assignee` / `assigned_at` |
| POST | `/api/orders/<id>/transfer` | `order.handle` | doing → doing，改 `assignee`，`assigned_at` 不变 |
| POST | `/api/orders/<id>/finish` | `order.handle` | doing → done，落 `feedback` / `done_at` |

`handlers` 只回姓名、账号名、单位三个字段，不回手机号——选人不需要联系方式。

## 8. 页面

- 列表新增**处理人**列：姓名 + 接单时间小字；没有就显示 `—` 并带
  `title="历史工单未记录处理人"`，不留空白（空白会让人以为是页面没渲染）。
- **工单号可点**，打开流转记录弹窗：状态 / 处理人 / 时限 / 处理耗时 + 时间线。
  时间线按事情发生的顺序读（正序），最后一个节点高亮。
- `doing` 状态的操作列多一个**转派**按钮；只剩自己一个账号时，
  前端直接提示"只有当前这一个处理人账号"，不让用户选完再报错。
- 工单号点击用 `CUR` 数组查数据，不往 `onclick` 里拼姓名字符串——
  姓名里有引号就会把整段 JS 弄坏。

## 9. 数据与演示

`scripts/seed_demo.py --reset` 重建演示库时会：

- 每张单补一条 `dispatch`（"派单Agent"）
- 办结的单补 `accept` + `finish`，**三成的单中间插一条 `transfer`**
  （否则"转派"这个功能演示时看不到）
- 处理人按 `幸福里物业` 的两个账号轮转（李经理 / 赵师傅）
- 所有事件的 `created_at` 用业务时间（派单 → 1h 后接单 → 3~30h 后办结），
  不是"跑脚本的此刻"

升级前已经存在的工单，`assignee` 留空、日志为空。**不回填**——审计里记的
`actor` 是"幸福里物业"这个单位名，把它填进"处理人"列等于用单位名冒充人名，
比留空更误导。页面会说明"早期工单没有逐步留痕"。想让演示数据完整，
重跑一次 `seed_demo.py --reset` 即可。

## 10. 已知边界

| 边界 | 影响 | 为什么先不做 |
|---|---|---|
| 没有 `reopen`（打回重办） | 居民不满意只能新开一单 | 需要配套居民评价入口，属功能扩展 |
| 没有多人协办（一单多处理人） | 只能有一个"当前处理人" | 日志里能看到交接过程，够用；真要多人得加联表 |
| 转派不限次数 | 理论上可以来回踢皮球 | 日志会全部记录，踢皮球本身就是可查的证据 |
| 处理人不能批量指派 | 逐单操作 | 演示规模（百级工单）用不上 |
| 工作量统计未做 | 没按人出"人均办结量" | 数据已具备（`assignee_id` + `done_at`），是报表层的事，不在本轮范围 |

## 11. 测试

`scripts/smoke_order_flow.py`（**93 项**，独立库 `data/smoke_orders.db`）：

| 分组 | 验什么 |
|---|---|
| 1 派单留痕 | 派单就写一条 `dispatch`，此时还没有处理人 |
| 2 接单 | 处理人是登录者本人（前端传"冒名的人"无效）、状态迁移、重复接单被拒 |
| 3 转派 | 查无此人 / 异单位 / 转给自己全部被拒；成功时 `assigned_at` **不变** |
| 4 办结 | 谁办结记谁；交接班时接单人不被覆盖；已办结不能再接单/转派/办结 |
| 5 处理耗时 | 真实接单时间算（约 10h）；老单没有接单时间时是 `null` 不是 `0` |
| 6 详情 | 流转按正序、带中文动作名/操作人/时刻；历史老单不报错、流转为空 |
| 7 列表 | 带处理人字段、可按人搜、搜索只改 `matched` 不改 `total` |
| 8 权限 | 街道能看不能办；社区不能办；异单位物业看不到也动不了别家单 |
| 9 名单 | 只给本单位、不含异单位、不含手机号、`{items,counts}` 包装 |
| 10 日志 | 事件顺序正确、操作人各自独立、`order_no` 齐全、条数与动作数一致 |
