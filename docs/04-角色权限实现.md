# 04 · 三角色登录与权限实现（F9）

> 对应《总体设计》2.2 角色权限矩阵的落地实现。
> 代码：`app/auth.py`（认证与 RBAC）、`app/views.py`（页面守卫）、`app/api/*.py`（接口守卫）
> 测试：`scripts/smoke_auth.py`（40 项断言）、`scripts/smoke_tasks.py`（31 项断言，含任务下发与行级隔离）

---

## 1. 设计原则

| 原则 | 落地方式 | 为什么这么做 |
|------|----------|--------------|
| **最小必要** | 物业拿不到 FDE 原文与人口台账；街道拿不到居民明细 | 保密场景下，"能看到"本身就是风险，不是"看到了不乱用"就够 |
| **权限点而非角色硬编码** | 用 `ledger.view`、`order.handle` 等功能点，角色只是集合 | 新增角色（如网格员）只改 `ROLE_PERMS` 一处，不用翻遍路由 |
| **前后端双重守卫** | 页面 `@perm_required` + API `@perm_required` | 前端隐藏菜单只是体验，接口才是真正的门锁；绕过 UI 直接调接口同样被拒 |
| **数据行级隔离** | 物业工单查询按 `property_co = 本组织` 过滤 | 同一张表里可能有多家物业，只在页面上过滤等于没隔离 |
| **越权留痕** | 每次 403 写 `audit_log(action=deny)` | 居民信息被谁尝试访问过，是可审计事实，不是日志噪音 |
| **不信任前端身份** | `creator` 取会话用户，忽略请求体传值 | 否则可冒名录入，责任链断裂 |

### "上级单位"是位置，不是角色

表格里的「街道」一列就是**上级单位**。系统不设 `superior` 角色，因为
上级单位的权限包与街道完全重合——再造一个角色只会带来同步维护的负担。

上级单位这个位置由三项数据共同定义：

| 要素 | 取值 | 作用 |
|---|---|---|
| 角色 `role` | `street` | 决定默认权限包（8 项） |
| 单位 `org` | 如"幸福里街道办事处" | 发文时自动带出，也是收文单位匹配依据 |
| 层级 `level` | `ROLE_LEVEL[role]` = "街道" | 决定 `notice.level` / `kind` / 是否进收文待办 |

层级**不写死在代码里**：`dispatch` 从 `ROLE_LEVEL` 取当前账号的层级，
目录投递用同一张 `SUPERIOR_LEVELS` 表判定要不要进收文流程。
这样做的直接好处是——管理员建一个"和平区民政局"账号（角色仍是 `street`），
发出来的文层级不会莫名其妙变成别的值，也不会因为代码常量而失去可解释性。

> 本系统只建模"街道 → 社区 → 物业"三级。区级及以上通过街道这一层接进来，
> 不单独成为一级。真要建模四级，应该给 `user` 加 `unit_level` 列，而不是往
> `ROLE_LEVEL` 里塞新字符串。

上级单位的账号**不能自助注册**（注册接口把角色写死成 `community`），
只能由管理员在「用户与权限 → 新建账号」里建，或调 `POST /api/admin/users`。
建完直接 `active`，不进审核队列——管理员建号这个动作本身就是审核。


### 为什么这样切

- **物业不给台账**：台账里有门牌、姓名、健康状况，物业只需要"哪栋哪单元要修什么"。工单内容在派单时已经过保密审查 Agent 脱敏。
- **街道不给首录**：街道是监督方，若也能录入，数据责任源头就模糊了；报表由社区生成、街道核对，责任链清晰。
- **街道给审计**：上级监督需要能查"谁在什么时候动了什么数据"，这是保密承诺的举证手段，不是额外权力。
- **社区不给审计**：审计里含其他人的登录与操作记录，属于管理信息，不向平级开放。
- **任务下发只给街道**：`task.manage` 是街道唯一的写权限。社区与物业有 `task.view` 但只能看到派给本角色的任务（`assignee_role` 行级过滤），街道作为下发方可看全部——这是"管理动作"与"办事动作"的分界：街道不产生业务数据，只施加截止时间。

## 3. 登录流程

```
GET /            → 未登录 → 302 /login?next=/
POST /login      → 校验用户名密码（PBKDF2 哈希，Werkzeug）
                 → session["uid"] 写入签名 Cookie（8 小时有效）
                 → 按角色跳转：社区→/  物业→/orders  街道→/tasks（任务看板）
POST /logout     → session.clear() + 写审计
```

安全细节：

1. **不泄露账号是否存在**：账号不存在与密码错误返回同一句"用户名或密码错误"。
2. **防开放重定向**：`next` 只接受以 `/` 开头且不以 `//` 开头的站内路径，否则回落到角色首页。
3. **会话固定攻击防护**：登录成功后 `session.clear()` 再写 `uid`，不复用登录前的会话。
4. **API 与页面不同响应**：API 未登录返回 `401 JSON`，页面返回 302。前端统一拦截 401 跳登录页、403 弹提示，避免"点了没反应"。

## 4. 代码结构

```
app/auth.py            # 角色/权限点定义、守卫装饰器、登录登出、启动初始化
  ├─ PERMS             功能点 → 中文名
  ├─ ROLE_PERMS        角色 → 功能点集合
  ├─ current_user()    从 session 取用户（请求内缓存到 g）
  ├─ perm_required()   页面/API 通用守卫（401 / 403 / 越权审计）
  ├─ login/logout()    会话读写 + 审计
  └─ init_auth(app)    上下文注入（can/current_user/ROLE_HOME）+ 建表补列 + 演示账号
app/views.py           /login /logout + 5 个页面全部挂守卫
app/api/*.py           8 个接口模块全部挂守卫
app/templates/login.html   分屏登录页（三角色卡片一键填入）
app/templates/403.html     越权提示页（显示当前角色与所需权限）
```

### 轻量兼容老库

SQLite 已有 `user` 表没有 `username` 列。`_migrate_user_table()` 用 `PRAGMA/INSPECT` 检查后 `ALTER TABLE ADD COLUMN` 补列，幂等、可重复执行，不引入 Alembic（毕设阶段没必要）。

## 7. 安全加固与剩余边界（答辩时如实说明）

### 7.1 本轮已修（有断言守住，见 scripts/smoke_security.py 32 项）

| 问题 | 原状 | 修法 |
|---|---|---|
| **工单水平越权（IDOR）** | 接单/办结只按 id 取单，物业 A 能操作物业 B 的工单（列表做了隔离、写操作没做，等于隔离只在"看"上成立） | `_load_order()` 统一做归属校验，越权返 403 并写 `audit(agent=auth, action=deny)`；读写两侧口径一致 |
| **公告越界读取** | 居民端只按 `status=published` 过滤，没校验 `scope`。一旦发布一条"仅社区可见"的内部通知，居民就能看到 | 列表与详情统一走 `visible_query("resident")`，详情页额外判 `scope=all`，否则 404 |
| **会话密钥可猜** | `SECRET_KEY` 回落公开默认串，session 是签名 cookie → 可离线伪造 `role=street` 直接登入 | 生产环境未配置时**现场随机生成**并告警；显式配置优先。密钥在 `create_app` 里裁决，不在类属性上定死（否则改环境变量无效） |
| **登录可爆破** | 无失败限制，6 位密码可无限猜 | 见下方 7.3，**双维度**限流：账号维度 5 次锁定（主），IP 维度 30 次兜底（辅），返回 429 且提示不区分账号是否存在；失败写 `login_fail` 审计 |
| **Cookie 缺属性** | 未显式声明 | `HttpOnly` + `SameSite=Lax`（跨站 POST 不带 cookie，是当前防 CSRF 的主要手段）；`Secure` 由 `SESSION_COOKIE_SECURE=1` 开启 |

对应测试：**32 项全过**，命令 `python scripts/smoke_security.py`。

### 7.2 限流维度：一个只有上线才会暴露的错误

第一版限流用的是 `IP|账号` 组合，本地测试完全正常（`127.0.0.1` 恒定）。
部署到托管环境后实测发现**第 6 次失败仍然放行**，查审计里的来源 IP：

```
219.144.89.57   117.85.66.38   140.249.104.14
183.131.72.228  60.163.165.219 219.144.89.206
```

同一分钟内 6 次请求，6 个不同 IP——反向代理有出口 IP 池，而且
`X-Forwarded-For` 是**请求头，客户端本来就能随便写**。两个结论：

1. 按 IP 计数在代理环境下永远不会累积，限流等于没做；
2. 把可伪造的请求头当作安全决策依据，从根上就不成立。

改为**账号维度为主**（`acct|用户名`，5 次）、**IP 维度为辅**（30 次，只防单 IP 扫大量账号）。
代价是攻击者可以故意失败几次把某个账号锁住（DoS），用 5 分钟短锁定期缓解，
生产环境应再加验证码。居民端同一问题的两处（填报、查询码）一并改成手机号维度——
查询码只有 6 位，真正的威胁是"知道手机号后枚举查询码"，按手机号限才是对症的。

用例里专门用**逐次变化的 XFF** 复现这个环境（`smoke_security.py` 第 4b 组），
否则这个洞在本地永远测不出来。

### 7.3 仍然存在的边界

| 项 | 现状 | 生产应做 |
|---|---|---|
| CSRF | 未引入 token，靠 `SameSite=Lax` + 写接口只收 JSON 双重约束 | Flask-WTF `CSRFProtect`，全部写接口校验 token |
| 密码策略 | 演示账号统一 123456 | 首登强制改密 + 复杂度校验 + 定期过期 |
| 传输加密 | 沙箱内 http 回源 | 反代启用 HTTPS，并开 `SESSION_COOKIE_SECURE=1` |
| 会话存储 | 签名 Cookie（客户端） | Redis 服务端会话，支持强制下线与并发登录限制 |
| 多进程部署 | 未配 `SECRET_KEY` 时每个进程随机，各进程互不认 session | 显式配置 `SECRET_KEY`（或密钥服务），再做多 worker |
| 权限粒度 | 功能点级 + 组织字段近似隔离 | 数据级（本社区/本网格）行级策略 |

这些不是"忘了做"，是**演示环境与生产环境的边界**，写进论文第 6 章"局限与展望"比藏着更好。
但前一张表里的五项不属于"边界"，是本该有的防护，已经补上并固化成测试。

## 8. 与保密设计的衔接

| 保密要求 | 权限层的支撑 |
|---|---|
| 数据最小必要 | 物业看不到台账与首录原文；街道看不到居民明细 |
| 访问可追溯 | 登录、登出、越权尝试全部写 `audit_log`，`agent=auth` |
| 责任可定位 | `creator` 取会话身份，工单操作记录操作人姓名 |
| 外网零调用 | 认证在本机完成，不依赖任何第三方身份服务 |
