# 基于 Multi-Agent 协作与本地大模型的社区"极简减负"智能体系统 —— 总体设计

> 版本：v0.2  日期：2026-10-17

---

## 一、术语与定义

| 术语 | 定义 |
|------|------|
| **FDE（First Data Entry）** | 首录入口。全系统唯一的业务数据第一录入点，保证"一次录入、多方复用"，杜绝重复填报 |
| **业务项（Work Item）** | 一段话经拆解后得到的最小业务单元，含类型、主体、字段、去向业务线 |
| **Agent** | 具备单一职责的智能体，输入/输出均为结构化 JSON，由调度器编排 |
| **Orchestrator** | 调度器。负责 Agent 调用顺序、消息路由、异常兜底 |
| **敏感字段** | 身份证号、手机号、健康信息、住址门牌、调解隐私内容等，受保密策略约束 |

## 二、业务分析

### 2.1 基层工作痛点（问题定义）

| # | 痛点 | 具体表现 | 对应系统对策 |
|---|------|----------|--------------|
| P1 | 重复填报 | 同一数据多头录入综治/民政/卫健/物业系统 | FDE 单点录入 + 填报Agent分发 |
| P2 | 表格泛滥 | 台账口径不一，人工整理耗时 | 台账Agent按模板自动写 |
| P3 | 留痕压力 | 巡查走访调解都要写记录归档 | 台账Agent自动生成流程记录 |
| P4 | 沟通链条长 | 社区↔街道↔物业靠微信群，易丢难追溯 | 派单Agent工单化 + 全程留痕 |
| P5 | 保密约束 | 居民敏感信息不能上公有云大模型 | 本地大模型 + 保密审查Agent + 审计 |

### 2.2 角色与权限矩阵

> 落地实现见 `docs/04-角色权限实现.md`。本期开放**三个业务角色**登录；系统管理员角色位已在代码预留（`ROLE_PERMS` 全集），不开放账号，运维由部署方兼任。

| 角色 | 定位 | 可见数据 | 可执行操作 |
|------|------|----------|------------|
| **社区工作者** | 主要用户、FDE 操作者 | 本社区全部业务数据（敏感字段授权可见） | 首录、确认拆解结果、处理任务、查看台账 |
| **街道（上级）** | 管理方 | 汇总报表（脱敏后）、进度看板 | 下发任务、督办、接收报表 |
| **物业（协同方）** | 执行方 | 仅与本物业相关的工单（不含居民敏感信息） | 接单、反馈、上传处理凭证 |
| **系统管理员** | 运维 | 审计日志（不含明文敏感值） | 用户管理、模型配置、日志审计 |

### 2.3 三方业务流转关系

```
                ┌──────────────┐
                │   街道（上级）  │ 下达任务 / 督办 / 要报表
                └──────┬───────┘
                       │ 任务下发 ↑↓ 数据上报（脱敏汇总）
                       ▼
  居民/事件 ──FDE──► ┌──────────────┐
  （数据源）          │   社区工作者   │ 首录一次，Agent 分发
                      └──────┬───────┘
                             │ 派单（脱敏工单）↑↓ 反馈凭证
                             ▼
                      ┌──────────────┐
                      │  物业公司     │ 维修/环境/门禁事项落地
                      └──────────────┘
```

**关键原则：跨角色流转的数据一律经保密审查 Agent 处理，物业与街道看到的均为最小必要数据。**

## 三、系统架构

### 3.1 分层架构

```
┌────────────────────────────────────────────────────────────┐
│  展示层  Flask + Jinja2 + Tabler(Bootstrap5) + ECharts       │
│  FDE首录台│任务看板│工单中心│台账中心│报表中心│审计日志        │
├────────────────────────────────────────────────────────────┤
│  接口层  REST API（/api/fde /api/tasks /api/orders ...）     │
│  统一返回格式 {code, msg, data}，统一异常拦截                 │
├────────────────────────────────────────────────────────────┤
│  协作层  Orchestrator 调度器                                 │
│  ┌────────┐┌────────┐┌────────┐┌────────┐┌────────┐        │
│  │拆解Agent││保密审查││填报Agent││派单Agent││台账Agent│        │
│  └────────┘└────────┘└────────┘└────────┘└────────┘        │
│  ┌────────┐┌────────┐                                       │
│  │报表Agent││督办Agent│  ← 消息总线（内存队列/后续可换Redis） │
│  └────────┘└────────┘                                       │
├────────────────────────────────────────────────────────────┤
│  模型层  Ollama + Qwen2.5-7B-Instruct（本地，无外网调用）     │
│          + FAISS 向量库（RAG：政策文件/表格模板/历史台账）    │
├────────────────────────────────────────────────────────────┤
│  数据层  MySQL（业务库）│ 审计日志库（只追加）│ 文件存储      │
└────────────────────────────────────────────────────────────┘
部署边界：全部组件位于社区/街道内网，物理隔离外网依赖
```

### 3.2 核心业务流程（FDE 主线，含失败兜底）

```
① FDE 提交原始文本/语音/图片
        ▼
② 拆解Agent（LLM）→ 产出业务项列表（JSON Schema 校验）
        ├─ 校验失败 → 返回人工确认界面（兜底，不静默出错）
        ▼
③ 保密审查Agent → 逐字段打标 {明文/脱敏/加密}
        ▼
④ 调度器按业务线分流：
   ├─ 有物业事项 → 派单Agent → 工单（脱敏）→ 物业端
   └─ 有政务事项 → 填报Agent → 查重复用 → 台账入库
        ▼
⑤ 物业反馈 / 工作者确认 → 台账Agent 补全流程记录
        ▼
⑥ 报表Agent 定期汇总 → 街道端（脱敏）
   督办Agent 全程监控 SLA，超时告警
⑦ 每一步写入审计日志（操作者、Agent、时间、输入摘要、输出摘要）
```

## 四、Agent 契约设计（输入/输出 Schema 约定）

| Agent | 输入 | 输出 | 降级策略 |
|-------|------|------|----------|
| 拆解Agent | 原始文本 + 业务线清单 | `[{type, subject, fields{}, target_lines[]}]` | JSON 校验失败 → 转人工 |
| 保密审查Agent | 业务项列表 | 同上 + `field_security{字段:级别}` | 默认按最高级别脱敏 |
| 填报Agent | 业务项 + 历史档案 | 台账记录 + 复用标记 | 查重冲突 → 人工确认 |
| 派单Agent | 物业类业务项 | 工单（脱敏）| 生成失败 → 进待办人工派发 |
| 台账Agent | 流程事件 | 台账记录/归档 | — |
| 报表Agent | 统计周期 | 报表数据 + 图表配置 | — |
| 督办Agent | 任务 SLA 规则 | 告警消息 | — |

## 五、数据库设计（核心表）

```
fde_record     首录原始记录：id, raw_text, source(文字/语音/图), creator, created_at
work_item      业务项：id, fde_id, type, subject, fields_json, status
field_security 敏感标记：id, work_item_id, field, level(1明文/2脱敏/3加密)
work_order     物业工单：id, work_item_id, property_co, content(脱敏), sla, status, feedback
ledger         台账：id, work_item_id, line(综治/民政...), content_json, created_at
report         报表：id, period, line, data_json, generated_at
task           任务：id, title, assignee_role, deadline, status
audit_log      审计：id, actor, agent, action, input_digest, output_digest, created_at（只追加）
user           用户：id, name, role, org, password_hash
```

## 六、保密设计（毕设创新点）

1. **模型本地化**：Ollama 内网部署，全流程零外网调用（可在日志中举证）
2. **字段三级管控**：每个业务项的结构化字段按名/值双规则判级并落 `field_security` 表（可查、可审计，不是只存在代码里的约定）
   - **1 级 明文**：楼栋号、事项类型、问题描述等公开信息，可跨角色流转
   - **2 级 脱敏**：姓名、房号、门牌、单元等可定位到自然人的信息，跨角色前打码
   - **3 级 加密**：身份证号、手机号、健康信息——《个人信息保护法》定义的敏感个人信息
   - 实现口径：3 级字段在**入库前**即被替换为不可逆掩码（`138****1234`、`320102********4512`），**原文不落库**。这比"加密后存储"更强：密钥泄露也无法还原。若业务确需可逆（如回拨居民电话），再叠加 AES 字段级加密，属生产增强项。
3. **最小必要原则**：物业工单自动剔除敏感字段；街道报表只给汇总
4. **审计留痕**：所有 Agent 调用记录摘要，可追溯不可篡改（只追加表）
5. **权限隔离**：三角色视图分离，敏感明文仅社区工作者授权可见

## 七、技术选型

| 层次 | 技术 | 理由 |
|------|------|------|
| 前端 | Tabler (Bootstrap5, MIT, 41K★) + ECharts | 纯 HTML 直接进 Jinja2，颜值即战力 |
| 后端 | Flask（蓝图模块化） | 毕设规模可控，与 Python AI 生态无缝 |
| LLM | Ollama + Qwen2.5-7B-Instruct | 中文强、支持 JSON 输出、内网运行 |
| Agent | 自研轻量调度器（或 LangChain） | 契约清晰，答辩可讲透 |
| RAG | FAISS + BGE 嵌入（本地） | 政策/模板检索增强 |
| 数据库 | MySQL 8 | 课程一致，报表 join 方便 |
| 环境 | Windows + Python 3.10+ | LangChain 生态要求 ≥3.8 |

## 八、评测指标（写论文用）

| 指标 | 目标 | 测量方式 |
|------|------|----------|
| 拆解准确率 | ≥85% | 30 条真实风格语料，人工核对业务项 |
| 敏感字段召回率 | ≥95% | 构造含敏感字段样本，统计漏检 |
| 重复填报减少率 | ≥60% | 对比传统流程录入字段数 |
| 报表生成耗时 | 分钟级 | 月末报表人工 vs 系统耗时对比 |
| 外网调用次数 | 0 | 网络抓包/日志举证 |

## 九、UI 参考（开源模板调研结论）

| 模板 | Stars | 技术栈 | 适配度 |
|------|-------|--------|--------|
| **Tabler** ⭐推荐 | 41K+ | Bootstrap5 纯 HTML，MIT | 最高：直接套进 Jinja2，政务风干净利落 |
