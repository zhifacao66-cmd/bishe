# 27 · 双端数据同步（本机 ↔ 阿里云 ECS）

> 2026-10-23 实施。适用于「本机写、服务器展示」的比赛/答辩场景。
> 线上沙箱那套（`/api/dbsync/*` + 防呆引擎）**没有做**，见 `TODO.md` F 节的取舍说明。

## 1. 为什么是"文件级同步"而不是接口

线上沙箱只开放一个 HTTP 端口，不提供外部数据库，想搬数据只能自己写接口 + 鉴权 + 防呆，
约 200 行。ECS 有 SSH 和完整文件系统，同一个需求退化成 **scp 一个文件**，
所以这套实现只有两个文件、约 400 行，且没有任何协议设计。

## 2. 用起来

```bash
python scripts/ecs_sync.py push     # 本机 → 服务器（推完立刻触发应用，约 2 秒生效）
python scripts/ecs_sync.py pull     # 服务器 → 本机（赛后把现场数据拉回来写论文）
python scripts/ecs_sync.py status   # 两端逐表行数 + 最后同步时间
```

`push` 的四步：本机取快照 → scp 上传（先数据、再 `.sha`、最后 `.apply` 请求标记）→
触发服务器应用 → 打印两端行数。

⚠️ **演示/比赛期间不要 `push`**：它的语义是"用本机这份覆盖服务器"。
服务器上产生的数据会一直留着（轮询任务不会碰它），赛后 `pull` 回本机即可。

## 3. 服务器侧怎么跑

| 件 | 位置 | 说明 |
|---|---|---|
| `snapshot_apply.py` | `C:\app\snapshot_apply.py` | 覆盖器，与 `scripts/snapshot_apply.py` 是**同一份文件** |
| `sync_once.bat` | `C:\app\sync_once.bat` | 单次应用入口，日志落 `C:\app\logs\sync-run.log` |
| 计划任务 `ca-sync` | 每分钟 | 只应用**显式请求**的快照；没请求就跳过，不碰服务器数据 |
| 收件区 | `C:\data-incoming\` | `community.db.new` + `.sha` + `.apply`（请求标记）；孤儿审计也存这里 |
| 状态 | `C:\data-incoming\applied.json` | 最后应用的 sha256 与时间，幂等靠它 |

## 4. 五个关键设计（每条都对应一个真实故障）

1. **不替换 `.db` 文件，在事务里 DELETE + INSERT。**
   Windows 下运行中的进程持有文件句柄，替换会撞「另一个程序正在使用此文件」；
   即使换成功，连接池仍指向旧句柄，页面能打开、数据却是旧的，且不报错。
2. **快照必须用 `sqlite3.backup()`。** 库开着 WAL，主文件不含未 checkpoint 的事务，
   直接拷 `community.db` 会安静地丢掉最近的写入。
3. **上传顺序：先数据、后 `.sha`。** 覆盖器先比对旁路 sha，不一致就静默跳过，
   避免上传到一半被当成"坏库"每分钟刷一条错误。
4. **按列交集插入。** 代码升级后服务器库可能多出新列，全列 INSERT 会报 `no column named`；
   取交集让新列走默认值，旧快照仍可应用。
5. **覆盖前把目标库独有的审计导出。** 覆盖会删掉对端新写的 `audit_log`，
   这些行不在快照里就永久消失。现在先写 `audit-orphan-<ts>.jsonl` 再删，日志里报条数。
6. **轮询任务只认「显式推送请求」，绝不自己纠正目标库。**
   这是踩了两次才定下来的，第二次代价很实在（见 §6）。
   上一版用"目标库指纹对不上就重覆盖"来修"两端差一条"，方向错了：它假设**本机是唯一写入端**，
   于是服务器上用户刚办的工单、刚登录的审计，会在 ≤60 秒内被静默覆盖回旧快照——
   用户看到的现象就是「我明明操作了，审计里什么都没有」。
   现在 `push` 会在收件区落一个 `<snapshot>.apply`（内容是要应用的 sha），
   轮询任务带 `--require-request`，**没有标记就直接退出，一个字都不动**；
   标记 sha 与快照不符（还在上传）也跳过；应用成功后把标记删掉。
   顺带把"sha 相同就跳过"在显式推送时绕开了——`push` 就是要覆盖，不该被幂等挡住。

## 5. 写入纪律（这是代价，不是缺陷）

- **谁在用，谁写。** 演示/比赛时一切操作都在服务器上，`ca-sync` 不会碰它（§4.6）。
- **不要在演示期间 `push`。** `push` 的语义就是"用本机这份覆盖服务器"，
  服务器上那些演示数据会被覆盖——覆盖前会先导出 `audit-orphan-<ts>.jsonl`，不会无声消失。
- **赛后要拿现场数据写论文**：`pull` 一次，把服务器整份拉回本机（先自动备份本机旧库）。
- 为什么不做行级合并：单人使用是**串行写**，合并（id 分段 + 全表 `updated_at` + 墓碑 +
  冲突清单，约 1100 行）是为不会发生的并发买保险，而且算错时静默覆盖、无人知晓。
- `kb_doc` 内容变化时覆盖器会**重启应用任务**（`community-agent-run`），
  因为检索索引在内存里，不重启会继续用旧文档回答、页面看不出异常。
  实测其余同步（不动 kb）不会重启：`server.log` 里 `[start]` 只有 1 次。

## 5.5 代码怎么更新到服务器（和数据是两件事）

数据靠 `ecs_sync.py push/pull`（人工决定方向），**代码更新是另一条路**：
`python scripts/ecs_deploy_code.py`。它只做一件事——把 `app/` + `run.py` + `config.py`
换上去，`data/` 一个字节都不碰。

```bash
python scripts/ecs_deploy_code.py --check    # 只报远端版本特征（dashboard/itemstate 在不在）
python scripts/ecs_deploy_code.py            # 打包 → 上传 → 备份 → 停服 → 换 → 启动 → 等健康
python scripts/ecs_deploy_code.py --rollback --stamp 20261023144949
```

**为什么要有脚本，而不是手工 scp 几个文件**——三条都是这台机器上真踩出来的：

1. **链路一次只让你连一次**：22 端口 TCP connect 约 50% 成功，而且在同一个终端里
   连着发第二条连接基本必失败（`Connection timed out` / `Connection closed`）。
   所以脚本里每个动作各占一次连接，失败就 sleep 重试；而**服务器侧的多个步骤
   合并成一个 .bat 一次下发**——分四次下发，断在中间就是"代码换了一半、服务停了"。
2. **`.bat` 必须是 CRLF**：只有 LF 时 cmd 会把 `if ... ( ) else ...` / `for ... do ( )`
   这类多行结构错解，报 `2>&1 此时不应有`，**而且前面几行已经执行了**（备份做完了、替换没做）。
3. **`.bat` 不能有中文注释**：UTF-8 中文在 `rem` 行里会被当成命令，
   报 `'……' 不是内部或外部命令`。所以脚本生成的 .bat 是纯 ASCII + CRLF（`write_ascii_crlf`）。

另外两条设计：

- **停服只杀 :80 上的那个 PID**（`netstat` 取 PID + `taskkill /pid`），
  不用 `taskkill /im python.exe`——`ca-sync` 每分钟也会起一个 python，
  正在 apply 快照时被杀会打断事务。
- **换之前一定先备份** `app/` → `app.bak-<时间戳>`，回滚就是把它换回来。
  脚本把时间戳打印出来，别丢。

服务器侧保留的、本机**不该覆盖**的东西：`main.py`、`start_server.bat`（`set PORT=80`、
`FLASK_ENV=prod`）、`llm.json`（隧道地址+令牌）、`.secret_key`、`data/`、
`snapshot_apply.py`、`sync_once.bat`。

> 实测（2026-10-23 14:49）：一次命令完成，health 回来 `llm.available=true`，
> 数据仍是 41 首录 / 54 事项 / 18 工单 / 60 台账 / 5 任务，`secure_count=43`。

## 6. 实测记录

### 6.1 初次落地（2026-10-23 12:24）

| 验证项 | 结果 |
|---|---|
| 本机新增一条审计 → `push` | 服务器 `/api/audit` 立刻返回 `id=277 agent=sync-selftest`，**应用未重启** |
| 只上传不触发 | 计划任务 `ca-sync` 在 12:25:01 自动应用，12:26:01 跳过 |
| 覆盖前孤儿审计 | 服务器独有 3 条 → `audit-orphan-20261023-122426.jsonl` |
| 全表比对 | user 5 / task 4 / notice 4 / work_order 17 / ledger 60 / kb_doc 10 / audit 276，两端一致 |

### 6.2 一次真实事故 → 改成显式请求（2026-10-23 13:04）

用户在 `http://47.108.235.113` 上操作了一轮（13:03:39 登出 → 物业登录 → 13:03:53 工单接单 →
13:03:57 管理员登录），**审计一条都没留下**。

原因不是没写进去，而是被覆盖器抹掉：`C:\data-incoming\audit-orphan-20261023-130401.jsonl`
里正是那 5 条（id 277–281），覆盖时间 13:04:01 —— `ca-sync` 每分钟比对目标库指纹，
发现"被改过"就整库覆盖回本机快照。这套逻辑假设本机是唯一写入端，而实际演示发生在服务器上。

改成显式请求后复测：

| 验证项 | 结果 |
|---|---|
| 无 `.apply` 标记的轮询 | 日志「无显式推送请求，跳过（目标库数据保持不动）」 |
| 显式 `push`（sha 与上次相同） | 日志「显式推送：快照与上次相同，仍按请求覆盖一次」→ 照做 |
| 服务器上真实操作（13:09:46 登录 → 13:09:49 接单 → 13:09:53 登出） | 跨过 13:10:01 的轮询，`/api/audit` 仍返回 283 条，5 条新审计全在 |
| 工单状态是否真生效 | `W20261021-101330-05` → `doing` / 李经理，接单留住了 |
| 回归 | `python scripts/smoke_ecs_sync.py` → **28 项全过** |

## 7. 排错

| 现象 | 原因 | 处理 |
|---|---|---|
| `push` 后服务器行数没变 | 快照内容与本机一致且被覆盖过 | 正常，日志会写「显式推送：快照与上次相同，仍按请求覆盖一次」 |
| 日志「无显式推送请求，跳过」 | 轮询任务跑在没有人推的时候 | 正常。它**就该跳过**，否则会抹掉服务器上的操作 |
| 日志「快照与校验文件不一致」 | 上传中断，`.sha` 是旧的 | 重跑 `push` |
| 日志「请求的 sha 与快照不一致」 | `.apply` 到了但数据还在传 | 正常，重跑 `push` 即可 |
| 日志「拒绝应用：quick_check=…」 | 快照损坏 | 重跑 `push`，别手工修库 |
| 页面数据变旧 | 应用没在跑 | `ssh` 进去看 `C:\app\logs\server.log` |
| 知识库答案没变但文档改了 | 未重启（未传 `--restart-task`） | 手工 `schtasks /run /tn community-agent-run` |
| **服务器上操作了、审计里没有** | 有人 `push` 覆盖过 | 查 `C:\data-incoming\audit-orphan-*.jsonl`，按时间能找到 |

`C:\app\logs\sync.log` 是 **UTF-8**，用 `type` 在 GBK 控制台看会乱码，用 VS Code 或 `chcp 65001` 打开。
