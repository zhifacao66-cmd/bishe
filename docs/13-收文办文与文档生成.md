# 收文 · 办文 · 文档生成

上级单位发一份文件下来，社区不是"转发一下就完事"。
真实流程是四步：**上级发文 → 社区签收 → 社区办文（落成本社区的执行通知）→ 对外发布**。
这一章讲这四步在系统里怎么落地，以及为什么这么设计。

---

## 1. 这条链路原来缺什么

在补齐之前，系统只能做到"文件丢进 `data/notices/` → 自动解析 → 发布到居民端"。
放到真实业务里，这一步跨得太大了，缺三个环节：

| 缺的环节 | 后果 |
|---|---|
| **收文没有交接** | 文件是服务器目录里多了一个文件，看不出"谁发的、发给谁、社区签没签收" |
| **没有办文** | 上级文件写的是"各社区要排查消防隐患"，居民看了不知道自己该干什么，社区还得另写一份 |
| **"不同格式文档"只是网页视图** | 「发布版 / 打印版」是两个 HTML 页面，不能下载、不能盖章归档、不能上报 |

补齐后，一份上级文件的完整生命周期是这样：

```
街道在线发文 / 文件丢进目录
        ↓  recv_status = dispatched      社区工作台出现收文待办
     社区签收（留签收人、时间）
        ↓  recv_status = received
     生成落地件（模型起草 / 规则模板兜底）
        ↓  kind = local, parent_id 指回原文
     导出 docx / md / txt  →  张贴、归档、上报
        ↓
     发布到居民端
```

## 2. 四个权限点，管四件事

公告相关的权限点从 3 个扩到 5 个，不是拆着玩，是让"发文的"和"办文的"各归各位：

| 权限点 | 角色 | 管什么 |
|---|---|---|
| `notice.import` | 街道 | 把上级文件接进系统（目录扫描 / 在线发文） |
| `notice.receive` | 社区 | 签收，承认"我收到了、我要办" |
| `notice.localize` | 社区 | 生成社区落地件 |
| `notice.manage` | 社区 | 发布 / 下架 / 置顶（属地口径，谁属地谁背书） |
| `notice.view` | 四方 | 查看与导出 |

为什么签收和办文要分成两个权限点：社区内部本来就分工，主任签收、经办人办文。
两个动作各留一条审计，出了问题能查到是谁在哪个环节。

**街道不持有 `notice.receive` 和 `notice.localize`**。
街道只负责发和督，不替社区办——不然"监督者"和"执行者"就合并了，
这跟工单那边"街道没有 `order.handle`"是同一条原则。

## 2.1 上级单位的账号怎么建、权限怎么配

### 要不要单独一个角色？

**不要。`street` 就是上级单位**，演示账号 `jiedao / 123456`（张科长，幸福里街道办事处）。

"上级单位"不是一个角色，而是一个**位置**——它在收文流程里的位置是"发文方 + 督办方"。
这个位置由三件事共同定义，缺一不可：

| 要素 | 取值 | 为什么 |
|---|---|---|
| 角色 | `street` | 决定默认权限包 |
| 单位 | 账号的 `org`，如"幸福里街道办事处" | 发文时自动带出，也是收文单位匹配的依据 |
| 层级 | `ROLE_LEVEL[role]` = "街道" | 决定 `notice.level`、`kind`、要不要进社区收文待办 |

单独造一个 `superior` 角色只会带来一个问题：它和 `street` 的权限包一模一样，
于是两个角色要同步维护，改一个忘一个。**位置相同就用同一个角色，差别放在数据里。**

### 权限包（8 项）

| 权限点 | 为什么给 |
|---|---|
| `notice.import` | 发文——这是上级单位存在的理由 |
| `notice.view` | 看自己发过的文，以及办到什么程度 |
| `task.manage` | 下发任务、施加截止时间（街道唯一的写权限） |
| `task.view` | 看任务看板 |
| `order.view` | 看超时工单，这是督办的对象 |
| `report.view` | 看汇总报表 |
| `audit.view` | 查"谁在什么时候动了什么数据"，这是保密承诺的举证手段 |
| `kb.view` | 只读知识库，发文时引用政策依据 |

**不给的，比给的重要：**

| 权限点 | 为什么不能给 |
|---|---|
| `notice.receive` | 签收是"我要办"的承诺，只能由办的人做 |
| `notice.localize` | 办文是把上级要求落到本社区楼栋和时间上，上级替不了 |
| `notice.manage` | 对外发布是属地背书，谁属地谁签字；置顶同理——排在最前=居民最先读到 |
| `fde.create` | 街道不产生业务数据。若也能录入，数据责任的源头就模糊了 |
| `ledger.view` | 台账含居民明细，最小必要 |
| `order.handle` | 街道不接单，否则监督者和执行者合并 |
| `user.manage` | 账号治理管的是"谁能用系统"，不是"谁能办业务"，不下放 |

`scripts/smoke_superior.py` 把这一整张"不给"的表逐条写成断言——
哪天有人"顺手"给街道补一个 `notice.localize`，测试会立刻红。

### 怎么建

管理员在「用户与权限 → 新建账号」里填：

```
账号 minzheng   姓名 李主任   单位 和平区民政局
角色 街道       密码 ≥8 位
权限 默认按角色预选 8 项，可增减
```

建完即可登录，不进审核队列。也可以直接调接口：

```bash
POST /api/admin/users
{"username":"minzheng","name":"李主任","org":"和平区民政局",
 "role":"street","password":"minzheng2026","perms":null}
```

`perms: null` = 跟随角色默认；传数组 = 按人授权。
比如只给 `["notice.view","report.view"]` 就是一个"只读监督员"账号，能看不能发——
机关里确实有这种岗位，以前只能靠"别点那个按钮"来约束。

### 层级为什么不再写死

`dispatch` 里原本写死 `level="街道"`。问题是：管理员建了个"和平区民政局"账号
（角色仍是 `street`），发出来的文层级还是记"街道"，于是页脚、导出 Word 的元信息头、
按层级统计全跟着错。

现在改成 `level = ROLE_LEVEL[current_user.role]`，**层级由账号档案决定，不由代码常量决定**。
目录投递那边同步改成 `is_superior(level)` 判定，两边共用 `SUPERIOR_LEVELS` 这一张表，
避免"页面按一套口径算、入库按另一套口径算"。

> **边界**：本系统只建模"街道 → 社区 → 物业"三级。
> 区级及以上不是系统的使用主体，它们的文件通过街道这一层接进来（现实中也确实如此：
> 区局发文给街道，街道再转发各社区）。所以 `ROLE_LEVEL` 里只有三个层级，
> 建"区民政局"账号时 `level` 仍记"街道"——它是街道这一层的**经办单位**，不是新的一级。
> 真要建模四级，正确做法是给 `user` 加 `unit_level` 列，而不是往 `ROLE_LEVEL` 里塞字符串。

### 督办视角：上级最关心的不是"我发了"，是"下面办了没有"

只有"待签收/已签收"两态，街道发完文还是得打电话问。所以补了**办文进度**：

| 字段 | 含义 |
|---|---|
| `local_count` | 这份来文生成了几份本社区落地件 |
| `local_published` | 其中几份已对外发布 |

列表页「来源」列据此显示三态，正好对应三种要督办的情况：

```
待签收          → 还没人接，该催
已签收 · 未办文  → 接了但没动，最该催
已办文 · 已发布  → 闭环了
```

详情页的四步时间线同步调整：第 1 步改显示**成文日期**（原来是入库时间，
演示库里所有记录同一天灌进去，会和回填的签收时间倒挂，看着像数据错了），
第 4 步改成看**落地件**发没发出去，而不是上级原文自己的发布状态——
原文发不发是信息公开问题，上级关心的是"社区把要求落成通知、贴在楼下了没有"。

> 批量取进度是一次查询再按 `parent_id` 分组，没有走 N+1。
> 列表页最多 200 条，这个量级不值得上缓存。

## 3. 收文：两种投递方式，对应两种真实场景

### 3.1 目录批量投递（`POST /api/notices/scan`）

上级单位把文件（.md / .docx / .txt）放进 `data/notices/`，
后台线程每 60 秒扫一次目录指纹，有变化就解析入库。

适合**批量转发**：区局一次下发七八个文件，管理员往目录里一放就完事。
字段解析完整的直接发布，缺发文单位的转「待确认」等人补。

### 3.2 在线定向投递（`POST /api/notices/dispatch`）

街道在页面上填标题、文号、收文单位、完成时限、正文，点「投递」。
适合**定向交办**：一件事指定给某个社区，需要留"谁投的、投给谁、什么时候要"。

两种方式的差别不在技术，在**责任链**：

| | 目录投递 | 在线投递 |
|---|---|---|
| 投递人 | 看不出来（只有创建人字段） | 明确，写审计 |
| 收文单位 | 全体社区 | 可指定，非指定单位签收会被拒 403 |
| 完成时限 | 无 | 有，落地件默认继承 |
| 初始状态 | 字段完整则直接发布 | 一律 `pending`，等社区确认 |

在线投递生成的公告 `status=pending`，**不直接对外发布**。
理由：点对点交办的文件往往带具体任务口径，社区该不该原样公开得自己判断。

## 4. 签收：只留痕，不改发布状态

```python
POST /api/notices/<id>/receive
```

签收写入 `received_by` / `received_at`，加一条 `action=receive` 审计。
**不碰 `status`**。

这个解耦是刻意的，两件事本来就不该绑一起：

- 上级原文该不该让居民看到，是**信息公开**问题，由社区在发布环节判断；
- 签收证明的是"社区知道要办"，是**内部留痕**，居民看不看得见跟它无关。

如果绑在一起，"收到就得马上公开"会变成硬约束，
遇到需要内部先研判的文件（比如涉及具体住户的），社区就只能不签收——流程反而卡死。

指定了 `receiver_org` 的文件，别家社区签收会被拒：

```
403  该文件指定收文单位为「和平社区」，本账号无权签收
```

## 4.5 办结：签收之后，才算"办完了"

```python
POST /api/notices/<id>/handle      # body: {"result": "办理结果"}
```

签收回答的是"我收到了"，办结回答的是"要求办成了没有"。两件事之间可能隔几天、
可能换人，所以**必须是两步**——合并之后系统只能回答"收到没收到"，
回答不了"办没办"。

三列一起写，缺一个就查不清：

| 列 | 写什么 | 缺了会怎样 |
|---|---|---|
| `handler` | 承办人姓名（取会话身份，不信前端传值） | 追责时只知道"社区办的" |
| `handled_at` | **首次**办结时间 | 周报「本周已办结」恒 0、「欠办」把到期收文全算进去 |
| `handle_result` | 办理结果文本（≥5 字、≤500 字） | 只有"办完了"三个字，等于没写 |

几条规则都有具体来由：

- **前置条件是已签收**（否则 409）。"签收了但没办"和"办完了没签收"是两种在真实
  公文里不存在的组合，系统不该造出来；
- **办结不进发文状态机**。`recv_status` 只到 `received`，办结是填
  `handle_result`，不是 `doc_status` 迁移（见 `app/docflow.py` 开头）。所以约束写在
  `docflow.handle_inbound()` 里，写一条 `DocLog(action="handle")` 与发文留痕同一个表；
- **补正不改首次办结时间**。结果写错了可以再提交一次，但 `handled_at` 不动——
  否则周报里"本周办结 3 件"会因为改个错别字变成 4 件；
- **权限点 `notice.handle` 单独开**，不并进 `notice.receive`：现实中主任签收、
  经办人办理，两人各自留痕。街道没有这个点（只发不办），物业也没有。

页面上的位置：`/notices/<id>` 的流转时间线第 5 格「社区办结」，
右侧「办理」卡里的表单。签收后出现，已办结时变成"补充办理结果"。

## 5. 办文：模型优先，规则兜底

```python
GET  /api/notices/<id>/draft      # 取草稿
POST /api/notices/<id>/localize   # 保存落地件
```

### 5.1 为什么要模型

上级文件是"各社区要做什么"，落地件是"本小区哪天查、查什么、找谁"。
这个转换不只是换个标题——要把"社区"换成"本社区"、把"各单位"换成"各位居民"、
把上级的抽象要求落到具体的楼栋和时间上。这正是本地模型擅长的改写任务。

`app/notice/localize.py:draft()` 调 `chat(..., schema=SCHEMA)` 约束输出
`{title, body_md}` 两个字段，避免模型自由发挥结构。

### 5.2 兜底模板不是"凑一段"

线上托管环境没有 Ollama，模型必然不可用。兜底路径给出的草稿必须**能直接用**，
所以它按转发件的公文结构组织：

```
各小区、各位居民：

根据{上级单位}《{文件名}》（{文号}）要求，结合我社区实际，现将有关事项通知如下：

一、本社区落实事项
1. 排查范围：辖区内所有高层住宅小区，重点为 10 层以上建筑
2. 排查内容：消防通道、疏散楼梯是否被占用堵塞
3. 工作要求：各社区于 10 月 25 日前完成自查，形成问题清单

二、时间安排
请于2026年10月25日前完成。

三、咨询方式
如有疑问，请联系幸福里社区，电话 010-88886666。
```

要点提取（`_points()`）不是简单截取前几段。
上级文件里的「一、排查范围」这类层级标题，**光取标题没有信息量**——"排查内容"四个字不是要求。
所以取标题时顺手挂上它下面第一句，一句话把这件事说清：

```
排查范围：辖区内所有高层住宅小区，重点为 10 层以上建筑
```

另外两条约束：

1. **不得新增上级没提的要求**。提示词里明确禁止，兜底模板只做搬运不做发挥。
   政务文件擅自加码是要担责的，这一点模型和模板都得守住。
2. **咨询电话取单位对外公开的号码**（`org_contact` 表），不写个人手机。
   这份文件是要贴在楼道里的，写社工个人手机等于把他的号码公开。

### 5.3 草稿来源要说清楚

接口返回 `source: "llm" | "rule"`，页面据此提示：

- `✓ 已由本地模型起草`
- `已用规则模板起草（模型未启用，措辞建议再顺一遍）`

规则拼的草稿结构对但措辞硬，社区看到提示就知道该自己顺一遍。
不告诉他，他会以为这是模型写的。

## 6. 文档生成：三格式，各有各的用处

```python
GET /notices/<id>/export/<fmt>     # fmt = docx / md / txt
```

权限挂 `notice.view` 而不是 `manage`：居民端和街道都要拿文件去贴、去报，
"能看"就该"能导出"，否则只能截屏。

### 6.1 docx：红头公文

按 GB/T 9704-2012 的常用简化约定排：

| 元素 | 规格 |
|---|---|
| 页边距 | 上 3.7cm / 下 3.5cm / 左 2.8cm / 右 2.6cm |
| 版头 | 发文机关标志，红色（C00000），小标宋，二号，居中 |
| 文号 | 仿宋，三号，居中，其下加红色反线（1.5 磅） |
| 标题 | 小标宋，二号，居中 |
| 正文 | 仿宋，三号，首行缩进 2 字符，行距固定值 28 磅 |
| 落款 | 右对齐，右缩进 2 字符 |
| 页码 | 页脚「- 1 -」，四号 |

字体用了「方正小标宋简体」「仿宋」，政务办公机上是标配。
**没装也不影响版式**——字号、行距、缩进都是显式写死的，不依赖字体自身度量，
Word 会自动回退到宋体。

主送机关（`各社区、各有关单位：`）按公文规矩**顶格不缩进**，其余段落缩进 2 字符。
判断方式是「短且以冒号结尾」。

> 实际效果见 `docs/示例-红头公文导出.docx`（从演示库的消防排查通知导出）。

### 6.2 md：可回灌的归档件

导出的 Markdown 带完整元信息头：

```markdown
---
title: 关于开展高层住宅消防安全专项排查的通知
issuer: 幸福里街道办事处
doc_no: 幸街发〔2026〕18号
issued_at: 2026-10-15
category: 通知公告
level: 街道
scope: all
pinned: false
---
```

**这些字段 `parse.py` 全都认**，所以导出件可以直接丢回 `data/notices/` 重新入库。
"导出 → 归档 → 再投递"形成闭环：社区把落地件导出存档，
明年上级来查，这份文件还能被系统重新识别，而不是躺在某个共享盘里谁也搜不到。

> 样例见 `docs/示例-归档件.md`。

### 6.3 txt：给不装 Word 的终端

纯文本，带分隔线和字段列表。用途很实在：粘进微信群、贴进没有 Word 的办公电脑。

### 6.4 为什么没有 PDF

容器里没有能稳定出 PDF 的库（reportlab / weasyprint 都是重依赖且有系统库要求），
硬上一旦装不上就是发布失败。而且公文场景里 PDF 本来就出自「打印 → 另存为 PDF」，
打印前必须人工确认版面。

所以 PDF 交给浏览器：详情页有「打印版（另存 PDF）」按钮，
点开是排版好的 print 版 HTML，Ctrl+P 存 PDF。

## 7. 数据模型：两份文档，两条记录

落地件不是把上级原文改个字段，而是**一条新记录**：

```
notice(id=4)  kind=superior  level=街道  title=关于开展高层住宅…的通知
     ↑ parent_id
notice(id=5)  kind=local     level=社区  title=幸福里社区关于落实…的通知
```

新增字段：

| 字段 | 取值 | 说明 |
|---|---|---|
| `kind` | superior / local / original | 上级来文 / 本级落地件 / 本级原创 |
| `parent_id` | int | 落地件指回上级原文 |
| `recv_status` | "" / dispatched / received | 收文状态，与发布状态解耦 |
| `receiver_org` | 社区名 | 空 = 全体社区 |
| `received_by` / `received_at` | — | 签收留痕 |
| `deadline` | date | 上级要求完成时限，落地件默认继承 |

保留两份记录的理由：

1. 上级原文是**证据**，落地件是**执行**，混成一份就分不清哪句是上级说的、哪句是社区加的；
2. 详情页两件互相链接，谁依据谁一查就到；
3. 落地件可以多份（同一份上级文件，社区给居民一份、给物业一份）。

老库升级时 `kind` 按 `level` 回填：`level=街道` 算上级来文，其余算原创。
一律标 superior 会让"收文待办"里凭空多出一堆假待办。

## 8. 页面

| 页面 | 给谁 | 关键信息 |
|---|---|---|
| `/notices` | 街道 | 在线发文表单、目录导入、公告列表（来源列标「上级来文 / 本级落地」） |
| `/notices` | 社区 | **顶部「收文待办」卡片**，一键签收 |
| `/notices/<id>` | 全部 | 四步流转时间线、导出按钮组、办理区（签收 / 生成落地件 / 发布） |
| `/notices/<id>/localize` | 社区 | 左：草稿表单；右：上级原文对照；底部时限与发布范围 |
| `/portal/notice/<id>` | 居民 | 网页版 / 打印版 / 发布版 |

流转时间线是这一块最值得看的东西，一眼就知道这份文件卡在哪一步：

```
● 上级发文 ──── ● 社区签收 ──── ○ 生成落地件 ──── ○ 对外发布
  幸福里街道办     王社工          未生成            未发布
  10-21 11:11     10-21 11:11
```

### 8.1 页面连续性：一条链走到底，也能原样退回来

这一块原来有两个断点，都是实际点出来的：

**断点一：详情页的返回键在最底下，而且不认来路**

返回键落在整页最底部，两三屏的文件看完还要再滚一遍才能走。
更麻烦的是它写死指向 `/notices`——用户明明是从「待签收」筛出来的，
回去却变成「全部」，得重新找刚才那条。

现在的做法是把**来路当参数传下去**：

```
/notices?recv=dispatched            ← 列表那一屏（筛选在 URL 里）
        ↓ 点标题
/notices/6?back=%2Fnotices%3Frecv%3Ddispatched
        ↓ 生成落地件
/notices/6/localize?back=%2Fnotices%3Frecv%3Ddispatched
        ↓ 提交
/notices/7?back=%2Fnotices%3Frecv%3Ddispatched   ← 落地件
```

`back` 在整个链路里**恒定指向列表那一屏**，不指向中间页。
如果每层都套一层 back，地址会变成俄罗斯套娃，谁也不敢改。
详情页顶部和底部各有一个返回，两条都指同一个地方。

配套的三件事：

| 问题 | 做法 |
|---|---|
| 刷新后筛选丢了 | 筛选条件写进 URL（`?status=` / `?recv=`），不再是 JS 变量 |
| 返回后停在页面顶部 | 滚动位置按"那一屏"存 sessionStorage，列表渲染完再滚回去 |
| 切筛选在历史里堆一长串 | `history.replaceState` 而不是 `pushState`，按一次后退就退得出去 |

> **安全**：`back` 直接拼进 `href`，不校验就是开放重定向——
> 攻击者可以把"返回列表"做成跳到钓鱼站的按钮。校验在 `app/params.py: safe_back()`，
> 只放行以单个 `/` 开头的路径，拒绝 `//evil.com`、`https://...`、`javascript:`、
> 以及 `/\evil.com` 这种反斜杠混淆。测试里有 5 条断言专门打这个。

**断点二：「待签收 3」点进去只有 1 条**

计数用的是全表 `filter_by(recv_status="dispatched").count()`，
而列表该按收文单位过滤。只有一个社区时看不出问题，
一旦街道把文件指定给某个社区，别家的待办就会算进自己的数字里——
点进去还签不了（403）。数字和明细对不上，比不显示更糟。

现在计数和明细同源，都走 `todo_query()`：

```python
q = Notice.query.filter_by(recv_status="dispatched")
if u and "notice.receive" in user_perms(u) and u.org:
    q = q.filter(db.or_(Notice.receiver_org == "", Notice.receiver_org == u.org))
```

收文单位留空的（= 全体社区）每家都算一条；街道没有 `notice.receive`，
它看的是全局督办视图，不做过滤——它的关注点本来就是"全区还有几件没签"。

### 8.2 办完一件，接着办下一件

流程的紧密性不只是"能返回"，还有"不用自己找下一步"：

| 节点 | 原来 | 现在 |
|---|---|---|
| 签收后 | 弹一句"已签收"就刷新，用户还得在右侧重新找办文按钮 | 直接问「现在去办文？」，确认即跳办文页 |
| 发布后 | 弹一句"已发布"停在本页 | 问「还有 N 条待签收，现在去处理？」，确认即跳筛选列表 |
| 详情页顶部 | 无 | 右侧常驻「还有 N 条上级来文待签收 →」 |
| 统计卡 | 纯数字，点不动 | 四张卡都是链接，点了直接筛 |
| 落地件详情 | 只能回列表 | 多一个「↩ 对照上级原文」 |

签收后的那句确认，比"自动跳转"温和，比"弹个提示"有用：
签收只是"我收到了"，真正要办的是下一步，而这个动作该由人决定，
不该替他决定，也不该让他自己回想。

管理端同理：`/admin/users?status=pending` 点进详情，返回时筛选还在。

## 10. 踩过的坑

### 10.1 章节标题和正文黏成一团

上级文件写的是：

```
一、排查范围
辖区内所有高层住宅小区，重点为 10 层以上建筑。
```

两行之间**没有空行**。原来的段落合并逻辑把连续非空行拼成一段，
结果渲染成「一、排查范围辖区内所有高层住宅小区」——标题和正文糊在一起。

因为样例文件恰好都在标题后空了一行，这个问题一直没暴露。
修法：识别「短且以 `一、` `（二）` 开头」的行，让它单独成段。
`render.py`（网页）和 `export.py`（文件）两处都改了，否则网页和导出的 Word 长得不一样。

**"样例全对"不等于代码正确**——这句话在公告解析上已经应验过两次。

### 10.2 落款出现两遍

版式会自动在文末排落款（右对齐、单位 + 日期）。
但如果正文里本来就有落款——上级文件原文末尾都带，社区手工编辑时也可能自己写——
导出件就会出现两个落款。

`parse.py` 入库时已经剥过一次，但正文来源不止一条（在线发文、手工改过的落地件），
所以 `export.py` 里再剥一次。剥的条件是「最后几行等于发文单位或日期」，
也包括「单位和日期挤在同一行」的写法。

### 10.3 落款被挤到第二页

公文规范在落款前留 2 行当印章区。但内容刚好占满一页时，
这 2 行会把落款推到第二页，出现"整页只有落款"的难看版式。

改成段前 14 磅，一页能装下就装下。内容真的超过一页的，
落款在第 2 页也属正常，不强求。

### 10.4 `card-h` 里的说明文字盖住标题

公告列表的卡片头是「标题 + 说明 + 四个筛选按钮」。
按钮组用 `margin-left:auto` 靠右，空间不够时说明文字被压成 0 宽，
文字**溢出到标题上**，看起来是两个字符串叠在一起。

修法：标题 `flex-shrink:0`，说明文字 `flex:1; min-width:0; overflow:hidden`。
`min-width:0` 是关键——flex 子项默认 `min-width:auto`，不加这句它不会缩到内容宽度以下。

这跟居民端 `portal.css` 里修「中文不断词撑破容器」是同一个坑的两种表现。

### 10.5 中文文件名在 HTTP 头里是编码的

`send_file(download_name="关于开展…的通知.docx")` 输出的响应头是：

```
Content-Disposition: attachment; filename=.docx; filename*=UTF-8''%E5%85%B3%E4%BA%8E...
```

`filename=` 那一段是空的（非 ASCII 无法放进 ASCII 头），真名在 `filename*` 里。
Chrome / Firefox / Edge 都认 RFC 5987，下载后文件名正常。
只有很老的 IE 会退化成 `.docx`。这不是 bug，是标准做法。

## 11. 局限

| 项 | 现状 | 可改进 |
|---|---|---|
| 落款印章 | 只排文字，不嵌印章图片 | 支持上传单位印章 PNG，按位置贴到落款处 |
